## Why this document exists

WP-4 built `SmartStudyPlanner.Tests/Services/WorkloadServiceScheduleTests.cs` — **16 test methods /
21 cases** characterizing `WorkloadServiceImpl.GenerateSchedule` — and proved non-vacuity by mutating
the allocator seven ways, including *least-loaded vs. earliest-with-room placement* and *reversing the
priority sort*. Those are exactly the two axes T3.3 will change.

So some of that suite will go red **on purpose**. Nobody has written down which. Without this, the
first red test during T3.3 becomes an argument instead of a decision — and the likeliest wrong
resolution ("make it green again") silently reverts the rework it was supposed to protect.

This is that missing input. It changes no test and no production code.

## 1. The finding that outranks the buckets: the corpus is deadline-degenerate

```csharp
// WorkloadServiceScheduleTests.cs:277-278
private static StudyTask NewTask(string ten)
    => new StudyTask(ten, FixedNow.AddDays(5), LoaiCongViec.BaiTapVeNha, 2);
```

`NewTask` hardcodes `FixedNow.AddDays(5)` as the deadline for **every task in every fixture**. All 21
cases therefore run a single-deadline corpus. Two consequences, and the second is the one that costs
money:

1. **The suite cannot detect a deadline regression at all.** This is deliberate — the class docstring
   (`:22-24`) says so and names Epic 3 / G2 as the owner. Not a defect.
2. **Most tests survive T3.3 by construction, not because they are deadline-neutral.** With all
   deadlines equal, any deadline-driven sort degenerates to the existing priority sort. "Still green
   after the rework" is therefore *much* weaker evidence than it looks. Green here means "the rework
   did not break the degenerate case" — it does not mean the invariant holds under varied deadlines.

Anyone reading a green suite during T3.3 as validation of deadline-awareness is reading it wrong.

## 2. Classification — 16 methods / 21 cases, five buckets

| # | Bucket | Methods / cases | Meaning during T3.3 |
|---|---|---|---|
| ① | **Certain flip** — baseline to be replaced | 1 / 1 | Expected red. Rewrite the assertion, don't revert the code. |
| ② | **Strategy-dependent** — purpose invariant, assertion placement-coupled | 4 / 5 | Red iff a strategy other than earliest-feasible is chosen. |
| ③ | **G2-dependent** — the only infeasible fixture | 2 / 2 | Do not bank on these until G2 closes. |
| ④ | **Seam decision**, not an invariant | 1 / 1 | Decide deliberately at M3.1. |
| ⑤ | **Clean invariant** — must survive unchanged | 8 / 12 | Red = real regression. Full stop. |

Arithmetic check: 1+4+2+1+8 = **16 methods**; 1+5+2+1+12 = **21 cases**.

### ① Certain flip — 1 method / 1 case

- **`GenerateSchedule_ChonNgayITAINHAT_ChuKhongPhaiNgaySomNhatConCho`** (`:173`) — the only test that
  dies under *any* deadline-driven placement. It pins the least-loaded rule at
  `WorkloadServiceImpl.cs:139-141`:

  ```csharp
  var targetDay = days.Where(d => d.TotalMinutes < capacityMinutes)
                     .OrderBy(d => d.TotalMinutes)     // ← this is what the test records
                     .FirstOrDefault();
  ```

  The fixture leaves day 1 with exactly enough room for "Thấp", and asserts the allocator **skips it**
  for the empty day 2. Earliest-feasible, latest-feasible and compaction all eliminate that behavior.
  The test's own comment already frames the behavior as recorded, not endorsed ("Công việc bị TRẢI RA
  chứ không dồn vào các ngày sớm"). **Expected casualty. Rewrite it in T3.3 to pin the new rule, with
  the same mutation check WP-4 used.**

### ② Strategy-dependent — 4 methods / 5 cases

Purpose is invariant; the assertion happens to name a day index or rely on `days` order.

- **`GenerateSchedule_UuTienCaoDuocXepTruoc`** (`:162`) — reads
  `days.First(d => d.Tasks.Count > 0).Tasks[0]`. Under latest-feasible, "Cao" lands on day 5 and "Thấp"
  on day 4, so the first non-empty day holds "Thấp" and the test goes red **even though priority
  ordering was honored perfectly**. Green under earliest-feasible.
- **`GenerateSchedule_CapacityVoHan_BaoHoaChuKhongTranSoAm`** (`:242`, **2 cases**) — the int-saturation
  and termination content is strategy-neutral and belongs in ⑤; `Assert.Equal(180, days[0].TotalMinutes)`
  at `:258` is not. Under any strategy that starts later than day 0, the day index is wrong while the
  actual guarantee still holds.
- **`GenerateSchedule_ViecBiCatNho_DuocDanhSoPhan`** (`:126`) — reads names via
  `days.SelectMany(d => d.Tasks)`, so the `(Phần 1/2/3)` *sequence* holds only while `days` stays
  date-ordered and the parts are laid down in increasing date order. The naming rule itself
  (`WorkloadServiceImpl.cs:160`) is invariant; the ordering of the flattened list is not.
- **`GenerateSchedule_ViecVuaDuMotNgay_KhongBiDanhSoPhan`** (`:137`) — the invariant it carries (the
  `(Phần n)` naming boundary: a task that fits exactly keeps its bare name) is genuinely
  strategy-neutral, but both assertions name `days[0]` (`:145-146`), and
  `Assert.Single(days[0].Tasks)` **throws** rather than fails informatively when the task lands
  elsewhere. Decoupling is `First(d => d.Tasks.Count > 0)`.

If earliest-feasible is ratified, all five cases stay green — which is precisely what makes a red one
here meaningful.

### ③ G2-dependent — 2 methods / 2 cases

Both use `("Rất dài", 90, 600)` at 60 min/day: **600 minutes needed against 360 available before the
day-5 deadline** (days 0–5; 300 under the stricter reading that the 09:00 deadline makes day 5
unusable — infeasible either way, and which reading applies is itself a T3.1 constraint-validator
question). This is the suite's only infeasible input.

- **`GenerateSchedule_HetChoTrong7Ngay_ThiMoThemNgay`** (`:150`) — asserts 10 days, 600 minutes total.
- **`GenerateSchedule_CacNgayLuonLienTiep_KeCaNgayMoMoThem`** (`:49`) — asserts the date sequence has no
  gaps or duplicates, including days opened past the initial 7 (`WorkloadServiceImpl.cs:145-146`).

Both assertions will *probably* survive — the minutes still have to go somewhere, and contiguity is
independent of placement. But **what a deadline-aware allocator is permitted to do with an infeasible
input is exactly the G2 question** (does the pass reject, partially commit, or commit with a reported
violation?). Treat these as provisional until G2 closes; do not cite them as invariants in the T3.3
review.

### ④ Seam decision, not an invariant — 1 method / 1 case

- **`GenerateSchedule_GhiDeDiemUuTien_ChiTrenTaskChuaHoanThanh`** (`:75`) — pins the impurity:
  `GenerateSchedule` writes `DiemUuTien` straight into the caller's model
  (`WorkloadServiceImpl.cs:112`), and only for tasks that pass the not-completed filter (`:110`).

  The SOE boundary is `Optimize(schedule) → (schedule, report)`. A pure seam may deliberately drop that
  side effect, in which case this test is *correctly* red and should be deleted or moved to whatever
  keeps owning priority stamping. **Decide it at M3.1, in writing.** The failure mode to avoid is
  letting it go red mid-T3.3 and getting "fixed" by re-adding the write-through out of reflex.

### ⑤ Clean invariant — 8 methods / 12 cases

Red here means a real regression, whatever strategy T3.3 picks.

Note *why* the two clean capacity tests are clean while `CapacityVoHan` (②) and

difference between bucket ② and bucket ⑤**, and it is the pattern to copy when writing T3.3's
replacements — a test can carry a perfectly strategy-neutral invariant and still be placement-coupled
purely through how it reaches the day it asserts on.

## 3. Recommended placement strategy — earliest-feasible

**Recommended, not ratified.** T3.3 owns the decision; this is the default that must be argued against.

**Earliest day with room, among days on or before the deadline.**

**Load-bearing assumption, stated explicitly:** deadline governs *day selection only*; **priority stays
the task-ordering key** (`WorkloadServiceImpl.cs:118`). Both this recommendation and §1's "any
deadline-driven sort degenerates to the priority sort under equal deadlines" depend on it. If T3.3
instead makes deadline the primary *task* sort, equal-deadline tasks fall back to insertion order and
`UuTienCaoDuocXepTruoc` (`:162`) can go red even under earliest-feasible — which would move it from
② into ①. Revisit this section if that is the direction taken.

- Keeps all five bucket-② cases green, so a red test there during T3.3 signals a genuine regression
  rather than an expected consequence of the strategy choice. That is worth real money in review time.
- Closest to today's observable behavior on feasible inputs, so T3.3's diff stays reviewable and the
  characterization suite keeps most of its value as a safety net.
- Latest-feasible / just-in-time consumes the slack before a deadline, so any estimate error turns
  directly into a miss — the failure mode D-G's inversion test exists to prevent.

**Honest caveat:** it does *not* keep bucket ① green. That flip is the entire point of T3.3 —
earliest-feasible is chosen for the cases it preserves, not because it preserves everything.

T3.6 is **one third done, not "partly done"**: the characterization tests exist; the ≥200-schedule
corpus and the quantified baseline do not.

- **The corpus must carry varied deadlines.** The existing fixtures cannot express a deadline

- **Capture the baseline at current HEAD**, and as a committed artifact rather than prose in a report.

## 5. Decisions made (ADR-style)

### D1 — Classify now, change nothing

- **Why:** the obvious move is to pre-emptively loosen the placement-coupled assertions (`days[0]` →
  "the first non-empty day") so T3.3 has fewer reds to triage. That weakens the baseline *before* a
  rework exists to measure it against, and WP-4's contract is explicit that the implementation is the
  spec. A test loosened in advance records nothing.
- **What for:** the suite keeps its full discriminating power through the start of T3.3; the
  de-coupling lands *inside* T3.3, beside the new behavior, mutation-verified the same way WP-4
  verified the originals.
- **Experience:** WP-4's own value came from mutation proof, not from the tests existing. Edits made
  without a mutation check beside them are how a characterization suite quietly becomes decoration.

### D2 — Five buckets, not two

- **Why:** the requested framing was "baseline vs. invariant". Two buckets hide the case that actually
  costs time during a rework: a test whose *purpose* is invariant but whose *assertion* is coupled to
  placement. Bucket ② is that distinction made explicit; ③ and ④ separate "blocked on a gate" and
  "blocked on a design decision" from "expected to break".
- **What for:** each bucket carries a different instruction for the person staring at a red test —
  rewrite it (①), check the strategy (②), wait for G2 (③), make the seam call (④), stop and
  investigate (⑤).
- **Experience:** "make it green" is the default reflex under time pressure, and it is correct for
  exactly one of these five buckets.

### D3 — Recommend a strategy without deciding it

- **Why:** an unratified default that must be argued against produces better decisions than an open
  field, but ratification belongs where the code exists to check it — T3.3 — not in a planning
  document written before the constraint validator (T3.1) is built.
- **What for:** M3.0 can proceed without blocking on a strategy debate, and T3.3 inherits a stated
  position plus the reason it might be wrong.
- **Experience:** the frozen guardrails (D-G/D-H/D-J) already narrow the field; what remains is a
  trade-off between reviewability and slack preservation, and that is legitimately T3.3's call.
