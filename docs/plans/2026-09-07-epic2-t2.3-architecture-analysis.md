## 1. Current verified facts

### 1.1 T2.2's output and how T2.3 must consume it

`SyncChangeEnumerator.GetChangesForPeerAsync(db, peerId, ct)` (`Sync/SyncChangeEnumerator.cs:37-53`) returns a `PeerChangeSet` — six `List<ChangedEntity<T>>`, one per synced entity (`Sync/PeerChangeSet.cs:6-12`). `ChangedEntity<T>` is `(Guid EntityId, T Entity, long Rev, bool IsDeleted)` (`Sync/ChangedEntity.cs:5`).

Two facts shape T2.3's design, not just its plumbing:

- **`Entity` is a tracked instance, not a DTO.** `GetChangesForPeerAsync` calls `await db.HocKys.ToListAsync(ct)` etc. on the *same* `AppDbContext db` it was handed (`SyncChangeEnumerator.cs:41-52`), then wraps those tracked rows into `ChangedEntity<T>`. If T2.3 runs merge-apply against this same context, every entity it touches is already attached to a change tracker whose `SaveChanges` override calls `SyncStamper.Apply` unconditionally (`Data/AppDbContext.cs:127-137`). The seam problem (§3) is reachable directly through T2.2's own return type, not only at some later, separate write call.
- **Enumeration is in-memory, not SQL-filtered.** `EnumerateChangesAsync<T>` loads the *entire* table (`db.HocKys.ToListAsync`, no `Rev > x` predicate in SQL) and filters in C# against the per-peer baseline dictionary (`SyncChangeEnumerator.cs:20-34`). Correct for M2.1's "fixture peers, no network" scope; T2.3 inherits an unfiltered enumeration and must not assume SQL-side filtering exists.

Watermark predicate actually shipped: `include row ⟺ no snapshot for (peer, entityType, row.Id) OR row.Rev > snapshot.Rev` — a per-(peer, row) baseline, not a single scalar per peer, per the guidelines' §2.2 design.

### 1.2 Base-snapshot semantics available for the 3-way merge

**This is the tightest finding in this pass: the base leg of the 3-way diff does not exist yet, by design, not by oversight.**

- `SyncBaseSnapshotRow.SnapshotJson` is `string?`, explicitly documented as "**Opaque, caller-supplied. NO code in this slice reads or interprets its contents — T2.3 (not built yet) decides that shape.**" (`Sync/SyncBaseSnapshotRow.cs:15-18`).
- `SyncBaseSnapshotStore` (`Sync/SyncBaseSnapshotStore.cs`) provides `Get`/`GetAllForPeer`/`Set`/`Delete` — a working container — but **zero production call sites exist** on `dev` (verified: `git grep` for `SyncBaseSnapshotStore\.` and `SyncChangeEnumerator\.` across `origin/dev` `*.cs` returns hits only under `SmartStudyPlanner.Tests/`). The store round-trips arbitrary fixture strings in tests; nothing writes a real snapshot in production.
- Consequence: **T2.3 does not "consume" a base snapshot — it must define the snapshot's serialization contract and be the first production writer of `SnapshotJson`.** That is new design surface, not wiring.
- **`snapshot.Rev` is not a substitute for the base snapshot.** `Rev` answers "did this row change since last sync" (change enumeration); it carries no field-level information. A T2.3 implementation that diffs current-vs-current and ignores `SnapshotJson` degenerates to entity-level LWW — precisely the lossier policy `lessons-learned.md` L7 documents D-F as rejecting ("*you cannot merge changes you cannot detect*").
- **Corollary on convergence:** if merge-apply bumps the local `Rev` of a merged row (per §3's analysis, it plausibly should, to re-offer the merged state next round), then the `SetAsync` call that records the new post-sync baseline must store the **post-apply** `Rev`, not the pre-apply one — otherwise the row re-enumerates as "changed" on every subsequent round and convergence (Epic 2's own acceptance criterion: "two peers at the same watermark hold identical data," master plan §Epic 2) never quiesces.

### 1.3 The frozen policy T2.3 must implement

From `docs/architecture/data-model.md` §8 (D-F + D-I, frozen) and `lessons-learned.md` L6/L7/L9 — restated here because T2.3's code must match this exactly, not a paraphrase:

> Field-level merge by default; a field changed on **both** sides relative to the base is a concurrent same-field edit → LWW with tie-break `ModifiedAtUtc` → `ModifiedByDeviceId` (lexicographic). Delete-vs-edit: tombstone wins. The losing side of every conflict is preserved in a conflict record (T2.4). No HLC.

The role-separation table (L6) is load-bearing: `Rev` is excluded from the tie-break ordering entirely — it is not a fallback, not a secondary key, not consulted at all once a conflict is identified by the 3-way diff.

**A naive-implementation trap worth naming explicitly:** `ModifiedAtUtc`/`ModifiedByDeviceId` are stored **per row**. The rule is defined **per field** ("a field differing from base on both sides is a concurrent same-field edit," L6). Applying the row-level `ModifiedAtUtc`/`DeviceId` pair to resolve *the whole row* — rather than to each individually-conflicting field — silently reimplements entity-level LWW under a field-level name. This is the single easiest way to build a plausible-looking, wrong T2.3.

## 2. Required T2.3 contract (derived, not decided)

Given §1.1–1.3, T2.3 must at minimum:

1. Define and own `SnapshotJson`'s serialization shape (per-entity-type field maps at minimum).
2. Be the first writer of `SyncBaseSnapshotStore.SetAsync` in a real (even if fixture-driven) code path.
3. Compute, per entity in a `PeerChangeSet` list, a 3-way diff against `(local current, remote incoming, base snapshot)`.
4. For each field: no-op if unchanged from base on both sides; take the non-base side if changed on exactly one side; apply LWW (`ModifiedAtUtc`→`DeviceId`, both row-level, per §1.3's trap) only where changed on **both** sides, and emit a conflict-record candidate for T2.4 to persist.
5. Write the merged row back through a path that does **not** let `AppDbContext.SaveChanges*`'s unconditional stamping (§3) overwrite the winning side's `ModifiedAtUtc`/`ModifiedByDeviceId` with local now/local device.
6. Decide (and record in its own DoR note, not here) whether merge-apply bumps local `Rev`, and if so, ensure the corresponding `SetAsync` baseline update uses the post-apply value (§1.2 corollary).

## 3. SyncStamper seam analysis

### 3.1 Current call path

Single seam, two entry points, confirmed identical on `dev`:

```
AppDbContext.SaveChanges(bool)          → SyncStamper.Apply(ChangeTracker, Clock, DeviceIdProvider())
AppDbContext.SaveChangesAsync(bool, ct) → SyncStamper.Apply(ChangeTracker, Clock, DeviceIdProvider())
```
(`Data/AppDbContext.cs:127-137`)

`SyncStamper.Apply` (`Data/SyncStamper.cs:21-43`):

```csharp
foreach (var entry in tracker.Entries().ToList()) {
    if (entry.Entity is not ISyncMetadata meta) continue;
    if (entry.State is EntityState.Added or EntityState.Modified) {
        meta.Rev++; meta.ModifiedAtUtc = utcNow(); meta.ModifiedByDeviceId = deviceId;
    } else if (entry.State == EntityState.Deleted) {
        entry.State = EntityState.Modified;
        meta.Rev++; meta.IsDeleted = true; meta.DeletedAtUtc = utcNow();
        meta.ModifiedAtUtc = utcNow(); meta.ModifiedByDeviceId = deviceId;
    }
}
```

`Clock` and `DeviceIdProvider` are **public settable properties** on `AppDbContext` (`Data/AppDbContext.cs:20,25`) — `utcNow`/`deviceId` are read fresh from these on every `SaveChanges*` call, batch-wide.

### 3.2 Exactly how remote-winner metadata is corrupted

Two distinct corruption routes, both already implied by the code above:

- **Modified branch (normal field merge-apply).** T2.3 writes a merged row whose winning field(s) carry the remote device's real `ModifiedAtUtc`/`ModifiedByDeviceId` as the provenance the *next* sync round's LWW must read. If that write reaches `SaveChanges*` as an `Added`/`Modified` entry, the seam overwrites both fields with **this device's** clock and id — the remote provenance is destroyed on first apply, and the next 3-way merge round has no way to recover which device actually authored the winning value.
- **Deleted branch (remote tombstone apply) — corrupts one field more than the Modified branch.** Applying a *remote* tombstone (the other peer deleted a row) is itself a local `Remove()` or an `IsDeleted=true` assignment; either route lands in the `Deleted`-or-Modified branch and the seam stamps `ModifiedAtUtc`, `ModifiedByDeviceId`, **and `DeletedAtUtc`** to local now/local device — three fields corrupted, not two, and the corruption is reachable via either mechanical route (calling `Remove()` vs. hand-setting `IsDeleted`), so a fix must cover both.

### 3.3 Minimum safe engineering seam(s) — narrowed, not chosen

The readiness plan (`2026-09-07-epic-2-lan-sync-readiness-and-execution-plan.md` §1.3) already named two candidates and explicitly declined to choose between them. This pass narrows, but does not decide, per its own mandate:

- **What the architecture already rules out:** `data-model.md` §8 and `sync-data-model.md` both assert, as a re-verified invariant, that no raw-SQL/`ExecuteUpdate`/`ExecuteDelete` write bypasses the seam **on synced entities' business writes**. That excludes "bypass `SaveChanges*` via a raw-SQL write" as a *silent* option outside the architecture's own audited invariant — any seam that routes around `SaveChanges*` must be treated as a new, audited exception to that invariant, not a quiet shortcut. It does not, by itself, pick between the two remaining in-seam variants (a suppression flag on `SyncStamper` vs. a dedicated merge-apply method that still calls `SaveChanges*`).
- **A plausible-looking wrong answer worth flagging explicitly, because the seam's own shape invites it:** temporarily reassigning `db.Clock`/`db.DeviceIdProvider` to return the remote value around a merge-apply `SaveChanges` call. This *looks* like it preserves provenance, but `Clock`/`DeviceIdProvider` are read once per `SaveChanges*` call and applied to **every** `ISyncMetadata` entry in that batch (`SyncStamper.cs:21` iterates `tracker.Entries()`) — it would corrupt every *other* entity's stamping in the same batch, including genuine local edits saved alongside a merge-apply. Name this as an anti-pattern in T2.3's own review checklist and give it a dedicated test (§8).
- Neither candidate is chosen here.

### 3.4 The existing precedent T2.3 should study, not copy blindly

`SqliteHocKyRepository.CopySyncSafeValues` (`Infrastructure/Persistence/SQLite/Repositories/SqliteHocKyRepository.cs:224-241`) solves the *mirror-image* problem: it protects a **tracked** entity's real `ISyncMetadata` from being stomped by an **incoming detached POCO's** stale/default values, by snapshotting `Rev`/`ModifiedAtUtc`/`ModifiedByDeviceId`/`IsDeleted`/`DeletedAtUtc` before `SetValues(source)` and restoring them after. A merge-apply write needs the same *shape* of guard in the **other** direction — preserve incoming *remote* metadata against the seam's own stamping, not protect existing local metadata against an incoming POCO. Same pattern, opposite direction; do not reuse the method as-is.

## 4. Entity-by-entity merge considerations

All six implement `ISyncMetadata` (`Models/ISyncMetadata.cs:9-16`: `Rev`, `ModifiedAtUtc`, `ModifiedByDeviceId`, `IsDeleted`, `DeletedAtUtc`) and are `DbSet<T>` on `AppDbContext` with **no `HasQueryFilter`** (confirmed: `OnModelCreating`, `AppDbContext.cs:69-118`, has none) — direct `DbSet` queries (what `SyncChangeEnumerator` uses) see tombstones; only each `Sqlite*Repository`'s explicit `.Where(!IsDeleted)` hides them.

## 5. Hidden write paths T2.3 could accidentally bypass or must not repeat

Swept every `Sqlite*Repository`'s write methods for the six synced entities plus the schema-migration seams:

**Cleared (no hazard) — reported because negative evidence has weight here:**
- `IStudyTaskRepository.UpdateAsync` (`SqliteStudyTaskRepository.cs:46-51`) — **zero production callers** (`git grep` confirms; only test call sites). `StudyTask` writes go exclusively through `LuuHocKyAsync`'s `CopySyncSafeValues`-protected reconcile path.
- `SqliteTaskEditorRepository.UpsertNoteAsync` (`SqliteTaskEditorRepository.cs:35-46`) — mutates a **tracked** entity's `Content` in place; safe, no metadata exposure.
- `AddLinkAsync`/`DeleteLinkAsync` (`SqliteTaskEditorRepository.cs:57-62, 71-80`) — plain `Add`/`Remove` through the normal seam; no bypass.

**Live defect, latent today, will become load-bearing under Epic 2 — the strongest finding in this pass:**

`SqliteTaskEditorRepository.UpdateLinkAsync` (`SqliteTaskEditorRepository.cs:64-69`) calls `db.TaskReferenceLinks.Update(link)` on a **detached** POCO. In production, that POCO is built by `TaskReferenceLinkItemVm.ToModel()` (`ViewModels/TaskReferenceLinkItemVm.cs:25-32`), called from `QuanLyTaskViewModel.cs:240`. `ToModel()` never sets `Rev`, `ModifiedAtUtc`, `ModifiedByDeviceId`, `IsDeleted`, or `DeletedAtUtc` — they arrive at CLR defaults (`Rev=0`, `IsDeleted=false`, `DeletedAtUtc=null`). `db.Update(link)` marks the **entire** entity `Modified` using those defaults as current values; `SyncStamper.Apply`'s `Modified` branch then does `meta.Rev++` starting from **0**, so every edit of an existing link resets its `Rev` to `1` — **not** the true incremented value.

**Why this matters for T2.2/T2.3, not just as a bug report:** T2.2's enumeration predicate is `row.Rev > snapshot.Rev`. If a peer's recorded baseline for a link is, say, `Rev=5` (from a prior sync), and a later edit resets the live row's `Rev` back to `1`, that peer's next enumeration silently **excludes** a real edit (`1 > 5` is false) — a genuine, silent data-loss path for `TaskReferenceLink` specifically, independent of anything T2.3 does.

The existing test (`RepositoriesTests.cs`, the `SqliteTaskEditorRepository` CRUD test) is green only because it **reuses the same in-memory object reference** across `AddLinkAsync` and `UpdateLinkAsync` calls — the object's `Rev` field already holds the value `SyncStamper` stamped during `Add`, so the reset never manifests in that test's specific object-reuse shape. It does not exercise the actual production shape (`ToModel()` minting a fresh POCO on every edit), so the defect is real, live-reachable via the existing UI today, and untested.

**Framing:** this is **latent, not currently live as a sync-correctness problem**, because T1.4/T2.2 have zero production callers today — but it becomes live the moment M2.2's transport wires enumeration into a real sync round, and it will silently break Epic 2's own T2.5 convergence property specifically for `TaskReferenceLink`. It is a **bug to fix in the existing repository layer**, not a T2.3 design decision, and not an owner-policy question — flagging it here because T2.3 is the first consumer that would actually notice its effects.

**One more raw-SQL write worth being precise about:** `Data/SyncSchema.cs:47` runs `ExecuteSqlRaw("UPDATE TaskNotes SET ModifiedAtUtc = UpdatedAtUtc")` — a one-time upgrade backfill that writes directly to a synced entity's metadata column, bypassing the `SyncStamper` seam. It is intentionally out-of-seam (a schema migration, not a business write) and does not contradict `data-model.md` §8's "no raw-SQL bypass on synced entities" — but that invariant is therefore true of **business writes** only, and T2.3 should not cite it as covering migration seams too.

**A requirement rather than a path:** a merge-applied **parent tombstone** (e.g., a remote-deleted `StudyTask`) is a new delete path by definition. Per `sync-data-model.md`'s standing rule ("*whenever a new delete path is added to a synced entity, route it through the shared cascade helper*"), it must call `TaskCascadeHelper.RemoveChildrenAsync` (`TaskCascadeHelper.cs:17-24`) or leave `TaskNote`/`TaskReferenceLink` children live-but-orphaned pointing at a tombstoned parent — exactly the class of bug `sync-data-model.md`'s cascade-tombstone lesson documents as having shipped once already, undetected, because the affected repository method had zero production callers at the time.

## 7. Proposed T2.3 acceptance / evidence checklist

Mapped onto the master plan's 7-item DoD (§"Definition of Done (every epic)") plus Epic 2's own stated acceptance criteria (master plan §"Epic 2 — LAN Sync Engine"):

- Different-field concurrent edits both survive intact (field-level merge proven, not just claimed).
- Same-field concurrent edits resolve by LWW `ModifiedAtUtc`→`ModifiedByDeviceId`, applied **per conflicting field**, not per row (§1.3 trap).
- The loser of every field-level and delete-vs-edit conflict is captured in a form T2.4 can persist as a conflict record (T2.3 does not need to persist it itself, per its own scope fence, but must produce it as a return value).
- Delete-vs-edit: tombstone wins; the edit is the T2.4-bound loser, not silently dropped.
- A remote-won field, after apply and a fresh reload from the DB, still carries the **remote** device's `ModifiedAtUtc`/`ModifiedByDeviceId` — not local now/local device (direct evidence the seam gap is closed).
- `gitnexus_impact` run before editing `SyncStamper`/`AppDbContext`; HIGH/CRITICAL reported before proceeding (per project CLAUDE.md mandate, doubly applicable here since both are flagged zero-diff by T1.4/T2.2's own DoD).
- `gitnexus_detect_changes` run before commit; scope matches only the files this task's DoR/scope fence names.
- Full suite green against the current baseline (487 tests baseline predates T1.4/T2.2; re-capture the actual current total/passed/skipped before starting, per this repo's own "cite a measured number, not a remembered one" convention).
- Architecture docs (`data-model.md` §8, `sync-data-model.md`) updated **after** code lands, per D-C.

## 8. Tests that should fail against a deliberately incorrect implementation

One test per sub-claim, each provably red under a specific wrong implementation (per this repo's own "a test that has never been observed to fail is not verified" standard, `2026-09-07-epic2-t1.4-t2.2-implementation-guidelines.md` §6.4):

| Test | Wrong implementation it catches |
|---|---|
| First-ever sync, no base snapshot exists | An implementation that treats "no snapshot" as "both sides changed everything" instead of "no conflict possible yet" |
| Different-field-both-sides-changed → both fields present in the merged result | Entity-level LWW (whole row replaced) instead of field-level merge |
| Same-field-both-sides-changed → LWW picks the later `ModifiedAtUtc` | Base-ignoring diff (treats every differing field as a conflict even when only one side actually changed it) |
| Tie-break reversed: equal-but-for-`DeviceId` timestamps → lexicographically smaller `DeviceId` loses per the frozen ordering | An implementation with the tie-break direction backwards, or using `>=`/`<=` inconsistently |
| Loser holds a much higher `Rev` than the winner | An implementation that (wrongly) consults `Rev` in the tie-break instead of ignoring it entirely (L6) |
| Two sides make the identical change to the same field | Must **not** produce a conflict record — a diff that compares "differs from base" without also comparing "sides differ from each other" over-reports conflicts |
| One-sided change (only one peer touched the field) | Must merge cleanly with **zero** conflict record — catches an implementation that LWWs every field that merely differs from the base, regardless of whether both sides touched it |
| Remote-won value, reloaded fresh from DB after apply | `ModifiedAtUtc`/`ModifiedByDeviceId` still equal the **remote** device's original stamped values — this is the direct regression test for §3's seam gap |
| Remote tombstone applied to a parent (`StudyTask` or `MonHoc`) with live `TaskNote`/`TaskReferenceLink` children | Children end up tombstoned too, not left live-and-orphaned (catches a merge-apply delete path that doesn't call `TaskCascadeHelper`) |
| Two devices independently create a `TaskNote` for the same task while offline, then sync | Exercises the unique-index collision (§4) — must not throw an unhandled constraint violation; resolution behavior depends on the owner decision in §9 |
| Apply the identical changeset twice (idempotence) | Second apply must not double-bump `Rev` or emit a duplicate conflict record — catches a merge-apply that isn't idempotent against retried/duplicated sync rounds |
| Suppression-flag or clock/device-override anti-pattern (§3.3) applied to a batch containing a merge-apply write **and** an unrelated local edit in the same `SaveChanges` call | The local edit must still be stamped with the local device's real clock/id — catches the "reassign `Clock`/`DeviceIdProvider` around the call" anti-pattern corrupting sibling writes in the same batch |

## 9. Owner-policy blockers (must STOP, not decided here)

Genuine policy questions, distinct from engineering seam choices that belong in T2.3's own DoR note:

- **FK-reparent mergeability** (`MonHoc.MaHocKy`, `StudyTask.MaMonHoc`): is an FK a normal LWW-eligible field, or does a concurrent reparent need its own conflict class? `LuuHocKyAsync`'s existing invariant (throws if a task's `MonHoc` isn't in the loaded graph) suggests the codebase already treats this as structurally special, but no decision record says how a *merge* should handle it.
- **`TaskNote` unique-index collision** (§4): two independently-created notes for the same task under concurrent offline edits — which one wins, or do both survive under a schema change? This interacts with the 1-1 cardinality invariant itself, not just field values.
- **`HocKy.IsSeeded` and `[NotMapped]` fields**: confirm these are excluded from the synced field set entirely (this pass recommends exclusion as the only coherent reading of existing code, but it is a policy confirmation, not something T2.3 should decide unilaterally).
- **Creation-provenance immutability** (`StudyLog.CreatedAtUtc`/`DeviceId`, `TaskReferenceLink.CreatedAtUtc`): confirm these are never touched by merge — this reads as the obvious answer, but it is written down nowhere as a ratified rule, and `TaskReferenceLinkItemVm.ToModel()` (§5) already demonstrates the codebase overwriting a "creation" timestamp on every edit once, unintentionally.
- **Six pre-existing, unresolved Epic 2 gates** already on record and out of this task's scope to touch (repeated from the readiness plan for completeness): LAN transport mechanism, discovery mechanism, sync trigger model, maximum offline window, tombstone retention/purge authority, and Epic 2-vs-G3-1 sequencing. None of these block T2.3 specifically (M2.1 is network-free), but T2.3's own conflict-record output feeds T2.4, which is downstream of some of these.

**Engineering choices that must be settled in T2.3's own DoR note, not escalated as owner policy:** the `SyncStamper` seam mechanism (§3.3's two candidates), and whether merge-apply bumps local `Rev` (§1.2 corollary).

## 10. Ready for implementation: **NO**

Three concrete blockers, one structural:

1. **Structural — the base leg of the 3-way merge does not exist.** `SyncBaseSnapshotRow.SnapshotJson` has no defined contract and no production writer (§1.2). T2.3 cannot be "implemented" against an undefined input; defining that contract is itself T2.3-scoped design work that has not happened yet.
2. **The `SyncStamper` seam mechanism is an open engineering decision** (§3.3) — two viable candidates exist, neither chosen, and the architecture only narrows (rules out silent raw-SQL bypass) rather than picks between them.
3. **The entity-by-entity field-participation table (§4) is not yet ratified** — in particular the FK-reparent question and the `TaskNote` unique-index hazard are unresolved and materially change what "field-level merge" means for three of the six entities.

Additionally, **the `TaskReferenceLink` Rev-reset defect (§5) should be fixed before T2.3 lands**, since it currently means one of the six entities' core sync-metadata invariant (`Rev` monotonically increases) is already false in production, and T2.3's correctness depends on that invariant holding for its enumeration input.

None of the above requires new owner-level product decisions beyond what §9 already lists — they are design/engineering work items that belong in T2.3's own Definition-of-Ready note, per this repo's own DoR convention (master plan §"Definition of Ready," item 1: "no OPEN gate in the task's blast radius").

## Decisions made

This document is an analysis, not an implementation or a ratification — consistent with its
scope fence (read-only; no owner/policy decisions made; no roadmap/planning documents edited).
Restated here per this repo's report convention:

- **Why.** T2.3 was about to be scheduled after T1.4/T2.2 shipped; before committing engineering
  time, the codebase needed an evidence-based check of whether the base-snapshot input,
  `SyncStamper` seam, and per-entity field rules T2.3 depends on actually exist and are settled.
- **What for.** To produce a DoR-gate verdict for T2.3 and hand the owner/implementer a
  concrete punch list instead of discovering the base-snapshot gap and the `SyncStamper`
  corruption path mid-implementation.
- **Experience / outcome.** Verdict: **not ready**. Three blockers found (base-snapshot
  contract undefined with no writer; `SyncStamper` seam fix unchosen between two named
  candidates; entity field-participation table unratified, especially FK-reparent and the
  `TaskNote` unique-index collision), plus one independent, previously-undocumented defect
  (`SqliteTaskEditorRepository.UpdateLinkAsync` resets `TaskReferenceLink.Rev` to 1 on every
  edit via a detached-POCO `Update()` call from `TaskReferenceLinkItemVm.ToModel()`) that
  should be fixed before T2.3 is tested against it. No alternatives were rejected — this
  document narrows options where the existing architecture already does so (§3.3) and
  otherwise defers all real choices to the owner-decision list (§9) and to T2.3's own future
  DoR note.
