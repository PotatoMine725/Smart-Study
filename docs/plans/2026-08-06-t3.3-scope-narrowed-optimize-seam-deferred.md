# T3.3 scope narrowed: Optimize() / G2 pass loop deferred to a new task

**Date:** 2026-08-06 · **Status:** Ratified (owner decision, session resumption, pre-Card-F-dispatch) ·
**Closes:** a scope gap found during Card F's pre-flight check, before any Card F code was written.

**Reads with:** [`2026-08-04-epic-3-execution-plan.md`](2026-08-04-epic-3-execution-plan.md) §3.6 (T3.3
bullets), §3.12 (Card F); [`2026-08-04-g2-optimization-pass-semantics.md`](2026-08-04-g2-optimization-pass-semantics.md)
§5 (consequences for downstream work); [`2026-08-04-m3.0-allocator-baseline-vs-invariant.md`](2026-08-04-m3.0-allocator-baseline-vs-invariant.md).

## What was found

Before dispatching Card F, its pre-flight check (execution plan §3.12: "read the five-bucket
classification; ratify placement strategy in writing at DoR") surfaced a second gap, not covered by
CP-3: the G2 note's §5 assigns the **G2-1/G2-2/G2-4 pass loop** (`Optimize(schedule) → (schedule,
report)`, checkpoints `C₀…C_N` over `N` schedule→schedule stages) to T3.3, and the execution plan's
Mission line for T3.3 ("deadline-aware allocator rework **+ pass loop per the G2 outcome**") repeats
that assignment. But:

- T3.3's own concrete bullets (execution plan §3.6, lines 378-387) and Card F's Scope/Stop criteria
  (§3.12) cover only the allocator's placement strategy, bucket ①/② test work, and naming debt —
  nothing about building `Optimize()`, wiring `IConstraintValidator`/`IObjectiveEvaluator` together, or
  defining a stage list.
- **`N` is undefined in code.** Checked `SmartStudyPlanner/Services/Pipeline/{PipelineContracts.cs,
  PipelineOrchestrator.cs}` and `Services/Pipeline/Stages/*.cs` directly: `IPipelineStage` /
  `PipelineOrchestrator` is a *different* pipeline — `ParseInput → Prioritize → BalanceWorkload →
  AssessRisk → Adapt`, a one-shot **semester → schedule** build (`BalanceWorkloadStage.Execute` calls
  `IWorkloadService.GenerateSchedule` exactly once). No stage anywhere transforms a schedule into an
  improved schedule. G2-2's own scope paragraph already rules out reading the allocator itself as
  "stage 1": `GenerateSchedule(HocKy, double)` maps a semester to a schedule, so there is no input
  schedule for `C₀`, and D-H's relative invariant is not even well-formed there.

Dispatching Card F against the unresolved Mission line risked one of two failure modes: a vacuous pass
loop (`N=0`, `k*=0` on every call, a guard that can never go red — the exact "signal that can't fail"
pattern this project has repeatedly guarded against, see [[feedback_verify_signal_can_fail]]), or an
implementer inventing a stage list unreviewed.

## Decision

**T3.3 ships placement-only**, matching its written Scope/Stop exactly: replace the least-loaded
placement rule (`WorkloadServiceImpl.cs:139-141` at time of writing) with earliest-feasible; keep the
priority sort; rewrite bucket ① with a mutation check; decouple bucket ②; fold in `WorkloadServiceImpl`
→ SOE naming debt; do not touch `ClampCapacityMinutes` (R4).

**The `Optimize()` seam / G2 pass loop is a new task**, not yet numbered (working name **T3.9**),
inserted into the execution order **before T3.4** — T3.4 asserts D-H "on the `Optimize` seam" (G2 note
§5), which presupposes the seam exists. T3.9's DoR must include defining the stage list (even if it
turns out to be a single stage) as a written, owner-reviewed decision — the same weight as CP-1..CP-3,
per the advisor consult that surfaced this gap. Card D (`IConstraintValidator`) and Card E
(`IObjectiveEvaluator`) are unaffected: they were built as independent seams (D-J) and are ready to be
wired into `Optimize()` whenever T3.9 lands.

## Why

- **What for:** Card F stays inside its DoR-reviewed, narrowly-scoped Stop criteria and can be reviewed
  against a suite that already exists (`WorkloadServiceScheduleTests.cs`). T3.9 gets its own DoR instead
  of inheriting an undefined `N` from a Mission-line forward reference written before G2 closed.
- **Experience:** the execution plan's T3.3 Mission line was written 2026-08-04, the same day G2 was
  still open — it names the eventual outcome ("pass loop per G2") without the outcome existing yet to
  specify against. The G2 note's §5 (written the same day, after G2-1..G2-6 were drafted) repeats the
  forward reference without checking it against the codebase's actual pipeline. Neither document is
  wrong on its own terms; the gap only surfaces when both are read against `Services/Pipeline/Stages/`
  directly — which is why this was resolved by reading code, not by reconciling prose.
