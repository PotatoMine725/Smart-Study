> Read-only design pass (no code, tests, or commits produced by the session that authored
> this doc). Grounded in `origin/dev`'s merged T1.4+T2.2 code (`15f3a1c`), the frozen D-I
> decision (`docs/plans/2026-07-02-architecture-freeze-decisions.md`), and
> `docs/architecture/lessons-learned.md` L6/L7/L9. Task: design (not implement) the test
> matrix for **T2.3** — master plan M2.1: "3-way field-level merge; LWW ModifiedAtUtc →
> DeviceId (no HLC)."

## Scope framing

**T2.3 = a pure merge function**, not a write path: `merge(base, local, remote) →
mergedFieldValues + perFieldOutcome[]`, no `DbContext`, no `SaveChanges` call. Evidence for
this reading, not an assumption:

- The T1.4/T2.2 guidelines doc (`docs/plans/2026-09-07-epic2-t1.4-t2.2-implementation-guidelines.md`,
  merged `origin/dev@15f3a1c`) frames M2.1 as "merge engine, no network, **pure**, fixture
  peers" and explicitly names the merge-*apply* write path as an **open
  Definition-of-Ready item**, not something T1.4/T2.2 could pre-empt.
- `SyncBaseSnapshotRow.SnapshotJson` is deliberately opaque today — "T2.3 (not built yet)
  decides that shape."
- Master-plan text for T2.3 is "3-way field-level merge; LWW ModifiedAtUtc → DeviceId" — a
  computation, not a persistence step.

This one call reshapes section F below: it splits into *characterization tests T2.3 must
add now* and *the actual apply path, which is out of scope until the DoR item is ruled on*.

### The DoR item, verified in code (not inherited from memory)

`AppDbContext.SaveChanges(bool)` / `SaveChangesAsync` unconditionally call
`SyncStamper.Apply(ChangeTracker, Clock, DeviceIdProvider())` on every `Added`/`Modified`
entry — this is documented as "the strongest invariant in the system," all 12 write sites
converge on it. If a merge-apply write later goes through this same seam carrying a field
the merge decided the **remote** side won, `SyncStamper` will still overwrite
`ModifiedAtUtc`/`ModifiedByDeviceId` with the **local** clock/device and bump `Rev` —
laundering remote provenance into local. This is real today, not hypothetical, and it's
why T2.3 can only be spec'd as a pure function until the owner rules on it.

## A-0. Diff integrity (prerequisite for everything in A)

| Test | Setup | Expected | Invariant | Breaking mutation | Class |
|---|---|---|---|---|---|
| Snapshot round-trip fidelity | Serialize a fully-populated entity (every merge-surface field, one of each CLR type: `string`, `DateTime`, `DateTime?`, enum, `int`, `bool`, `string?`) into `SnapshotJson`, deserialize it, diff against the untouched live entity | **Zero** fields report as changed | A base snapshot that loses precision on round-trip manufactures false concurrent-edit conflicts that clobber real single-side edits | Drop sub-second `DateTime` precision in the serializer → previously-zero diff count goes non-zero → red | T2.3 required |

## A. 3-way merge

Shared invariants: **A1** unchanged fields survive untouched · **A2** a field changed on
exactly one side always reflects that side post-merge · **A3** a field changed on both
sides is *detected* as a conflict (never silently resolved as "no conflict") · **A4**
fields resolve **independently** — one entity can have some fields resolved by A2 and
others by LWW in the same merge call.

| # | Test | Setup (base / local / remote) | Expected | Invariant | Breaking mutation | Class |
|---|---|---|---|---|---|---|
| A-1 | Unchanged on both sides | `TenTask` identical in base, local, remote | Merged value = base value, reported as `Unchanged`, no conflict | A1 | Assert `ConflictCount == 0`; a resolver that always takes `local` regardless of equality passes this row but fails A-2b | T2.3 required |
| A-2 | Local-only change | `TenTask`: base="X", local="Y", remote="X" | Merged = "Y" (local), reported `LocalOnly` | A2 | A resolver that always prefers remote whenever remote ≠ base → red | T2.3 required |
| A-3 | Remote-only change | `TenTask`: base="X", local="X", remote="Z" | Merged = "Z" (remote), reported `RemoteOnly` | A2 | A resolver that always prefers local → red | T2.3 required |
| A-4 | Same-field concurrent change | `HanChot`: base=D0, local=D1, remote=D2 (D1≠D2, both ≠ D0) | Reported `Conflict`, resolved by LWW (see section B) | A3 | Resolver treats "both differ from base" as "take local" without invoking LWW → red once remote's `ModifiedAtUtc` is later | T2.3 required |
| A-5 | Different-field concurrent changes | Local changes `TenTask` only; remote changes `HanChot` only (different fields, same entity) | Merged entity has local's `TenTask` **and** remote's `HanChot` together — not a whole-row pick | A4 | An implementation that resolves at row granularity ("pick the side with the later `ModifiedAtUtc` for the whole entity") passes A-2/A-3 individually but fails this — the discriminating test for L7 | T2.3 required |
| A-6 | Multiple fields changed on both sides | Local changes `TenTask` + `DoKho`; remote changes `TenTask` (same field, different value) + `HanChot` (different field); base differs from both on all three | `TenTask` → LWW; `DoKho` → local (A2); `HanChot` → remote (A2) — three independent outcomes in one merge call | A4 | Any shared mutable "last winner" state carried across field resolutions within one call (e.g., a resolver that reuses the *previous field's* winning side as a tiebreak shortcut) → red | T2.3 required |

## B. LWW

Shared invariants: **B1** later `ModifiedAtUtc` wins regardless of `DeviceId` · **B2**
equal `ModifiedAtUtc` → `DeviceId` decides via the ratified comparer (E2) · **B3** the
tie-break is order-independent — swapping which side is passed as "local" vs. "remote"
argument doesn't change the *logical* winner · **B4** `Rev` is never read by the tie-break.

> Every row below is **two test cases**: run once as `(A=local, B=remote)` and once as
> `(A=remote, B=local)`, asserting the same side wins both times. A single-direction test
> cannot distinguish "correct LWW" from "always take the second argument."

| # | Test | Setup | Expected | Invariant | Breaking mutation | Class |
|---|---|---|---|---|---|---|
| B-1 | Newer `ModifiedAtUtc` wins | Side A: `ModifiedAtUtc=T1`; Side B: `ModifiedAtUtc=T2`, T2>T1 | B's value wins | B1 | Compare in the wrong direction (`<` instead of `>`) → red | T2.3 required |
| B-2 | Older `ModifiedAtUtc` loses | Same as B-1, inverse assertion on the losing side's value | A's value discarded from the merged output (but preserved for T2.4's conflict record, not T2.3's concern) | B1 | Resolver returns the older value → red | T2.3 required |
| B-3 | Equal `ModifiedAtUtc` → `DeviceId` tie-break | Both sides `ModifiedAtUtc=T` (identical `.Ticks`), `DeviceId` differ | Winner determined per E2's ratified comparer/direction, deterministically | B2 | Swap the comparer direction → red (this is exactly why B2 must be ratified, not inferred) | T2.3 required |
| B-4 | `DeviceId` tie-break is byte/ordinal, not culture-aware | Two device ids that sort differently under `Ordinal` vs. a Vietnamese culture-aware comparer (e.g. ids containing diacritics or case variants) | Winner matches `StringComparer.Ordinal` result | B2 | Use `string.Compare` with current culture → red on a non-`en-US` CI/dev machine, which is exactly the nondeterminism class this guards | T2.3 required |
| B-5 | `Rev` is never consulted | Remote: `Rev` far higher, `ModifiedAtUtc` **older** than local | Local's value wins (positive test for a negative claim — L6) | B4 | Change the resolver to compare `Rev` (or fall back to `Rev` when timestamps are "close") → red | T2.3 required |
| B-6 | Order independence / commutativity | Any conflicting pair, called as `resolve(A,B)` and `resolve(B,A)` | Same logical side wins both ways | B3 | A resolver keyed off argument position ("second argument wins ties") → red under swap | T2.3 required |

## C. Metadata / provenance

| # | Test | Setup | Expected | Invariant | Breaking mutation | Class |
|---|---|---|---|---|---|---|
| C-1 | Winning `ModifiedAtUtc` preserved in merge output | Remote wins a field (later timestamp) | The merge function's per-field result carries remote's exact `ModifiedAtUtc`, not `DateTime.UtcNow` at merge time | C1 | Stamp the merge-time wall clock instead of the winner's timestamp → red | T2.3 required |
| C-2 | Winning `ModifiedByDeviceId` preserved | Same as C-1 | Merge output carries remote's `DeviceId` string exactly | C2 | Stamp the local device id instead → red | T2.3 required |
| C-3 | `Rev` is untouched by merge computation | Any conflict scenario | The pure `merge()` function's output makes no claim about a merged `Rev` value — it operates purely on field values | C3 | An implementation that computes `Rev = max(local.Rev, remote.Rev)` and treats that as meaningful → red once cross-device `Rev` comparison is asserted meaningless (L6) | T2.3 required |
| C-4 | **Characterization: today's write path restamps unconditionally** | Build an entity in `Modified` state whose in-memory `ModifiedAtUtc`/`ModifiedByDeviceId` were hand-set to simulate "already carries a merge-decided remote-origin stamp." Save via `ctx.SaveChangesAsync()` (the real, only write path) | `SyncStamper` **overwrites** both fields to the local `Clock()`/`DeviceIdProvider()` and bumps `Rev` — i.e., assert the *current, wrong-for-merge-apply* behavior explicitly | — (pins the DoR gap as an executable fact, not prose) | If `SyncStamper` is later changed to preserve pre-set provenance without a deliberate seam (E1), this test goes red — which is exactly its job: it must not go green silently | T2.3 required (characterization) |

C-4 is the load-bearing test in this whole matrix: it is what stops a future implementer
from wiring a merge-apply write path straight into the existing seam and silently
laundering remote provenance into local. It should ship with T2.3 even though it exercises
Epic-1 code, specifically so E1 has to be ruled on explicitly rather than discovered in
production.

## D. Tombstones

**Governing reasoning, not just a verdict:** the generic per-field independence rule (A4)
cannot handle delete-vs-edit correctly. If side A tombstones (`IsDeleted`: false→true) and
side B edits `TenTask`, those are **two different fields**, each changed on exactly one
side — A4/A2 would take *both* independently and produce an edited-but-tombstoned row,
which is incoherent. That's precisely why D-I states "tombstone wins" as a **separate,
cross-field override rule** that runs *after* per-field resolution, not something the
generic diff can derive on its own. Implementing and testing that override is T2.4's job
by construction — it needs a rule T2.3's algorithm structurally cannot reach.

| # | Test | Setup | Expected | Class |
|---|---|---|---|---|
| D-1 | Both sides tombstoned, no field conflict | Base: `IsDeleted=false`. Local and remote both set `IsDeleted=true` (with differing `DeletedAtUtc`/`ModifiedAtUtc`/`DeviceId`) | This **is** reachable by the generic algorithm: `IsDeleted` changed on both sides to the *same* value (true) → same-field concurrent change → plain Section B LWW picks the winning side's `DeletedAtUtc`/provenance; result `IsDeleted=true` either way | **T2.3 required** — one row, plain LWW, no cross-field policy engaged |
| D-2 | Delete vs. concurrent edit of a different field | Local tombstones; remote edits `TenTask` (or vice versa) | Tombstone wins overall; edit is preserved only in the conflict record | T2.4 required |
| D-3 | Delete vs. concurrent edit of the *same* field pre-delete | Local tombstones after editing `TenTask`; remote edits `TenTask` differently | Tombstone wins; losing edit preserved in conflict record | T2.4 required |
| D-4 | Conflict record for the delete-vs-edit case | Any D-2/D-3 scenario | A persisted conflict record captures the losing side's field value + provenance (L9: "no irreversible loss" without a full history subsystem) | T2.4 required |
| D-5 | Conflict record for same-field LWW (non-delete) | Any A-4/B-1..B-3 scenario | Losing side's value + provenance persisted as a conflict record | T2.4 required (D-I: conflict records cover LWW *and* delete-vs-edit alike, but persistence is uniformly T2.4) |
| D-6 | Resurrection boundary | One side tombstones, other side later *un-deletes* (edits `IsDeleted` back to false) — does this schema even support that, or is a "new" row the only path back? | Needs an owner ruling — likely out of scope entirely for v1 | Out of scope (flag, don't spec) |

## E. Idempotency / determinism

| # | Test | Setup | Expected | Invariant | Breaking mutation | Class |
|---|---|---|---|---|---|---|
| E-1 | Pure-function determinism | Call `merge(base, local, remote)` twice with byte-identical inputs | Byte-identical output both times, no shared/mutated state between calls | Referential transparency | A resolver that memoizes or mutates a static "last winner" cache → red on interleaved calls with different inputs | T2.3 required |
| E-2 | No dependency on field enumeration order | Call merge with the merge-surface field list shuffled/reordered (if the implementation iterates a collection) | Same merged result regardless of iteration order | Determinism independent of collection ordering | An implementation with an early-exit "first conflicting field found" shortcut that changes behavior under reordering → red | T2.3 required |
| E-3 | Replaying the identical remote state twice (DB-applied) | Requires the apply-write path (E1) to exist | Second application is a no-op — same DB row, same `Rev` | Convergence / no-data-loss under redelivery | — | **T2.5** (needs the apply path T2.3 doesn't own) |
| E-4 | Merge order-independence across repository/UI call order | Merge invoked from two different call sites with the same three inputs | Same result regardless of caller | Determinism independent of caller | — | T2.3 required (folds into E-1 in practice; list separately only if the real API exposes multiple entry points) |

## T2.5 property-level candidates (named, not specified — starts after T2.3/T2.4 land)

- Convergence: two devices apply arbitrary interleavings of concurrent field edits; after a
  full bidirectional sync both converge to the identical final state (master-plan
  explicitly starts this at T2.5).
- No-data-loss: every losing value across a randomized fuzz run is recoverable from a
  conflict record.
- Generative field-mutation fuzzing across all six entities' merge surfaces (would have
  caught A-5/A-6-class bugs by construction rather than by hand-picked fixture).

## Out of scope entirely for this gate

T2.1 (transport/discovery/trigger), T2.6/G4 (retention/purge), HLC (explicitly rejected by
D-I), any UI/sync-trigger surface, `SyncStamper.cs` changes outside whatever E1 ultimately
authorizes.

## Recommended acceptance gate

**Entry** (must be ruled before implementation, not discovered during it):
1. E1 — restamp-seam mechanism for merge-apply writes (options enumerated above; owner
   picks or defers the apply path entirely out of this slice, mirroring how T1.4/T2.2
   fenced off T2.3).
2. E2 — `DeviceId` tie-break comparer + winning direction, ratified.
3. E3 — `ModifiedAtUtc` equality/`Kind`-normalization rule, ratified.
4. E4 — `CreatedAtUtc` (StudyLog, TaskReferenceLink) merge-surface status, ratified.
5. E5 — the per-entity merge-surface table above, ratified as the frozen surface (L7
   discipline).

**Exit:**
1. Every "T2.3 required" / "T2.3 required (characterization)" row above exists, passes,
   and was **observed red** via its named mutation before being fixed — red/green evidence
   reported per the T1.4/T2.2 §6.4 precedent (mutate, confirm red, revert, confirm green).
2. Full suite ≥ the `504 total / 503 passed / 0 failed / 1 skipped` baseline at
   `origin/dev@15f3a1c`, zero regressions.
3. Positive confirmation (not "didn't need to"): `SyncStamper.cs` unchanged unless E1's
   ruling explicitly authorized a specific, scoped change; no conflict-record persistence
   added; no delete-vs-edit policy code added; no transport/DI wiring added.
4. A-5/A-6 (per-field independence) and C-4 (restamp characterization) are non-negotiable —
   these are the two tests that would have caught L7's and this session's central finding
   respectively; a T2.3 PR without them should not pass review regardless of what else it
   covers.
