## 1. What was built

`WorkloadServiceImpl` gained an `internal` method,
`GenerateScheduleWithIdentity(HocKy, double) : (List<ScheduleDay> Days, List<ScheduledItem> Items)`,
that runs the **exact same allocation algorithm** as before (priority sort, least-loaded placement,
overflow-day opening, `ClampCapacityMinutes` — none of it touched) but builds a new
`SmartStudyPlanner.Services.Soe.ScheduledItem` per scheduled chunk *before* deriving the
`ScheduledTask` that goes into the returned `ScheduleDay`. Each `ScheduledItem` carries:

- `MaTask` (`Guid`) and `HanChot` (`DateTime`) — copied from the source `StudyTask`, unchanged by
  fragmentation: every "(Phần n)" part of a cut-up task shares the same `MaTask`/`HanChot`.
- `TenTaskGoc` — the base task name, pre-suffix.
- `TenHienThi` — the display name after the existing fragmentation-suffix rule
  (`WorkloadServiceImpl.cs`, unchanged expression: `minutesNeeded > spaceLeft || part > 1`).
- `TenMon`, `Date`, `SoPhut` — same values the current `ScheduledTask`/`ScheduleDay` already compute.

`GenerateSchedule` (the `IWorkloadService` member, signature unchanged) now delegates:
`GenerateSchedule(hocKy, capacityHours) => GenerateScheduleWithIdentity(hocKy, capacityHours).Days`.

**Placement:** `SmartStudyPlanner/Services/Soe/ScheduledItem.cs`, namespace
`SmartStudyPlanner.Services.Soe`. This mirrors the test namespace
`SmartStudyPlanner.Tests.Services.Soe`, which already exists from Card A
(`SoeCorpusGenerator.cs`, `SoeBaselineMetrics.cs`, `SoeBaselineCaptureTests.cs`) — the repo's mirror
namespace convention put the SOE test fixtures there first, so the production SOE namespace is
already implied. Cards D (`IConstraintValidator`) and E (`IObjectiveEvaluator`) are named in the
execution plan as landing in "a new SOE namespace" — putting the identity type there now means they
consume `ScheduledItem` from a namespace that already exists, instead of D or E having to invent it
under time pressure. `Models/ScheduleModels.cs` was **not** extended: `ScheduledItem` is an
allocator-internal seam type, not a UI/display type, and the UI-facing `ScheduledTask`/`ScheduleDay`
in `Models` are explicitly meant to stay display-only (per their own doc comment).

**Why `(List<ScheduleDay> Days, List<ScheduledItem> Items)` — two parallel lists, not
`ScheduleDay` owning its `ScheduledItem`s:** the obvious alternative to a tuple of two lists correlated
by `Date` is to give each `ScheduleDay` a `List<ScheduledItem>` alongside (or instead of) its
`List<ScheduledTask>`. That was rejected on a dependency-direction ground, not a convenience one:
`ScheduleDay` lives in `SmartStudyPlanner.Models`, is bound directly by `WorkloadBalancerPage.xaml`,
and its own doc comment says it exists only for display ("chỉ dùng để hiển thị, không lưu DB").
`ScheduledItem` lives in `SmartStudyPlanner.Services.Soe` — a services-layer, allocator-internal type.
Giving `ScheduleDay` a property of type `Services.Soe.ScheduledItem` would make `Models` depend on
`Services`, inverting the direction every other type in `Models/` currently respects (nothing in
`Models/` references `Services/` today). A parallel list returned from a `Services`-layer method keeps
the dependency pointing one way: `Services.Soe` knows about `Models.ScheduleDay` (fine, it already
does — it builds them), but `Models.ScheduleDay` still knows nothing about `Services.Soe`. The `Date`
field is what makes the correlation sound without an object reference between the two: it's a real,
tested join key (`GenerateSchedule_CacNgayLuonLienTiep_KeCaNgayMoMoThem` pins that day dates are
contiguous and duplicate-free), not a convention invented for this tuple. This is a T3.8 design
decision on its own, independent of the `DiemUuTien` question below — flagged here so CP-2 ratifies the
whole seam shape, not just the write-through.

**Why lockstep build-then-project, not two independent passes:** the spec text describes "build the
internal representation, then project it into `List<ScheduleDay>`" as if it were two full passes over
a completed schedule. It is implemented as build-then-project *per chunk* instead: each
`ScheduledItem` is constructed first, and the `ScheduledTask` appended to `targetDay.Tasks` is a
direct field-for-field projection of that same item, at the same point in the loop. A genuinely
two-pass design (compute all `ScheduledItem`s first, then reconstruct `ScheduleDay` buckets from them
afterward) was considered and rejected: the day-opening logic is **stateful and greedy** — which day a
chunk lands on depends on the cumulative `TotalMinutes` already placed on every prior day, evaluated in
placement order. Reconstructing `ScheduleDay` buckets from a flat item list after the fact would mean
re-deriving that same greedy state from `Date` values alone — solvable, but it duplicates the
allocation logic's contract without changing what either pass computes, for no benefit at T3.8 (no
consumer needs the two passes to be physically separate yet). Per-chunk lockstep gets identity
threading with zero risk of the projection drifting from the allocation decision, since there is no
second algorithm that could disagree with the first.

**Behavior preservation:** `WorkloadServiceScheduleTests.cs` — all 21 existing test cases (14 `[Fact]`
methods + 2 `[Theory]` methods across 7 `[InlineData]` cases; confirmed via
`dotnet test --filter FullyQualifiedName~WorkloadServiceScheduleTests`), byte-identical assertions —
pass unchanged. Both call sites
(`WorkloadBalancerViewModel.cs:37`, `BalanceWorkloadStage.cs:41`) and `WorkloadBalancerPage.xaml` show
zero diff (`git diff` empty for all three, plus `PipelineContracts.cs`). Five tests were added in
`SmartStudyPlanner.Tests/Services/Soe/WorkloadServiceIdentityTests.cs`, characterizing: identity fields
match the source task; fragmented parts of one task share one `MaTask`/`HanChot`; completed tasks
produce no `ScheduledItem` (parity with the existing "completed tasks never scheduled" invariant); the
public `GenerateSchedule` projection matches `GenerateScheduleWithIdentity`'s items in the single-task
case; and — the one that matters most for Cards D/E — an explicit multi-task counterexample
(8 tasks × 40 min at a 120 min/day capacity) proving that `Items` order and the day-major-flattened
`ScheduledTask` order **diverge** once `OrderBy(d => d.TotalMinutes)`'s stable-sort tie-break sends a
later chunk back to an earlier, already-used day. The correct correlation — grouping `Items` by `Date`
and comparing per-day insertion order — is asserted right after proving the divergence is real, so the
test both documents the hazard and pins the fix. An earlier draft of this test suite asserted
index-based 1:1 correlation across the whole schedule as if it were a general contract; it only held
for the single-task fixture it was written against and has been corrected before this card closed.

## 2. The `DiemUuTien` write-through — recommendation, not executed

**The question (M3.0 doc §④, execution plan CP-2):** `GenerateSchedule` currently writes
`task.DiemUuTien = _decisionEngine.CalculatePriority(task, mon)` directly into the caller's
`StudyTask` model, for every non-completed task, as a side effect of scheduling
(`WorkloadServiceImpl.cs:49` in the pre-T3.8 numbering). `GenerateSchedule_GhiDeDiemUuTien_ChiTrenTaskChuaHoanThanh`
pins this. Does a schedule-generation seam that's meant to become part of a pure
`Optimize(schedule) → (schedule, report)` boundary (G2, architecture freeze) keep this side effect, or
does priority stamping move to whatever ends up owning it?

### What keeping it costs

`GenerateScheduleWithIdentity` is not pure: calling it twice on the same `HocKy` with a
`IDecisionEngine` whose output depends on external state (clock, ML predictor) can produce different
`DiemUuTien` values stamped into the *same* `StudyTask` objects as a side effect unrelated to what the
caller asked for (a schedule). T3.3's planned pass loop (G2) and any future re-run/what-if scheduling
(re-generating a schedule without committing it, e.g. to preview a capacity change) inherit this
impurity for free — every call mutates shared task state, whether or not the caller wants that.
Architecturally, this is exactly the kind of side effect the `Optimize(schedule) → (schedule, report)`
seam is supposed to exclude by construction.

### What dropping it costs — checked, not assumed

Searched all `DiemUuTien` read sites (`Grep` across `SmartStudyPlanner/`) for anything that depends on
`GenerateSchedule` having just stamped it:

- **`PrioritizeStage.cs:49`** (pipeline `PipelineStageType.Prioritize = 1`) stamps `DiemUuTien` via the
  same `_decisionEngine.CalculatePriority(task, mon)` call, and runs **before**
  `BalanceWorkloadStage` (`PipelineStageType.BalanceWorkload = 2`) in stage order
  (`PipelineContracts.cs:9-15`). In the pipeline path, `GenerateSchedule`'s write is a **redundant
  re-stamp of a value already set this run** — not the source of truth.
- **`QuanLyTaskViewModel.cs:105-113`** (`TinhDiemVaSapXep`) stamps `DiemUuTien` independently, on its
  own trigger (task-management page), unrelated to `GenerateSchedule` ever having run.
- **`WorkloadBalancerPage.xaml`** — confirmed via its own binding paths (execution plan pre-read) —
  binds only `ScheduleDay.{DisplayName, TotalMinutes, HeaderText, Tasks}` and
  `ScheduledTask.{TenTask, TenMon, SoPhut, ThoiGianHienThi}`. **`DiemUuTien` is not bound anywhere in
  the Workload Balancer UI.**
- `DashboardConverters.cs`, `TaskDashboardItem.cs`, `DashboardPage.xaml`, `QuanLyTaskPage.xaml` all read
  `DiemUuTien` for task-list display, but those views are populated by `PrioritizeStage` /
  `TinhDiemVaSapXep`, not by a prior call to `GenerateSchedule` — nothing in those paths calls
  `GenerateSchedule` first and relies on its write.

**No downstream reader depends specifically on `GenerateSchedule`'s write.** Every path that reads
`DiemUuTien` either stamps it itself first (pipeline, task-management page) or doesn't read it at all
(Workload Balancer UI). The write-through is, today, a no-op from every current caller's point of
view except the direct `WorkloadBalancerViewModel` path — and even there, nothing downstream of
`BuildSchedule` reads `DiemUuTien` off the affected tasks in that same session before some other stamp
(pipeline run, task-page visit) would overwrite it anyway.

### Recommendation — ratified 2026-08-05

**Drop the write-through when T3.3 reworks the allocator into the pass-loop seam** (not in this card —
T3.8's job is identity, not T3.3's rework). Concretely: `GenerateSchedule_GhiDeDiemUuTien_ChiTrenTaskChuaHoanThanh`
should be **deleted** at that point, not "fixed" by re-adding the write-through — per the M3.0 doc's own
explicit warning about this exact failure mode. Priority stamping should be understood as
`PrioritizeStage`'s / `TinhDiemVaSapXep`'s job, both of which already do it independently and do not
need `GenerateSchedule` to also do it. The cost of dropping is near-zero (checked above, not assumed);
the cost of keeping is a standing purity violation in a seam the architecture freeze specifically wants
pure.

**This recommendation is not executed by this card.** `GenerateSchedule_GhiDeDiemUuTien_ChiTrenTaskChuaHoanThanh`
remains green and unmodified — the write-through line (`task.DiemUuTien = _decisionEngine.CalculatePriority(task, mon)`
inside `GenerateScheduleWithIdentity`) is untouched. Owner ratification at CP-2 is what authorizes T3.3
to act on it.

## 3. Decisions made (ADR-style)

- **Why:** `IConstraintValidator` (T3.1) and `IObjectiveEvaluator` (T3.2) cannot be built against
  `List<ScheduleDay>` — it carries no task identity and no deadline, so neither seam can ask "is this
  chunk's task past its deadline?" or "which task did this chunk come from?". T3.8 exists to make that
  question answerable without changing what either existing call site or the WPF binding surface sees.
- **What for:** Card D and Card E get a concrete, already-tested type (`ScheduledItem`) and an
  already-wired internal seam (`GenerateScheduleWithIdentity`) to build against, in the namespace the
  execution plan already pointed them at. The `DiemUuTien` write-through question — otherwise likely to
  resurface as a reflexive "make the red test green" fix mid-T3.3 — is answered in writing now, with
  the downstream-reader check that the M3.0 doc flagged as unverified.
- **Experience:** the two-pass-vs-lockstep design question cost more thinking than the identity type
  itself — the type is three lines different from `ScheduledTask`; the placement-loop's statefulness is
  what made "just reconstruct it after" the wrong default. Checking actual `DiemUuTien` read sites
  (`Grep`, four call sites, one XAML confirmed unbound) turned "probably safe to drop" into a checked
  claim instead of a guess, which is what the task card asked for explicitly. A code-quality review
  round caught two things worth naming: first, `ScheduledItem` was originally a `sealed class` with
  `{ get; init; }` properties instead of the `record` the repo already uses for this exact shape
  (`HeatCell`, `TableSnapshot`, `StatusSegment` et al.) — fixed, since Card D/E's tests will plausibly
  reach for value equality (`Assert.Equal`, `Distinct`, `GroupBy`) that a plain class silently fails.
  Second, and more consequentially: the first version of `WorkloadServiceIdentityTests.cs` asserted
  index-based correlation between `Items` and the day-major-flattened `ScheduledTask` list as if it
  were the general contract, and it only happened to hold because the fixture used a single task. A
  multi-task fixture (8 tasks, tied `TotalMinutes`, stable-sort tie-break) proved that assumption false
  — the real, tested join key is `Date`. Both fixes landed before this card's commit; a single-fixture
  test that "passes" is not evidence a stated contract is general, which is the same lesson this repo's
  test-signal conventions already insist on elsewhere.
