## What was found

Card F's code-quality review (dispatched fresh, verified against `git diff --name-status f7655d1..60fae4d`)
found that the execution plan lists "fold in `WorkloadServiceImpl` → Balancer/SOE naming debt" as in-scope
for T3.3 (§1.5 line 114, restated §3.6 line 386, and restated a third time in this card's own
scope-narrowing doc, `2026-08-06-t3.3-scope-narrowed-optimize-seam-deferred.md`), but the shipped diff
contains zero renames — `WorkloadServiceImpl`, `IWorkloadService`, and `GenerateSchedule` are all
unchanged. Unlike this card's two other deviations from a naive reading of its scope (the `Optimize()`
seam deferral and the CP-2 write-through reversal), this one had no ratified decision doc — it was simply
absent, which the reviewer correctly identified as exactly the failure mode this project's decision-doc
discipline exists to catch.

## Why it was actually descoped (reasoning existed, was never written down)

The reasoning was stated in Card F's implementer dispatch prompt at the time (2026-08-06, before any code
was written), but never promoted to a ratified doc — that omission is what this note corrects:

> "'WorkloadServiceImpl → Balancer/SOE naming debt' is named in the plan as debt to 'fold into' this card,
> but is genuinely underspecified (no concrete rename is written down anywhere) and a real rename of the
> public class `WorkloadServiceImpl`, interface `IWorkloadService`, or method `GenerateSchedule` would
> touch DI registration and call sites *outside* this card's two-file scope — which the plan's own risk R6
> (about T3.8) warns against by the same logic. Do not rename any public type, interface, or public
> method."

Concretely: the execution plan names a *target vocabulary* ("Balancer/SOE") but never names a target
type/namespace, a rename map, or which of `WorkloadServiceImpl`/`IWorkloadService`/`GenerateSchedule` (if
any) actually needs to move. A rename executed without that specification would be an implementer's
guess, not an implementation of a decision — and `WorkloadServiceImpl` is referenced from DI registration
(`ServiceLocator`), `WorkloadBalancerViewModel`, `BalanceWorkloadStage`, and the four touched/untouched
test files verified in this review round, none of which are in Card F's stated two-file scope. R6 (T3.8's
"scope-creeps into a UI rework" risk) already establishes the precedent for refusing this kind of
blast-radius expansion inside a narrowly-scoped card.

## Decision

**Descoped from T3.3/Card F entirely.** If this naming debt is still wanted, it needs its own task: a
concrete rename target (type names, target namespace) specified in writing, and its own DoR covering the
call-site/DI blast radius — the same weight as any other architecture-touching decision this session has
required (CP-1..CP-3, the two other T3.3-adjacent decision docs). Not picked up implicitly inside a future
card; named explicitly if and when the owner wants it scheduled.

## Why

- **What for:** Card F's diff now matches what's actually decided, not a partially-executed reading of a
  plan line written before the blast-radius question had been asked. Future readers of the execution plan
  get a pointer to this note instead of silently wondering why the rename never happened.
- **Experience:** the gap wasn't a missed requirement so much as a decision made informally (in a dispatch
  prompt, which a controller writes but doesn't ratify the way a dated docs/plans note does) and never
  surfaced for the record. The fix isn't "do the rename now" — the reasoning against doing it inside this
  card still holds — the fix is writing down the decision that was already, correctly, made.
