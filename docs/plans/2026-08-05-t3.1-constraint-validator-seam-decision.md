## 1. What was built

Three new files in `SmartStudyPlanner/Services/Soe/` (flat namespace `SmartStudyPlanner.Services.Soe`,
mirroring `SmartStudyPlanner.Tests.Services.Soe` — see §5 for why this stayed flat rather than a
`.Constraints` sub-namespace):

- **`IConstraintValidator.cs`** — the hard-filter contract, `ConstraintValidationResult`, and
  `DeadlineViolation` (the per-chunk explainability detail). `IConstraintValidator.Validate` takes only
  `IReadOnlyList<ScheduledItem>` — no weight, no score, nothing from T3.2's territory (D-J). The
  signature itself is category-neutral (no "deadline" anywhere in it), so a future capacity or calendar
  predicate can be added as another concrete `IConstraintValidator` without touching this interface.
- **`IDeadlinePolicy.cs`** — the extension point, plus `UniformDeadlinePolicy`, its **one** production
  implementation. `IDeadlinePolicy.IsViolation(ScheduledItem item)` takes the whole `ScheduledItem`, not
  two bare `DateTime`s (see §3 for why that signature choice specifically matters).
- **`ConstraintValidator.cs`** — the sole `IConstraintValidator` implementation, delegating the
  per-chunk predicate to an injected `IDeadlinePolicy` (default `UniformDeadlinePolicy`).

Tests: `SmartStudyPlanner.Tests/Services/Soe/ConstraintValidatorTests.cs`, 11 `[Fact]` methods, built
directly against hand-built `ScheduledItem` fixtures (no allocator call — T3.1's scope is the validator
itself, not wiring; that is T3.3's job).

```csharp
public interface IConstraintValidator
{
    ConstraintValidationResult Validate(IReadOnlyList<ScheduledItem> items);
}

public interface IDeadlinePolicy
{
    bool IsViolation(ScheduledItem item);
}

public sealed record ConstraintValidationResult(
    bool IsFeasible,
    int ViolatingTaskCount,
    int TotalOverdueMinutes,
    IReadOnlyList<DeadlineViolation> Violations);

public sealed record DeadlineViolation(
    Guid MaTask, string TenTaskGoc, DateTime Date, DateTime HanChot, int SoPhut);
```

## 2. Granularity decision — date-only, not time-of-day

**Decision:** the predicate is `item.Date.Date > item.HanChot.Date` — a chunk is a violation only if
it lands on a calendar **day** after the deadline's day. The deadline's time-of-day component is
ignored entirely. Concretely, for the bucket ③ scenario (M3.0 doc, `2026-08-04-m3.0-allocator-baseline-vs-invariant.md:105-110`):
a 09:00 deadline on day 5, this predicate reads day 5 as **usable** — the "360 minutes available"
reading, not "300."

**Why date-only, not a preference but a constraint from the seam being consumed:**

1. **`ScheduledItem.Date` carries no time-of-day at all** — its own doc comment states it is "already
   `.Date`." The allocator's scheduling model operates at whole-day granularity; there is no
   representation of *when within a day* a chunk happens. A time-of-day predicate would have to invent
   an assumption the source seam does not model — e.g., "a chunk is deemed to occur at day's end" or
   "a morning deadline forfeits the whole day" — and bake that fabrication into the validator. That is
   inventing data, not making a design decision, and it directly contradicts this card's explicit
   instruction not to invent scope the codebase doesn't support.
2. **It matches the one directly relevant precedent already in the codebase**: `DeadlineUrgencyRiskEvaluator`
   (Risk Analyzer) computes `task.HanChot.Date - clock.Now.Date` — pure date subtraction, time-of-day
   discarded. Adopting the same arithmetic style keeps this validator's predicate consistent with the
   nearest existing "is this overdue" computation in the system (see §3 for the full DF-1 alignment,
   which is a related but distinct question from granularity).
3. **This choice does not flip the one pinned infeasible fixture.** Bucket ③ is documented as
   "infeasible either way" (`m3.0-allocator-baseline-vs-invariant.md:108-110`): 600 minutes needed
   against both the 360-minute and 300-minute readings. So the granularity call has zero effect on that
   fixture's feasibility label — its consequence is on *other*, non-pinned boundary cases (day-5-exactly
   placements), which is exactly the case this card's boundary test (`Validate_HanChot09hNgay5_ChunkDatDungNgay5_KhongLaViPham`)
   exercises directly. This is noted so the decision cannot later be mistaken for "picked to make a test
   pass" — it was not.

## 3. Overdue-definition alignment (DF-1)

Two definitions of "overdue" coexist in the codebase (execution plan §5.1):

- `IUrgencyRule` (`Services/Strategies/IUrgencyRule.cs`, Decision Engine) — a **3-day cliff**:
  `daysLeft < 0 → 100` (`JustOverdueRule`), but `daysLeft < -3 → 0` (`OverdueRule`, checked first in the
  composed chain per `SchedulingOrchestrator.cs`). Past 3 days late, the priority *score* collapses to 0
  — the task effectively drops out of the ranking, as a scheduling-order heuristic.
- `DeadlineUrgencyRiskEvaluator` (`Core/Risk/Evaluators/DeadlineUrgencyRiskEvaluator.cs`, Risk Analyzer)
  — **no cliff**: `daysLeft < 0 → 1.0`, forever, regardless of how many days have passed.

Both ask the same underlying question — **"is *today* past the deadline?"** — using the same date-only
arithmetic (`HanChot.Date` minus a reference date), and differ only in what they do *after* that boundary
(decay to 0 vs. flat 1.0). This validator's predicate asks a related but different question: not "is
today past the deadline" but **"is *this placement* (`ScheduledItem.Date`, a specific scheduled day)
dated after the deadline."** Same date-only arithmetic, different reference point — the reference is the
chunk's scheduled date, not "now."

**Disposition:** the predicate's semantics align with `DeadlineUrgencyRiskEvaluator`'s **no-cliff**
reading, and explicitly reject `IUrgencyRule`'s 3-day-cliff reading. This is not a stylistic preference —
the cliff reading is **structurally incompatible** with what this validator must supply. D-H's second
comparison key (total overdue minutes) requires a magnitude that is **monotone in lateness**: a task 10
days late must register as worse than one 1 day late. A cliff definition that collapses "violation" to
zero past some threshold (as `OverdueRule` does to the priority *score*) would make a 10-day-late chunk
and a 30-day-late chunk indistinguishable past the cliff — directly breaking the invariant this seam
exists to support. The no-cliff reading has no such collapse: `TotalOverdueMinutes` keeps growing with
each additional late day, which is what D-H needs. Reconciling `IUrgencyRule` and
`DeadlineUrgencyRiskEvaluator` with each other is explicitly **out of scope** for T3.1 (Decision Engine /
Risk Analyzer work, owner: DP-1) — this validator adopts neither by copying it wholesale, but the
no-cliff *shape* is the one it is structurally compatible with, and that alignment is stated here per the
task card's disposition requirement.

## 4. Per-chunk vs. per-task — `ViolatingTaskCount` vs. `Violations.Count`

A task fragmented into multiple `(Phần n)` chunks can have more than one chunk placed after its deadline.
`ConstraintValidationResult` deliberately reports **two different counts** that are not required to
match:

- **`ViolatingTaskCount`** — counts **distinct `MaTask`** values with at least one violating chunk. This
  feeds D-H's first comparison key (hard-constraint violation count).
- **`Violations`** (and its `.Count`) — one entry **per violating chunk**. This is the per-chunk detail
  needed for explainability and is the basis for `TotalOverdueMinutes`.

**Why count violations per task, not per chunk:** how many chunks a given task is split into is an
allocator implementation detail (T3.3's chunking, driven by daily capacity), not a fact about
feasibility. If `ViolatingTaskCount` counted chunks instead of tasks, two schedules exhibiting the exact
same underlying problem (one task genuinely overdue) could report different violation counts purely
because one allocator run split that task into more pieces than another — the count would then measure
chunking granularity, not constraint violation. Counting distinct tasks keeps `ViolatingTaskCount`
invariant under re-chunking, which is what D-H's "violation count" is supposed to mean: a statement about
the schedule's feasibility, not its fragmentation shape. The chunk-level reading was considered and
rejected for this reason.

**Why `TotalOverdueMinutes` sums per chunk, not per task:** this is a magnitude, not a count — "how many
minutes were spent on work placed after its deadline" is naturally the sum of every late chunk's minutes,
with no principled reason to count only a task's single latest (or single largest) chunk once fragmented.

This asymmetry is pinned directly by
`Validate_TaskBiCatNhoNhieuChunkTreHan_ViolatingTaskCountDemMotTask_ViolationsDemMoiChunk`
(`ConstraintValidatorTests.cs`) — one `MaTask`, two late chunks (40 min + 50 min), asserting
`ViolatingTaskCount == 1`, `Violations.Count == 2`, `TotalOverdueMinutes == 90`. Anyone consuming this
result later (T3.4) should read that test before assuming the two counts must agree.

## 5. Namespace — flat `SmartStudyPlanner.Services.Soe`, not a sub-namespace

Card C already established `SmartStudyPlanner.Services.Soe` / `SmartStudyPlanner.Tests.Services.Soe` as
the mirror pair for Epic 3 SOE work (`ScheduledItem.cs`), explicitly naming Cards D and E as continuing
in that same namespace. This card stayed flat rather than introducing `SmartStudyPlanner.Services.Soe.Constraints`:
Card E (T3.2, `IObjectiveEvaluator`) is being built in parallel, in the same flat namespace, without
visibility into whichever choice this card made — a sub-namespace on one side and not the other would
leave the SOE namespace asymmetric between the two seams for no structural reason (there is exactly one
constraint-validator family and one objective-evaluator family; a sub-namespace buys nothing when there
is only one thing to group). Flat keeps both cards' output uniform and matches what Card C already
pointed at.

## 6. What was deliberately not built

- **No second `IDeadlinePolicy` implementation.** Per-type (`LoaiCongViec`) grace/urgency-decay is
  explicitly deferred out of Epic 3 (execution plan §2.1/§2.4, DP-1) — D-G's removal of `w6` forecloses
  it from the SOE's objective side, and the plan is explicit that Epic 3 ships exactly one uniform
  implementation. The signature choice in §7 below is what keeps a second implementation possible later
  without touching this card's code.
- **No capacity or calendar predicate.** The plan's "deadline / capacity / calendar predicates as a hard
  filter" line (D-J) names three predicate *categories* the validator's interface should be able to host
  — it does not instruct building all three now, and T3.1's named deliverables (§3.6) are specifically
  the deadline predicate, the policy extension point, and the violation-magnitude shape. Nothing else in
  the codebase currently defines a capacity or calendar constraint to validate against, so building
  either now would be inventing logic with no source of truth. `IConstraintValidator`'s signature is
  already category-neutral, so adding either later is additive, not a redesign.
- **No wiring into `WorkloadServiceImpl` or the allocator.** That is T3.3 (a future card, Card F).
  `WorkloadServiceImpl.cs`, `ScheduledItem.cs`, `Models/ScheduleModels.cs`, and both `GenerateSchedule`
  call sites are untouched by this card (confirmed via `git status` — only the three new production
  files and one new test file under `Services/Soe`/`Tests/Services/Soe` are new; nothing else in the
  tree was touched by Card D).

## 7. Why `IDeadlinePolicy.IsViolation` takes a whole `ScheduledItem`, not two `DateTime`s

The extension point exists specifically so a **second** implementation (the deferred per-type grace
policy) can land later "touching no SOE internals" (§2.2 of the execution plan). A per-type policy needs
to know the source task's `LoaiCongViec` to decide differently per type — but `LoaiCongViec` is not a
field on `ScheduledItem` today. A signature of `IsViolation(DateTime placementDate, DateTime hanChot)`
would force that future implementation to *change this interface's signature* to add the missing input —
exactly the rewrite the extension point was created to prevent. Taking the whole `ScheduledItem` instead
keeps the signature stable: a future implementation reads whatever additional field it needs once that
field exists (on `ScheduledItem` or a successor carrier type), without `IDeadlinePolicy` itself having to
change. This was corrected during design review before any test was written against the two-`DateTime`
shape, so no test needed to change as a result.

## 8. Decisions made (ADR-style)

- **Why:** T3.1 cannot be built without answering the granularity question and the DF-1 alignment
  question — the execution plan states both as non-optional, non-deferrable deliverables (§2.2, §5.1).
  Leaving either unstated would let a future card (T3.3, T3.4) invent an answer under time pressure
  instead of building against a documented one.
- **What for:** Card D delivers a validator whose feasibility answer is reproducible and explainable —
  date-only granularity documented against the one scenario (bucket ③) that made the ambiguity concrete,
  and a stated (not silently invented) overdue-definition alignment that names which existing definition
  it is compatible with and, just as importantly, which one it structurally cannot be compatible with and
  why. T3.4's D-H invariant suite gets a `ConstraintValidationResult` shape it can build both comparison
  keys from without re-deriving them.
- **Experience:** the first design pass had `IDeadlinePolicy` taking two bare `DateTime`s and a single
  `ViolationCount` field meant to double as both the per-task and per-chunk count. Both were wrong for
  the same underlying reason — designing the shape without first checking it against the *specific*
  future extension it exists to support (a per-type policy needing task-type information; T3.4 needing a
  fragmentation-invariant count). Checking the shape against the concrete second-implementation and
  concrete second-consumer scenarios *before* writing tests against it is what caught both; a passing
  test suite against the wrong shape would not have caught either, since eleven tests can all pass
  against a signature that still forecloses the extension it was built for.
