## Finding / fix

### M1.2-R1 — `SqliteStudyTaskRepository.DeleteAsync` skipped the G1 cascade (fixed)

**Problem.** `DeleteAsync` loaded only the `StudyTask` and called `db.StudyTasks.Remove(existing)`.
Pre-M1.2 this was a hard delete and the DB's `ON DELETE CASCADE` removed the task's `TaskNote`/
`TaskReferenceLink` for free. Post-M1.2, `SyncStamper` converts `Remove()` to a tombstoning
`UPDATE` instead of a real `DELETE`, so the DB-level cascade no longer fires — the task would be
tombstoned but its Note/Links left live, pointing at a dead parent. Exactly the G1 invariant this
milestone exists to establish, violated by a public repository method.

Reviewer noted this was **latent, not active**: `gitnexus_impact` confirmed `DeleteAsync` has
zero production callers (the UI deletes tasks through `LuuHocKyAsync`'s delete-by-absence path,
which already cascades correctly) and only one caller overall — its own childless round-trip test,
which never exercised the orphan because it never gave the task a Note or Link. Re-ran the same
`gitnexus_impact` check independently before touching anything — confirmed: risk **LOW**, 1 direct
caller, that same test.

**Fix.** Reproduced first, per TDD: added
`StudyTaskRepository_DeleteAsync_CascadesToNoteAndLinks` (seed a task with a `TaskNote` + a
`TaskReferenceLink`, call `DeleteAsync`, assert task/note/link all read back `IsDeleted == true`)
and confirmed it failed for the expected reason (`note.IsDeleted` false — the note was left live).

Extracted the cascade logic the review flagged as duplicated-in-waiting into a shared
`internal static class TaskCascadeHelper` (`Infrastructure/Persistence/SQLite/TaskCascadeHelper.cs`,
one method: `RemoveChildrenAsync(AppDbContext, Guid maTask, CancellationToken)`) and pointed both
call sites at it:
- `SqliteHocKyRepository.LuuHocKyAsync` — replaced its private `CascadeRemoveTaskChildrenAsync`
  (deleted, now dead code) with calls to the shared helper, same two call sites (MonHoc-removed
  branch, Task-removed branch).
- `SqliteStudyTaskRepository.DeleteAsync` — calls the shared helper before `db.StudyTasks.Remove`,
  in the same `SaveChanges` batch, so the seam tombstones Note/Links alongside the task.

This follows the review's stated preference (shared helper over duplicating the logic a second
time) so the two delete paths can't drift apart again.

## Decisions made

### D1 — Fix `DeleteAsync` in place rather than removing it from the interface

**Why it had to be made.** The review offered two valid paths: cascade-fix `DeleteAsync` (it's a
public repository API, so a silent orphan-producer is a real risk even with zero current callers),
or delete the method from `IStudyTaskRepository`/`SqliteStudyTaskRepository` outright if it's
genuinely unwanted. Leaving it as-is (uncascaded) was not an option — that's the finding itself.

**What it's for.** `Add`/`Update`/`Get`/`Delete` is the conventional CRUD shape every other
repository in this codebase exposes; removing `Delete` would make `IStudyTaskRepository` an outlier
and would foreclose a future feature (e.g. a bulk-delete or admin tool) from deleting a task
directly instead of through `LuuHocKyAsync`'s delete-by-absence path. Fixing it keeps the public
contract complete and honest: calling `DeleteAsync` today does exactly what its name promises,
including for entities with children.

**Experience for future development.** When a repository method is "dead in production" but part of
a public interface, default to fixing it to the correct invariant rather than deleting it — deleting
working-but-unused code is a bigger, separate decision (API-surface reduction) that shouldn't ride
on the back of an unrelated bug-fix commit. If a method is later confirmed truly unwanted, remove it
in its own change with its own rationale.

### D2 — Extract a shared `TaskCascadeHelper` instead of duplicating the cascade a second time

**Why it had to be made.** `TaskNote`/`TaskReferenceLink` are FK-only relationships to `StudyTask`
(no navigation property), so EF Core's `.Include()`-driven `ChangeTracker` fixup — the mechanism
`SyncStamper` relies on everywhere else — can never see them. Any code path that removes a
`StudyTask` must hand-cascade these two tables itself. `SqliteHocKyRepository.LuuHocKyAsync`
already had this logic (`CascadeRemoveTaskChildrenAsync`, private to that class); copying it
verbatim into `SqliteStudyTaskRepository.DeleteAsync` would have created two independent
implementations of "which children does a StudyTask cascade to" with no mechanism keeping them in
sync — precisely the kind of drift the reviewer flagged as the underlying risk, not just the one
missed call site.

**What it's for.** A single `internal static TaskCascadeHelper.RemoveChildrenAsync(db, maTask, ct)`
makes "all FK-only children of a StudyTask" a one-place fact. Both delete paths call it, so they
cannot silently diverge again, and a future FK-only child type (if one is ever added) is a one-line
change applied to every caller at once instead of a hunt-and-fix across the codebase.

**Experience for future development.** Whenever EF's navigation-based fixup can't reach a
relationship (FK-only, no navigation property, or reached only via raw SQL), treat the hand-written
cascade as a piece of domain logic that deserves its own named, shared, tested unit — not an inline
block re-derived at each call site. Before adding a new method that deletes/tombstones an entity with
any FK-only children, grep for existing cascade helpers for that entity first (as this fix did for
`StudyTask`) rather than re-deriving which child tables need it.
