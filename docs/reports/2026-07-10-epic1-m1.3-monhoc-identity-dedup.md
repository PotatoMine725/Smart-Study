## Scope

M1.3 — the last Epic 1 item. Give `MonHoc` a semantic identity so "Toán"/"toán "/"Toán  " are
treated as one subject, centralize the four scattered read-side dedups behind that shared
definition, and prevent new normalize-equal duplicates at the add path. Bounded to `MonHoc`, per
the brief — no generalization to other entities, no DB unique constraint, no cross-device
identity-merge (Epic 2).

## Work items

### 1. Identity helper — `Models/MonHocIdentity.cs`

`Normalize(string?)`: NFC-normalize → trim → collapse internal whitespace runs to a single space
→ invariant-culture lowercase. Diacritics preserved (`"Toán" == "toán "` but `"Toán" != "Toan"`,
per the owner-locked decision in the brief). Null/whitespace-only input returns `string.Empty`.
Also exposes `NameComparer : IEqualityComparer<string?>` for call sites that need to dedupe raw
display strings (rather than group `MonHoc` objects) while preserving a real (non-lowercased)
label.

Unit-tested (`SmartStudyPlanner.Tests/Models/MonHocIdentityTests.cs`, 15 cases): NFC
precomposed-vs-decomposed pairs (`"Toán"` via U+00E1 vs `'a'`+U+0301), case, leading/trailing/
internal whitespace (including tab), diacritic-distinct pairs, null/empty/whitespace-only, and the
comparer's `Equals`/`GetHashCode` contract.

## The discriminating test — found and fixed a pre-existing M1.2 gap

Before implementing, ran `gitnexus_impact({target: "MonHoc", direction: "upstream"})`: risk
**CRITICAL**, 55 impacted symbols — expected per the brief ("hub entity, expect a wide radius");
the fan-out is almost entirely tests constructing `MonHoc` objects, and none of this work changes
`MonHoc`'s public shape.

Traced the brief's discriminating-test scenario (merging clones that each own a *distinct* task)
against `LuuHocKyAsync` before writing any code and found a likely collision: its task reconcile
was scoped **per-`MonHoc`-parent** (diffed `oldMon.DanhSachTask` against `newMon.DanhSachTask` by
the parent's Guid), not globally across the `HocKy`. A task that moved between merged clones would
read as "removed under its old parent" *and* "new under the representative" — two conflicting
operations on the same `StudyTask` row in one `SaveChanges`.

Per `superpowers` guidance, didn't act on the prediction — reproduced it first, against
**unmodified M1.2 code**, using two `MonHoc` rows with the exact same raw name (no normalization
involved) each owning a distinct task. It threw:

```
InvalidOperationException: The instance of entity type 'StudyTask' cannot be tracked because
another instance with the same key value for {'MaTask'} is already being tracked.
```

This confirmed the gap was **pre-existing** (M1.2-era, via the existing raw-`TenMonHoc` dedup
already merging exact-duplicate clones) rather than something M1.3 introduces — M1.3 only widens
the trigger (case/whitespace variants are far likelier to carry genuinely distinct tasks than
byte-identical seed clones, which is presumably why this had gone uncaught). Brought this finding
back before touching `LuuHocKyAsync`; owner chose to fix it inside M1.3 (see D2).

**Fix — `SqliteHocKyRepository.LuuHocKyAsync`:** task reconcile is now a flat diff across the whole
`HocKy` (`oldTasksByMaTask`/`newTasksByMaTask`, keyed by `MaTask`, computed before any `MonHoc` is
touched), mirroring the existing `HocKy`-level `MonHoc` diff instead of nesting task-diffing inside
it. A first pass (detach-from-collection before removing the doomed parent) still let the bug
through: EF Core's cascade-on-remove fixup resolves a doomed parent's dependents from its own
tracked relationship snapshot at the moment `Remove()` is called, not from the live
`ObservableCollection` state, so a merely-detached-but-not-yet-reassigned task still got swept into
the cascade and wrongly tombstoned. Fixed by reordering: reparented survivors have their `MaMonHoc`
FK reassigned (and `ChangeTracker.DetectChanges()` forced) **before** any `MonHoc.Remove()` call, so
by the time cascade fixup runs, a surviving task's FK no longer points at the doomed parent at all.

Two integration tests cover this (`SmartStudyPlanner.Tests/Infrastructure/Persistence/RepositoriesTests.cs`):
- `HocKyRepository_DuplicateNamedMonHocClones_DistinctTasks_MergeReconcilesWithoutCollision` —
  regression test for the pre-existing exact-duplicate-name case (no M1.3 code involved in
  triggering it).
- `HocKyRepository_CaseWhitespaceVariantMonHocClones_DistinctTasks_MergeReconcilesWithoutCollision` —
  the brief's actual discriminating test (`"Toán"` / `"toán "`). Both assert: exactly one live
  subject, both tasks present under it, the losing clone reads back `IsDeleted == true`, no task
  lost, no `UNIQUE`/PK exception.

## Decisions made

### D1 — Reparent merged tasks' FK in `LayDanhSachHocKyAsync`, not just their in-memory collection membership

**Why it had to be made.** The pre-M1.3 merge logic moved a clone's tasks into the representative
`MonHoc`'s `DanhSachTask` collection but never touched each task's `MaMonHoc` scalar. That's an
internally inconsistent in-memory graph — navigation says one parent, the FK field says another —
and `LuuHocKyAsync`'s reconcile (both before and after D2's fix) needs the FK to be the source of
truth for "which `MonHoc` does this task belong to now."

**What it's for.** Makes the graph `LayDanhSachHocKyAsync` returns self-consistent: every task's
`MaMonHoc` actually matches the `MonHoc` whose `DanhSachTask` collection contains it, so any code
reading either the FK or the navigation gets the same answer, and `LuuHocKyAsync` doesn't need
special-case knowledge that "this task's FK might be stale relative to its collection membership."

**Experience for future development.** When merging/consolidating entities in memory before a
save, keep FK scalars and navigation collections in sync at the merge site itself, not just at the
eventual save site — an inconsistent detached graph is a latent bug even if the immediate caller
happens to reconcile it correctly, because the *next* caller of the same read method might not.

### D2 — Fixed the pre-existing reconcile gap inside M1.3 rather than handing it back as a blocker

**Why it had to be made.** The brief anticipated this exact possibility and named the remedy
("the same Guid-diff treatment M1.2 gave `HocKy`") but explicitly left the scope call to the
owner rather than assuming authorization to rework freshly-accepted M1.2 code. Reproduced the
collision against **unmodified** M1.2 code first (exact-duplicate names, no normalization) to
separate "does M1.3 introduce this" from "does M1.3 widen an existing trigger" before asking —
brought a failing test and the actual exception, not a prediction. Owner chose to fix it inside
M1.3.

**What it's for.** M1.3's actual goal — safe, correct dedup — only lands if widening the merge
trigger doesn't also widen exposure to a data-loss/crash bug. Fixing it here means M1.3 ships as a
milestone that's actually safe to use, not one that passes its own narrow test while leaving a
known related crash reachable by the same feature it just made more likely to trigger.

**Experience for future development.** When a spec explicitly names a possible pre-existing gap
and its remedy pattern, that's not the same as pre-authorizing the rework — reproduce the failure
against the *unmodified* baseline first (isolates "pre-existing" from "newly introduced," which
changes how big a deal the finding is) and bring concrete evidence (failing test + exception) back
for an explicit scope decision before touching already-accepted code. Treat brief text like "flag
it rather than papering over it" as a mandate to surface the finding clearly, not as license to
silently rework unrelated milestones' code.

### D3 — Reorder reparent-then-remove, and force `DetectChanges()`, instead of relying on collection-membership alone

**Why it had to be made.** A first implementation attempt detached a reparenting task from its
doomed parent's `DanhSachTask` collection *before* calling `db.MonHocs.Remove(oldMon)`, expecting
that to keep it out of EF Core's cascade-on-remove fixup. It didn't: EF resolves a removed parent's
dependents from its own tracked relationship snapshot at the moment `Remove()` executes, not from
live `ObservableCollection` contents (these are plain POCOs using snapshot-based change tracking,
not notification-based) — the task still got cascade-tombstoned despite being detached, since its
FK scalar hadn't moved and `DetectChanges()` hadn't run to reconcile the snapshot. Only caught by
writing real assertions in the discriminating test (task count) instead of only checking for "no
exception thrown," which the first attempt already satisfied while silently losing a task.

**What it's for.** Reassigning the FK scalar *and* forcing `ChangeTracker.DetectChanges()` before
any doomed parent's `Remove()` fires ensures EF's cascade fixup, when it runs, sees the reparented
task as already belonging elsewhere — so cascade only ever touches genuinely-orphaned tasks.

**Experience for future development.** With snapshot-based EF Core change tracking, don't assume
mutating a plain `ObservableCollection` navigation property is enough to influence cascade
behavior that fires synchronously inside `Remove()`/`Add()` calls — that behavior consults EF's own
tracked relationship state, which is only guaranteed current immediately after `DetectChanges()`.
When reordering a parent-removal + child-reparent sequence, do the reparent (FK reassignment +
explicit `DetectChanges()`) *before* the parent removal, not just before `SaveChanges()`. And: "no
exception" is not sufficient verification for a reconcile/merge fix — assert the actual resulting
data shape (counts, specific rows), since a swallowed/silent data-loss bug throws nothing.

### D4 — Also fixed `AnalyticsViewModel`'s subject-filter equality check, not just `SubjectOptions`

**Why it had to be made.** The brief's line-4 target (`AnalyticsViewModel.cs:90`) was specifically
`SubjectOptions`'s `Distinct()`. But `ApplyFilters` immediately downstream compares each task's raw
`TenMonHoc` against `SelectedSubject` (one of those deduped options) with raw string `==`. Fixing
only the dropdown would have deduped the *display* while leaving the *filter* broken: selecting
the shown option would silently exclude every log belonging to whichever clone wasn't chosen as
the representative — a "dedup that half-works," which is precisely what the brief's centralization
goal (D-A) exists to prevent.

**What it's for.** Keeps the dedup coherent across the whole feature (what's shown *and* what's
matched), not just at the one call site literally named.

**Experience for future development.** When a brief names a specific line as a dedup site, check
what immediately consumes that site's output before considering the site "centralized" — a
GroupBy/Distinct fix is often paired with a downstream equality check reading the same field, and
both need the same comparer or the fix is cosmetic.
