## 0. Summary

Eight PRs (#88–#95) took the structural conflict fence from *"two frozen rules collide and nobody
has ruled"* to two merged slices, seven closed owner decisions and a 970-test suite. The durable
lessons are **not** about the fence. They are about seams, sources and authority:

- Three HIGH defects in Slice 2 lived **between** components that each reviewed clean, and 942 green
  tests were fully consistent with all three.
- Two of the review's six substantive findings had no derivable answer in the sources; escalating
  them instead of fixing them was vindicated when the owner ruled one of them **against** the
  review's own engineering recommendation.
- A spec that defines a model as *"whatever the executing path does"* has no answer once two
  executing paths disagree — measured here, and resolved on semantics rather than on either
  implementation.

Seven knowledge entries were written across five existing articles, one new article
(`decision-governance.md`) and a new `knowledge/README.md`. Three documentation-convention changes
were made, each from a pattern seen more than once. **No engineering decision was reopened and no
production code was touched.**

### Documentation convention — the recurring problems these artifacts showed

Each item was seen more than once, and the fix is the smallest one that addresses it.

1. **An artifact type that exists in practice but not in the table.** `docs/README.md` offers
   *decision record → `plans/`*. Every ruling round since 2026-09-11 has instead filed a dated
   ruling record in `specs/` — four of them now (PR-5 amendment, PR-6 rulings, the 2026-09-14 fence
   rulings, the 2026-09-17 M-3/H-1 record) — because their rulings are cited by policy code and
   tests, and belong beside the contracts they bind. Practice diverged consistently and for a reason.
   → **the table gains an `Owner ruling record` row**, with the distinction named and the header
   block (`Closes · Amends · Does not amend · Leaves open · Implemented by`) plus consistency check
   written down. No files were moved.
2. **A review's open question, closed elsewhere, leaves no trace on the review.** #94's Q-1 and Q-2
   were both ruled within a day; Q-2 was ruled **against** the engineering recommendation the review
   attached to it. The merged review still reads as live advice. `review/README.md` already said
   "link the addressing PR/commit at the bottom", which is the wrong granularity for a finding-level
   reversal. → **a dated one-line pointer at the finding, and a back-link from the ruling record.**
3. **The in-repo record of what shipped is missing, and the convention was already adequate.** The
   plan still reads *"Status: `draft`. Planning only"* after two slices merged; `CHANGELOG.md`'s
   newest entry is 2026-08-27 and it carries **nothing for Epic 2** — not these slices, not the
   PR-5/PR-6 work before them; `active/README.md` last moved 2026-08-27; no in-repo file names PRs
   #91/#93/#95.
   `plans/README.md` already required `draft → in-progress → done` and a CHANGELOG row per shipped
   slice — so this is a **compliance gap, not a missing rule**, and it is reported as such. One
   genuine gap sits next to it: nothing said where a slice's *verification evidence* lives, and for
   these slices the mutation tables — the only proof those tests can fail — exist solely in PR
   descriptions on GitHub. → **`plans/README.md` gains "a PR description is not an in-repo
   artifact"**, plus an explicit reminder to move the plan's Status when a slice merges.

Everything else in the convention held up. The evidence-labelling discipline, the amendment rule and
the verdict-vocabulary table were all used correctly and under pressure by these artifacts — #94 even
recorded its mapping from the commissioning brief's vocabulary to this folder's. **No change was made
where the existing convention was already adequate.**

## Decisions made

**D1 — Report the stale canonical-state documents and the plan's stale `Status`; do not fix them
here.**
*Why it had to be made:* the pull to "fix it while I'm in the docs anyway" is strongest exactly where
the claim is weakest — I would be asserting what shipped from reports *about* the work, at a moment
when the repo's own record of it is missing. That is the substitution this cycle's central lessons
warn about, and the 2026-08-19 pass ruled the same way on the same fork.
*What it's for:* the owner gets a scoped decision and a reviewable diff, instead of knowledge edits
mixed with history claims.
*Experience for future development:* a distillation pass that starts editing the canonical history has
changed jobs. The test that settles it: *does this claim come from evidence I read, or from a
document summarising evidence I did not?*

**D2 — Write the new review-pointer convention, but do not retroactively amend #94 in this commit.**
*Why it had to be made:* applying the rule to the review that motivated it is tempting and would make
the convention look proven. But amending a merged review is an edit to someone else's dated artifact,
and the pointer text should name the ruling's own back-link, which does not exist yet — doing half of
a two-sided convention creates a dangling reference.
*What it's for:* the convention lands as a rule; the first application is a small, reviewable follow-up
that touches both sides at once.
*Experience:* a convention and its first retrofit are two changes. Bundling them hides which one the
reviewer is being asked to approve.

**D3 — Open a new article for decision governance rather than extending `architecture-process.md`.**
*Why it had to be made:* the natural-looking home is a single-incident narrative — it opens by
scoping itself to the 2026-06-30 → 2026-07-02 freeze and to decisions D-A…D-J, and its six sections
tell one story. Five recurring lessons about ruling rounds would have had to be spliced into someone
else's incident.
*What it's for:* `architecture-process.md` stays readable as what it is; the governance lessons get a
home that the *next* ruling round extends, which is the test for whether a new file is earned.
*Experience:* the useful question is not "is this lesson new?" but "is this lesson's **home** new?" —
and a single-incident article is not a home for a recurring practice, however adjacent the subject.

**D4 — Check every candidate lesson against the final tracked state before writing it.**
*Why it had to be made:* the richest source in this cycle is the Slice-2 review, and it is partly
superseded. Three of its statements would have entered the knowledge base as durable advice while
being wrong at the point of citation — most sharply its H-1 recommendation, which the owner ruled
against.
*What it's for:* a knowledge base whose entries survive a check against the tree, not just against
the document they came from.
*Experience:* the most citable document in a cycle is usually the review, and a review is a snapshot
taken *before* the decisions it triggered. Distil the reviews for their **method**; distil the
rulings for their **content**. The 2026-08-19 pass paid the same tuition on an amended paragraph.

**D5 — Write `knowledge/README.md` even though the brief warns against creating documents.**
*Why it had to be made:* documentation economy says do not add a file per task — and the shape rule
it records was, until now, rediscoverable only by reading eleven articles or by finding D2 of a
report from a month ago. The previous pass had to re-derive it and then wrote the reasoning into its
own decision log, where the next writer will not look.
*What it's for:* the next agent extending `knowledge/` reads one short page instead of guessing, and
`extend before you add` becomes a rule rather than a habit.
*Experience:* the economy rule is about summaries and per-incident files. A folder's own contract is
the one kind of document that pays for itself every time someone writes in that folder.
