## Findings / fixes

### R1 — flaky A6 fault tests (fixed)

`FocusViewModelA6Tests`'s two throwing-repo tests sampled `ExecutionTask.IsFaulted`
after a single `await Task.Yield()` — a race against the fake repo's own
post-yield fault, reproduced as 2/8 and 2/6 failures in isolation. Replaced the
yield-then-sample pattern with capturing `ExecutionTask` immediately after
`Execute(null)` and awaiting it directly. (This was superseded in shape, not
in spirit, by R5's rework below — the fault is now caught rather than
propagated, so the tests await `execTask` directly and assert it completes
successfully instead of asserting a thrown exception.) Verified 20/20 clean
runs in isolation, twice: once right after the R1-only fix, once again after
the R5 rework.

### R5 — "surface failures" meant user-visible (owner decision: **(b)**)

Owner decision: a failed autosave must reach the user, not just be capturable
in a test. `FlowExceptionsToTaskScheduler = true` alone left the fault live
only on `ExecutionTask` with no runtime subscriber — an unobserved task
exception, silent to the user.

**Change (`FocusViewModel.cs`):**
- `HoanThanh()`/`ThoatKhanCap()` now route the `LuuThoiGianThucTe` call through
  a new `TryLuuThoiGianThucTe(bool, string)` helper that catches the failure,
  tracks `_telemetry.Track("autosave_failed", { task, command, error })`, calls
  a new `NotifyUser(string)` delegate, and returns `false` — the caller then
  returns early instead of marking the task complete / invoking `OnKetThuc`.
  A failed persist no longer leaves the in-memory task marked done while the
  write never landed.
- `NotifyUser` is a public settable `Action<string>` defaulting to a no-op
  field initializer (mirrors the existing `Clock`-style seam pattern already
  used in `AppDbContext`). The production, ServiceLocator-resolving
  constructor overrides it with a real `System.Windows.MessageBox.Show(...)`
  call (same convention already used elsewhere in this codebase, e.g.
  `QuanLyTaskViewModel`). Test-facing constructors never touch it, so tests
  never pop a real modal.
- `FlowExceptionsToTaskScheduler = true` is kept as a defensive backstop for
  any exception outside the guarded `await` (there isn't one today), not as
  the primary surfacing mechanism anymore.

**Emergency-exit decision (owner-ratified, not assumed).** `ThoatKhanCap` binds
to the "✖ Thoát khẩn cấp" button on `FocusWindow` — a maximized, topmost,
borderless focus-lock window (`FocusWindow.xaml.cs:15` wires
`vm.OnKetThuc = () => this.Close()`). Symmetric-with-`HoanThanh` early-return
would let a failing write trap the user in that window exactly when they need
to leave fastest. Put the discriminating question to the owner explicitly
(not decided unilaterally): **always exit** won — `ThoatKhanCap` now tracks
`autosave_failed` + calls `NotifyUser` on failure same as `HoanThanh`, but
unconditionally calls `OnKetThuc?.Invoke()` regardless of save outcome.
`HoanThanh` keeps the block-on-failure behavior — it is not an escape hatch,
so staying open to let the user retry is the safer default there.

**`focus_abort` telemetry stays unconditional (self-caught regression).** A
first pass of this fix only tracked `focus_abort` on the save-success branch,
reasoning it'd be "double-tracking" alongside `autosave_failed` on a failed
attempt. That's wrong — `focus_abort` means *the user hit emergency exit*
(now always true, given the decision above); `autosave_failed` means *the
write failed* — two independent true facts, not a duplicate. Suppressing
`focus_abort` on a failed save would have silently undercounted an existing
metric that used to fire unconditionally, with nothing catching it (291/291
still passed, since no test asserted the old unconditional behavior).
Fixed to track `focus_abort` unconditionally again, and added a test
(`ThoatKhanCap_RepoThrows_...`) asserting both `autosave_failed` and
`focus_abort` are recorded on a failed abort.

**Test changes (`FocusViewModelA6Tests.cs`):**
- Added an inline `FakeStudyTelemetry` capturing `Track` calls (no such
  recording double existed yet).
- Both throwing-repo tests now assert: `ExecutionTask` completes successfully
  (not faulted — the failure is caught, not left unobserved), an
  `autosave_failed` telemetry event was recorded, `NotifyUser` was invoked
  with a non-empty message. `HoanThanh`'s test additionally asserts the task
  was **not** marked complete (`NgayHoanThanh` stays `null`) and `OnKetThuc`
  was **not** invoked; `ThoatKhanCap`'s test asserts the opposite —
  `OnKetThuc` **was** invoked (window still closes on a failed save).
- `HoanThanh_NewStudyLog_HasDeviceIdStamped` untouched in logic (reviewer
  confirmed it wasn't flaky); only reparented onto the shared `BuildVm` helper.

**Verification honesty note.** "Surfaced to the user" is verified at the
`NotifyUser` seam in unit tests (a lambda is substituted and asserted as
called with a non-empty message) — not end-to-end through a real
`MessageBox.Show` dialog, which isn't drivable in this environment. The
production wiring (`FocusViewModel(TaskDashboardItem)` overriding `NotifyUser`
to a real `MessageBox.Show(...)` call) is verified by inspection and by
confirming, via grep, that this 1-arg constructor is the *only* one used in
production (`FocusWindow.xaml.cs:12`) — so nothing in production is
constructing this ViewModel through a path that would leave `NotifyUser` at
its no-op default. Also note: `MessageBox.Show` is a blocking modal, not the
"non-blocking" phrasing the review used when describing option (b) — the
review explicitly allowed "toast/dialog," and a blocking dialog matches this
codebase's existing error-notification convention elsewhere (e.g.
`QuanLyTaskViewModel`), so this divergence from the literal word "non-blocking"
was accepted as consistent with codebase convention rather than re-litigated.
