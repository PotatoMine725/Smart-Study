## Plan gap found during exploration (owner decision required)

Before writing any code, `gitnexus_impact` on `SqliteHocKyRepository.LuuHocKyAsync` (10 direct
callers — `TaoHocKy`, `XoaTask`, `ThemTask`, `HoanThanhTask`, `XoaMon`, `ThemMon`, `LuuDuLieu`,
`MoFocusMode` — the app's single most-called write path) surfaced a correctness blocker the plan
text didn't anticipate: `LuuHocKyAsync` persisted the whole `HocKy` → `MonHoc` → `StudyTask` graph
by **hard-removing** the old subtree and **re-inserting** a new one with the same GUIDs.
`XoaTask`/`XoaMon` delete by *absence* (drop the item from the in-memory graph, re-save the whole
semester) — there is no explicit `Remove()` call for a genuine user delete. Once `HocKy` implements
`ISyncMetadata` and the seam converts `Remove()` to a soft `IsDeleted` update instead of a real
`DELETE`, the old row would still physically exist when the second `Add()` tried to insert a
row with the same primary key — a `UNIQUE constraint failed` on **every** save, not just deletes.

Put to the owner as a two-option decision (reconcile-rewrite vs. narrow G1's scope for M1.2);
**reconcile-rewrite chosen** — G1 closing in M1.2 is a locked plan item, and the alternative would
leave `HocKy`/`MonHoc`/`StudyTask` deletes as real hard deletes, not sync-safe. Reproduced the
failure first (`HocKyRepository_LuuVaLayDanhSach_RoundTripVaOverwrite`, `PK-collision`) before
writing the fix, per TDD.

## What changed

### T1.1 — `ISyncMetadata` on all six entities
`HocKy`, `MonHoc`, `StudyTask`, `StudyLog`, `TaskNote`, `TaskReferenceLink` all implement
`Rev`/`ModifiedAtUtc`/`ModifiedByDeviceId`/`IsDeleted`/`DeletedAtUtc`. Reconciled per the locked
decisions: `StudyLog.IsDeleted` reused as-is; `TaskNote.UpdatedAtUtc` renamed to `ModifiedAtUtc`
(same meaning, one name — `SqliteTaskEditorRepository.UpsertNoteAsync`'s manual stamp removed,
now seam-owned); `CreatedAtUtc` kept distinct from `ModifiedAtUtc` on `StudyLog`/`TaskReferenceLink`.

### `SyncStamper` — Deleted-state cascade tombstone (G1)
Extended the M1.1 seam: `EntityState.Deleted` entries are now converted to `Modified` +
`IsDeleted=true` + `DeletedAtUtc` + `Rev++`, instead of only handling `Added`/`Modified`.
`tracker.Entries()` is snapshotted to a list *before* any state is mutated, so flipping a parent's
state back to `Modified` can't disturb EF's own cascade fixup (which already resolved loaded
children to `Deleted` by the time the snapshot was taken). This also **closed R2** from the M1.1
review: `SyncMetadataStampingTests` now drives a real `AppDbContext` + real `HocKy`/`MonHoc`
entities instead of a parallel test-only `DbContext`/entity pair.

### `SqliteHocKyRepository.LuuHocKyAsync` — reconcile-rewrite (owner-approved)
Replaced remove-then-recreate with a diff against the loaded DB graph, keyed by Guid: unchanged
rows are updated in place via `CurrentValues.SetValues` (with the tracked entity's real
`Rev`/`ModifiedAtUtc`/`ModifiedByDeviceId`/`IsDeleted`/`DeletedAtUtc` restored afterward, so the
incoming detached POCO's stale/default sync fields can't stomp them); rows absent from the new
graph are `Remove()`d (tombstoned by the seam); new rows are `Add()`ed. `MonHoc`/`StudyTask`
cascade-tombstoning uses EF's own fixup (both levels are `.Include()`d together). `TaskNote`/
`TaskReferenceLink` are **not** reachable via `.Include()` (FK-only relationship, no navigation
property on `StudyTask`) — a removed task's notes/links are explicitly looked up and `Remove()`d
in the same `SaveChanges` batch (`CascadeRemoveTaskChildrenAsync`), then tombstoned by the seam
same as everything else. Net effect: unchanged rows keep their identity and `Rev` history instead
of being churned on every save (bonus fix beyond the immediate PK-collision bug).

### T1.8 — `Data/SyncSchema.EnsureColumns` (schema-upgrade seam, sibling of `TelemetrySchema`)
Idempotent `ALTER TABLE ... ADD COLUMN` per missing column (checked via `PRAGMA table_info` first
— SQLite's `ADD COLUMN` has no `IF NOT EXISTS`). `TaskNotes.UpdatedAtUtc` is copied into
`ModifiedAtUtc` for existing rows if the old column is present. Every row without a stamp
(freshly-added column, or a `TaskNotes` row with no `UpdatedAtUtc` to reconcile from) is backfilled
with the upgrade-time clock/device id — the two columns are backfilled **independently** (a row
already reconciled from `UpdatedAtUtc` has a non-null `ModifiedAtUtc` but still needs
`ModifiedByDeviceId`; a single combined `WHERE ModifiedAtUtc IS NULL` would have skipped it — caught
by `EnsureColumns_OnPreEpic1TaskNotesTable_BackfillsModifiedAtUtcFromUpdatedAtUtc` failing with a
NULL-column read before the fix). `SyncSchema.NeedsUpgrade(db)` gives `App.xaml.cs` a cheap
pre-check (one column on one representative table — all six migrate together) so normal launches
on an already-migrated DB don't do any work.

### Backup + migration report (`Data/DbBackup.cs`, `Data/MigrationReporter.cs`)
`DbBackup.CreateBackup` copies the live `.db` file to a timestamped `.bak` before
`SyncSchema.EnsureColumns` runs (only when `NeedsUpgrade` is true, so backups don't accumulate on
every launch). `MigrationReporter.Capture`/`CaptureTable` give a per-table row count + SHA-256
content checksum, ordered by `rowid` for determinism. **Row count is the primary lossless-upgrade
signal** — the checksum only compares meaningfully across the schema change when restricted to the
columns common to both snapshots (the new D-I columns are *expected* to differ pre/post; that's the
migration, not corruption), so a before/after comparison must pass the pre-upgrade column list
explicitly (`CaptureTable_RestrictedToCommonColumns_MatchesAcrossSchemaUpgrade` proves this).

### App.xaml.cs wiring + closing a real gap found by chief-engineer review (`Data/AppStartup.cs`)
`SyncSchema.NeedsUpgrade(db)` → if true, back up then `SyncSchema.EnsureColumns(db)`, placed right
after the existing `TelemetrySchema.EnsureTables(db)` runtime-migration call. A pre-commit advisor
review flagged that all 309 tests up to that point drove `AppDbContext` against an **externally-owned,
always-open `:memory:` connection** — none exercised the actual startup path: a **file-based**
`AppDbContext` that opens/closes its own connection, combined with `DbBackup.CreateBackup`'s
`File.Copy` on that same live file. That combination is exactly where a real bug would hide (e.g.
`File.Copy` throwing if the file is still held open) and is invisible to every other test in this
milestone. Fixed by extracting the whole bootstrap sequence out of `OnStartup` (which is WPF
lifecycle and can't be driven from a unit test) into `AppStartup.EnsureDatabaseReady(db, dbPath)` —
mirroring the exact reasoning `TelemetrySchema` was already extracted for — and adding
`AppStartupFileBasedTests`, which seeds a pre-Epic-1 shape on a real closed file-based SQLite
connection, then runs the identical sequence `OnStartup` calls against a fresh file-based
`AppDbContext`. Both tests pass: the backup file is created successfully, rows survive, and a
second "launch" against the now-migrated DB is a no-op that doesn't re-create a backup.

### Read-path `!IsDeleted` filters
Extended to every repository read query that didn't already have it (`SqliteStudyLogRepository`
already filtered): `SqliteHocKyRepository.LayDanhSachHocKyAsync` (filtered `Include` on the
`MonHoc`/`StudyTask` collections — EF Core's collection-filtered-`Include` syntax), `SqliteMonHocRepository`
(`GetAsync`/`GetByHocKyAsync`), `SqliteStudyTaskRepository` (`GetAsync`/`GetByMonHocAsync`/`GetAllAsync`),
`SqliteTaskEditorRepository` (`GetBundleAsync`/`UpsertNoteAsync`/`GetLinksAsync`). `AppDbContext`'s
`OnModelCreating` cascade config got a comment explaining its new role (drives ChangeTracker fixup,
no longer produces a real SQL cascade) rather than being removed.

- `dotnet build SmartStudyPlanner.slnx` — 0 errors (94 warnings, pre-existing baseline unchanged
  except one new suppressed `EF1002` cluster — `SyncSchema`'s dynamic ALTER/UPDATE statements
  interpolate only hardcoded internal table/column literals, never external input; SQL identifiers
  can't be parameterized, so `ExecuteSqlRaw` is required and the warning is suppressed with a
  one-line justification at the point of use).
- `dotnet test SmartStudyPlanner.slnx` — **309/309 passed** (291 baseline + 18 new).
- `gitnexus_detect_changes(scope: all)` — risk **medium**, 4 affected processes, all rooted at
  `App.OnStartup` (expected: `SyncSchema`/`DbBackup`/`AppStartup` were wired directly into startup,
  which fans out to nearly everything by construction — not a false positive, a real and intended
  blast radius for a startup-path change).

**Verification honesty note — in-place upgrade (plan item 3, "point the app at a copied
pre-upgrade DB").** No real pre-Epic-1 `SmartStudyData.db` exists to copy (this is a pre-alpha dev
environment, not a shipped build with live user data yet). The plan's own T1.8 test-strategy
section specifies building the pre-upgrade shape via raw `CREATE TABLE` rather than a committed
legacy fixture — exactly what `SyncSchemaDualPathTests`/`MigrationReporterTests`/
`AppStartupFileBasedTests` do, mirroring the established `TelemetrySchemaDualPathTests` (M8)
pattern; the last of these three now also exercises a real file-based DB with its own connection
(not the `:memory:`/externally-owned-connection pattern every other test in this milestone uses),
closing the gap a pre-commit advisor review flagged. This is the intended verification mechanism
here, not a substitute for one; a real end-to-end run against an actual alpha-tester DB remains
untested by construction (there isn't one yet) and should be the first thing checked against real
user data if/when one exists.
