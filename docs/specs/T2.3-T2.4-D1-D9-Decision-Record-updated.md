# 1. D1 — T2.3 là pure merge function

## Vấn đề

T2.3 cần merge dữ liệu từ base, local và remote nhưng không nên phụ thuộc `DbContext`, transaction, persistence hay UI.

## Phương án đã cân nhắc

### A — Merge trực tiếp trong `DbContext`

```text
DbContext
  -> load base/local/remote
  -> merge
  -> mutate tracked entities
  -> SaveChanges
```

Nhược điểm:

- Logic merge phụ thuộc persistence.
- Khó test độc lập.
- Dễ trộn semantic merge với `SyncStamper`.
- Khó chứng minh determinism.

### B — Pure merge function

```text
merge(base, local, remote)
        |
        +-- MergedState
        |
        +-- ConflictCandidates[]
```

Không có:

```text
DbContext
SaveChanges
transaction
network
UI
```

## Đã chốt

**D1 = B.**

T2.3 semantic core là **pure merge function**.

Điều này cho phép:

- kiểm thử 3-way merge bằng fixture;
- kiểm thử deterministic / order-independent;
- tách semantic merge khỏi persistence;
- T2.4 nhận side-output conflict để persist.

## Phương án

## Đã chốt

### Contract

- Có version.
- Có `entityType`.
- Có explicit merge-surface `fields`.

- Unknown version => fail closed.
- Unknown entity type => fail closed.
- Missing required merge field => fail closed.
- Bookkeeping giữ ở các cột của `SyncBaseSnapshotRow`.
- Có thể dùng explicit serializer/registry; semantics không thay đổi.

# 3. D3 — DeviceId tie-break

## Vấn đề

Nếu:

```text
Local.ModifiedAtUtc == Remote.ModifiedAtUtc
```

cần tie-break deterministic.

## Đã chốt

```text
Comparer = StringComparer.Ordinal

if timestamp differs:
    later timestamp wins

if timestamp equal:
    lexicographically greater DeviceId wins

if timestamp AND DeviceId equal AND field values differ:
    canonical field-value tie-break; lexicographically greater canonical value wins

if timestamp AND DeviceId equal AND field values equal:
    same provenance/value; argument order must not matter

Rev:
    never consulted
```

Sơ đồ:

```text
same field changed on both sides
              |
              v
       ModifiedAtUtc?
        /              different        equal
      |                |
      v                v
 newer wins      DeviceId Ordinal
                       |
                       v
                 greater wins
```

Không dùng `Rev`, culture-aware comparison hoặc argument-position winner.

# 4. D4 — Structural relationship policy

## Vấn đề

Hai thuộc tính:

```text
MonHoc.MaHocKy
StudyTask.MaMonHoc
```

là structural/reference relationships, không phải ordinary value fields.

Nếu:

```text
Base   = A
Local  = B
Remote = C
```

và `B != C`, timestamp không đủ để kết luận parent đúng.

## Các trường hợp

### A — Một phía đổi

```text
Base   = A
Local  = B
Remote = A
```

=> accept B.

### B — Hai phía cùng đổi tới cùng target

```text
Local  = B
Remote = B
```

=> accept B, không conflict.

### C — Hai phía đổi tới target khác nhau

```text
Local  = B
Remote = C
```

=> `StructuralConflict`.

Không auto-winner.

### Target không tồn tại / đã tombstone

Đây là apply/orchestration concern, không phải pure merge concern.

## Đã chốt

**D4 = structural conflict, không LWW khi hai target khác nhau.**

Các reason có thể về sau gồm:

```text
ConcurrentReparent
MissingParent
ParentTombstoned
InvalidRelationship
```

nhưng tên enum/schema cụ thể chưa phải owner policy.

`TaskNote.MaTask` không thuộc D4; đây là D5.

Sơ đồ:

```text
                  FK / relationship
                       |
          +------------+------------+
          |            |            |
       one-side     same target   different target
          |            |            |
          v            v            v
        accept       accept     StructuralConflict
```

# 20. D9 — SyncStamper boundary

## Vấn đề

Current `AppDbContext.SaveChanges/SaveChangesAsync` gọi `SyncStamper`; `SyncStamper` stamp mọi `Added/Modified` bằng local clock/device.

Điều này đúng cho local edit nhưng sai khi merge result mang remote provenance.

Ví dụ remote thắng:

```text
ModifiedAtUtc      = remote timestamp
ModifiedByDeviceId = remote DeviceId
```

ordinary SaveChanges có thể biến thành:

```text
ModifiedAtUtc      = local now
ModifiedByDeviceId = local DeviceId
```

=> provenance bị hỏng.

## Anti-pattern bị loại

Không tạm đổi:

```text
db.Clock
db.DeviceIdProvider
```

quanh SaveChanges vì chúng áp dụng batch-wide và có thể làm hỏng unrelated local edits.

## Engineering DoR

Trước implementation phải chốt seam cụ thể.

Các hướng đã xem xét:

```text
A. scoped suppression mechanism
B. dedicated merge-apply seam vẫn gọi SaveChanges
C. raw SQL bypass
```

Raw SQL không được dùng như silent shortcut. Nếu đi vòng SaveChanges, đó phải là exception được audit rõ ràng.

# 23A. Owner-ratified amendment — D9-T1..D9-T6 (2026-09-08)

Current-code triage identified six policy gaps that were not mechanically resolvable from the frozen text alone. The owner has explicitly ratified the following amendments. These rulings supersede any earlier `OPEN` wording or ambiguity on the same point.

## D9-T1 — Unresolved conflict staging

For `StructuralConflict` and `ConstraintConflict`, while the conflict is `Unresolved`, the live domain state **must equal Base**. The conflict candidates are not allowed to remain materialised as competing live domain state. `ConflictRecord` is the staging boundary holding the recoverable Base/Local/Remote evidence until explicit resolution.

This is a semantic invariant; the concrete staging mechanism is engineering design, subject to the Epic-1 tombstone/no-hard-delete constraints and the existing `TaskNote` uniqueness invariant.

For a null Base, “live = Base” means that the conflict scope has no live domain row. Resolution may subsequently materialise Local, Remote, Base(null), or a new ManualMerge result.

## D9-T2 — Full provenance tie

LWW ordering is now fully defined:

```text
1. ModifiedAtUtc
2. StringComparer.Ordinal on ModifiedByDeviceId
3. if both are equal and values differ:
       canonical serialized field value
```

At step 3, the lexicographically greater canonical field value wins. If values are equal, the result is identical on both sides and is not a conflict. `Rev` remains excluded from this ordering.

The canonical value used for this tie-break must be deterministic and the same on every peer.

## D9-T3 — Creation provenance / merge surface

The following are ratified as **copy-on-create, immutable, excluded from the LWW merge surface**, unless explicitly classified otherwise below:

```text
StudyLog.DeviceId        -> creation provenance
StudyLog.CreatedAtUtc    -> creation provenance
TaskReferenceLink.CreatedAtUtc -> creation provenance
```

`StudyLog.MaTask` and `TaskReferenceLink.MaTask` are creation-time references, not ordinary LWW merge fields.

The following remain explicitly excluded as derived/dev state:

```text
HocKy.IsSeeded
StudyTask.DiemUuTien
StudyTask.MucDoCanhBao
```

These fields are not conflict candidates and are not used for convergence semantics.

## D9-T4 — Tombstoned structural parent

If a structural target required by `D4` exists only as a tombstone, the incoming child/relationship is **not** materialised as a live orphan. The apply outcome is a `StructuralConflict`.

A missing required parent remains a fail-closed/deferred apply concern governed by apply ordering; no implicit live orphan is permitted.

## D9-T5 — Auto-resolved evidence

T2.3 may emit conflict evidence for decisions that are semantically auto-resolved. Two explicit resolution kinds are ratified:

```text
AutoLww
AutoTombstone
```

Such evidence records are written directly as:

```text
Status = Resolved
```

and are **not re-resolvable**. `FieldConflict` evidence represents the LWW decision and `delete-vs-edit` evidence represents the tombstone-wins decision; neither changes the underlying deterministic merge outcome.

Unresolved human-resolution conflicts remain:

```text
Unresolved
    -> KeepLocal / KeepRemote / KeepBase / ManualMerge
    -> Resolved
```

## D9-T6 — One unresolved conflict per logical scope (v1)

Version 1 enforces:

```text
at most one Unresolved ConflictRecord per logical conflict scope
```

`ConflictKey` remains the retry/idempotency identity for a candidate state. If a new candidate pair maps to the same logical scope but produces a different `ConflictKey` while an older record in that scope is still `Unresolved`, the sync operation is **rejected** rather than creating a second unresolved conflict. Supersede/reopen semantics are out of scope for v1.

# 27. Open / implementation-only items

### CLOSED-7 — Exact per-entity merge-surface table

Owner ratified the semantic exclusions and reference/provenance treatment in D9-T3. The implementation must encode the ratified table explicitly and may not infer new policy.

### OPEN-8 — `TaskReferenceLink` Rev-reset defect

Phải được xử lý independently trước hoặc cùng T2.3 để không xây sync trên invariant Rev đã biết là broken.
