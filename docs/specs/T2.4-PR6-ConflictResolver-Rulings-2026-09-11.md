This file does **not** edit the frozen Decision Record, the D4/D9-T4 amendment, the PR-5
context-lifetime amendment, or the 2026-09-08 engineering DoR. It follows the pattern those
amendments set. It is the dated, tracked record of owner rulings that the PR-6 design review
escalated because the frozen text left them open.

## Why it was needed

The PR-6 design review (`docs/review/2026-09-11-t2.4-pr6-conflict-resolver-dor.md`, rev 1) found four
places where no ratified text decides what the resolver must do:

- **B-1.** The Option A context-lifetime amendment is PR-5-only by its own text, so PR-6 had no
  ratified context lifetime.
- **B-2.** DoR §12.2's parent-rule outcomes are apply-time actions: stage a StructuralConflict, or
  cascade-tombstone. Neither is coherent at resolution time. PR-5 residual 12 is one instance of
  this gap.
- **B-3.** Neither D6-H nor DoR §13 says what a ManualMerge result with `IsDeleted = true` means.
  For a parent-owning type it would need a cascade, and that sets A2-b against A2-c.
- **B-4.** The D4/D9-T4 amendment created a record shape with no local candidate. It did not say
  what `KeepLocal` means for that shape.

It also asked for an acknowledgement of E-3, an engineering rule that narrows a written DoR sentence.

## The rulings (verbatim)

> B-1 — PR-6 context lifetime:
> Option A.
> Each ResolveAsync operation owns exactly one AppDbContext. The context must be disposed on every success/failure path. A failed operation must not reuse the failed context; retry means a new ResolveAsync call with a fresh context.
> This PR-5-specific context-lifetime amendment remains scoped to PR-5. For PR-6, apply the explicit per-ResolveAsync context ownership rule above.
>
> B-2 — Resolution-time result-parent liveness:
> Option A, with KeepBase subcase (i) exempt.
> Reject resolution if the requested materialized result would have a tombstoned or missing structural parent. The ConflictRecord remains Unresolved.
> KeepBase is exempt when it produces no domain write; however, if a KeepBase path would actually materialize/write a result, the same parent-liveness rule applies.
> Do NOT materialize a requested result merely to satisfy FK-only children.
>
> B-3 — ManualMerge with IsDeleted=true:
> Option A.
> Reject ManualMerge results with IsDeleted=true in PR-6 v1.
> Do not introduce leaf-specific exceptions or cascade semantics in PR-6.
>
> B-4 — KeepLocal on AL-PT:
> Option A.
> For AL-PT (ParentTombstoned with no local candidate), KeepLocal is KindNotApplicable and must be rejected. Do not reinterpret KeepLocal as a null result.
>
> E-3 — Entity-scoped ManualMerge identity:
> ACKNOWLEDGED.
> For entity-scoped Structural ConflictRecords, ManualResultEntityId must equal the record's EntityId. A fresh Guid is only appropriate for constraint scopes where a new entity is actually being created.

## What the rulings do and do not authorise

| Item | Authorised / required | Forbidden |
|---|---|---|
| **B-1** | One `AppDbContext` per `ResolveAsync` call, created from the composition-root factory, disposed on every exit path (`Applied`, `NoOpReplay`, `Rejected`, `Failed`); a retry is a new `ResolveAsync` call with a fresh context that re-reads the record | Sharing a context across `ResolveAsync` calls; reusing a failed call's context for its retry; a caller-supplied context whose disposal is left to the caller |
| **B-2** | Reject when the result that would be materialised has a tombstoned or missing parent; the record stays `Unresolved`, nothing is written. `KeepBase` is exempt only when it produces no domain write | Cascade-tombstoning or otherwise changing the requested result at resolution time; materialising the requested result (as a tombstone or otherwise) to satisfy FK-only children; exempting a `KeepBase` that does write |
| **B-3** | Reject every ManualMerge result with `IsDeleted = true`, for every entity type | A leaf-type (TaskNote) exception; any cascade semantics in PR-6 |
| **B-4** | `KeepLocal` on an AL-PT record ⇒ `Rejected(KindNotApplicable)` | Treating that `KeepLocal` as a null result (equivalent to `KeepBase(null)`) |
| **E-3** | For entity-scoped Structural records, `ManualResultEntityId == EntityId`; a fresh Guid only where a constraint scope actually creates a new entity | A fresh Guid on an entity-scoped Structural record |

**Unchanged by all five:** D1–D9 and D9-T1..D9-T6 semantics; D7-G (a null result is legitimate for
`KeepBase`); ACK A2-c (the resolution result is an ordinary local write, stamped by `SyncStamper`, with
no `MarkSyncApplied`); D8-H (reject on drift, no force, no rebase).

## What these rulings do not decide

Everything below is how the design review *applies* the rulings. Each item is either derived from a
ruling plus frozen text, or an engineering choice the owner may override. None of it is an owner
ruling. Detail is in the review's §11 and §15.2.

- **B-2 and FK parents (derived).** The ruling's first sentence says *structural* parent. For an FK-only
  child (a TaskNote result whose task is tombstoned), materialising it live is already forbidden by
  frozen ACK A2-a. Materialising it as a tombstone is forbidden by the ruling's last sentence. The only
  outcome left is rejection. The review records that result as derived, not as ruled.
- **B-2's "would actually write" clause (engineering).** The review keys the exemption on "the
  resolution's write plan is empty", not on `Kind == KeepBase`. Under engineering choice E-5 and the
  drift gate, no reachable input makes `KeepBase` write. The clause is therefore a structural guard,
  and no test can observe it.
- **B-2 for a result that is itself a tombstone (reading).** The review applies the rule literally.
  Any materialised result with a tombstoned or missing parent is rejected, whether or not the result
  itself is a tombstone. `KeepBase(null)` still frees the scope.
- **B-4 predicate (engineering).** The review keys the check on "the record has no local candidate".
  The `CK_SyncConflictRecords_LocalCandidate` CHECK and the D4/D9-T4 amendment make that set equal to
  AL-PT in every reachable case.
- **Reject-reason names** (for example the name used for B-3's rejection). These are engineering
  naming.
