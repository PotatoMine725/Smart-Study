The frozen Decision Record is **not** edited by this file. D1–D9 and D9-T1..D9-T6 remain as
ratified; this document is the dated amendment that extends the ConflictRecord *representation* so
that D9-T4 can be honoured in the one case where the v1 evidence model had no slot for the truth.

## Why it was needed

PR-5 found that a remote **pure create** whose structural parent is tombstoned locally could not be
staged at all. D9-T4 demands a `StructuralConflict`, but for a pure create there is no Base **and no
local row**, while `ConflictCandidate.Local` and the schema's `LocalSnapshotJson` were both
non-nullable. The only available value was the remote row, so staging would have meant recording a
local candidate that never existed — fabricated evidence in an append-only, immutable evidence table
(D7-F). PR-5 therefore rejected the operation (keeping the invariant that matters: the child is not
materialised) and escalated rather than inventing a representation.

## The ruling (verbatim)

> D4 / D9-T4 Amendment — Pure Create Under Tombstoned Structural Parent
>
> When a remote pure-create operation targets a structural parent that is
> tombstoned, the operation MUST resolve as StructuralConflict and MUST NOT
> materialize the child as a live row.
>
> A StructuralConflict MAY have no local competing candidate when the local
> state contains no row for the logical child scope.
>
> In that case:
> - ConflictCandidate.Local MUST be absent/null;
> - LocalSnapshotJson MUST be absent/null;
> - ConflictCandidate.Remote and RemoteSnapshotJson represent the actual
>   remote candidate;
> - the absence of a local candidate MUST NOT be represented by a fabricated
>   placeholder row or synthetic local snapshot;
> - the child MUST NOT be materialized;
> - the conflict is persisted as an unresolved StructuralConflict subject to
>   the existing D9-T6 scope-lock semantics.
>
> This is an extension of the ConflictRecord representation only; it does
> not change the meaning of D9-T4 that a tombstoned structural parent can
> never have a live child.

## What the amendment does and does not authorise

| | |
|---|---|
| Authorised | `ConflictCandidate.Local` nullable; `LocalSnapshotJson` / `LocalFingerprint` / `LocalEntityId` nullable |
| Authorised | An `Unresolved` `StructuralConflict` record with no local candidate |
| Unchanged | A tombstoned structural parent can never have a live child (D9-T4's meaning) |
| Unchanged | D9-T6 scope-lock governs the resulting record exactly as for any other unresolved conflict |
| Forbidden | Any fabricated placeholder row or synthetic local snapshot standing in for the absent candidate |
| Forbidden | Materialising the child |

The amendment is scoped to `StructuralConflict`. It says *"A StructuralConflict MAY have no local
competing candidate"*, not *"a ParentTombstoned StructuralConflict"* — so the implementation permits
absence at the `Kind` level and does not narrow it further to `StructuralReason.ParentTombstoned`.

## Implementation consequences (PR-5)

1. **PR-1 pure core** — `ConflictCandidate.Local` becomes `EntitySnapshot?` and `LocalEntityId`
   becomes `Guid?`. `ConflictKeys.CandidateFingerprint` gains an `AbsentCandidate` sentinel so an
   absent candidate is distinguishable from a present one, and `ConflictKeys.ConflictKey` throws
   `MergeContractViolationException` when any kind other than `StructuralConflict` arrives with no
   local candidate, or when the snapshot and the id disagree about presence.
2. **PR-4 staging row / schema** — `LocalEntityId`, `LocalSnapshotJson` and `LocalFingerprint` become
   nullable, guarded by a new DB-level `CK_SyncConflictRecords_LocalCandidate` CHECK constraint:
   the three columns are present or absent **together**, and absence is legal only for
   `Kind = 1` (`StructuralConflict`). SQLite cannot drop `NOT NULL` or add a CHECK in place, so
   `SyncConflictRecordSchema.EnsureTable` gained a one-shot, transactional table rebuild that
   preserves existing rows.
3. **PR-5 apply layer** — the pure-create case stages the conflict through a dedicated path that
   performs **no** `WriteAsync` and **no** baseline upsert. It is deliberately not routed through
   `StageStructuralAsync`, which rewrites the local row to Base and reads `localEntity.Rev`.

### Replay behaviour, stated explicitly

Re-offering the same create while the record is still `Unresolved` is **rejected by the D9-T6
scope lock**, not reported as `ConflictAlreadyStaged`. For an entity operation the scope-lock key is
the structural scope key — the same `ScopeKey` the staged record occupies — and that check runs
before parent inspection. Both replay shapes therefore converge on the same safe outcome: no second
record, and no materialised child.

- remote unchanged (same `ConflictKey`) → `Rejected(ScopeHasUnresolvedConflict)`
- remote edited (new `ConflictKey`, same `ScopeKey`) → `Rejected(ScopeHasUnresolvedConflict)`

### Residual, still rejected

A local row that exists **with no Base** under a tombstoned structural parent is a different case:
there *is* a competing local candidate, so the amendment does not apply, but "hold the local row at
Base" has no Base to hold it at and no audited withdrawal mechanism exists for anything but a
`TaskNote` (M5). PR-5 rejects it with the typed reason
`SyncApplyReason.ParentTombstonedLocalRowWithoutBase`. It is believed unreachable — phase-1 parent
tombstones cascade before phase-2 child application, so the local child is already a tombstone by
the time this could be evaluated — and no test constructs it.
