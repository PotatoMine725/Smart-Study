The frozen Decision Record is **not** edited by this file, and neither is DoR §12.1's `[FROZEN]`
unit claim ("one logical operation = one transaction"). This document ratifies only the *context
lifetime mechanism* that §12.1's prose separately describes ("owns one `AppDbContext` ... for the
whole run") — a claim the residuals note (R2 OPEN) already identified as outside D1–D9 and
D9-T1..D9-T6, and which PR-5 needed ratified before it could implement against it.

## Why it was needed

`docs/review/2026-09-09-t2.4-pr5-pr2-residuals.md` (R2) found that a failed `SyncStamper`
validation leaves a dirty, unmarked instance in the `ChangeTracker`. Under §12.1's literal
run-scoped context, that dirty instance survives into the *next* logical operation's transaction
as ordinary happy-path behaviour (Case A), or an already-`SaveChanges`-committed-then-rolled-back
instance is handed back by identity resolution on a later read (Case B). The residuals note offered
two candidate fixes and required the owner to ratify one before PR-5 implemented against it (R2
checklist item: "context-lifetime deviation from DoR §12.1 raised with the owner and ratified
before implementing").

## The ruling (verbatim)

> ONE APPCONTEXT PER LOGICAL OPERATION (Option A)
>
> - One logical sync operation owns one `AppDbContext`.
> - The context is disposed on every path.
> - The entire logical operation remains inside one transaction.
> - A failed operation must not reuse its mutated `DbContext`.
> - Retry / subsequent operation must use a fresh `DbContext` and reload authoritative persisted
>   state.
> - This is a PR-5-specific engineering / governance decision. It does not change D1-D9 semantics.
>   It does not change D9-T1..D9-T6 semantics.
> - It supersedes the "one AppDbContext ... for the whole run" mechanism wording in DoR §12.1 for
>   PR-5 only.

## What the amendment does and does not authorise

| | |
|---|---|
| Authorised | One `AppDbContext` per logical sync operation — created, used for exactly one `BeginTransactionAsync` / `COMMIT` / `ROLLBACK` cycle, then disposed |
| Authorised | Discarding a failed operation's mutated context instead of reusing it for the next operation or a retry |
| Authorised | A retry or subsequent operation constructing a fresh context from the same composition-root factory and reloading authoritative persisted state |
| Unchanged | DoR §12.1's `[FROZEN]` unit claim: one logical operation = one transaction |
| Unchanged | D1–D9 and D9-T1..D9-T6 semantics (this amends an engineering mechanism, not the frozen semantic contract) |
| Forbidden | Sharing one `AppDbContext` (and its `ChangeTracker` / identity map) across independent logical operations within a run |
| Forbidden | Reusing a failed operation's context for its own retry |

## Relationship to DoR §12.1

DoR §12.1's `[FROZEN]` tag is on its *unit* claim ("one logical operation = one transaction"),
which this amendment preserves exactly. The separate prose in the same section — "owns one
`AppDbContext` ... for the whole run" — is the run-scoped *mechanism* wording this amendment
supersedes, for PR-5 only. It does not touch §2.1 (D1–D9) or §2.2 (D9-T1..T6), and it does not
apply to any component outside PR-5's sync-apply session.

## Rationale

Per-operation context lifetime makes R2's Case A and Case B structurally impossible rather than
requiring a disciplined, hand-maintained `ChangeTracker` / identity-map reset between operations:
there is no long-lived tracked state for a failed operation's dirty or stale-but-`Unchanged`
instances to leak into. The alternative (one context per run, plus an explicit dirty-state reset
between operations) was rejected because that reset mechanism is easy to get subtly wrong, and
Case B in particular leaves nothing dirty to detach — the surviving instance looks clean and is
still ahead of the database.

## Implementation

Implemented in PR-5 (`worktree-pr5-apply-session`, PR #76): each logical sync operation constructs
its own `AppDbContext` from the composition-root factory (preserving `DeviceIdProvider` identity),
scopes one transaction to it, and disposes it on every exit path — see
`docs/review/2026-09-10-t2.4-pr5-apply-session.md`, section "Context lifetime — the
residuals-note OPEN, resolved", for the as-built description. This document is the durable, dated
owner-ruling that report was written against; no tracked governance record of the ruling existed
until now (the report itself flags this gap and names the D4/D9-T4 amendment as the pattern to
follow).
