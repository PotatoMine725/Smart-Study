## What's correct (confirmed)

- **Shared helper, no drift.** `TaskCascadeHelper.RemoveChildrenAsync(AppDbContext, Guid, ct)` is a single
  `internal static` method (correct visibility — both callers are in the production assembly; the test drives
  `repo.DeleteAsync`, not the helper, so no `InternalsVisibleTo` needed). Its body is byte-for-byte the old
  private `CascadeRemoveTaskChildrenAsync` — Note → `Remove`, Links → `RemoveRange`. The comment states the
  FK-only rationale (why EF's `.Include()` fixup can't reach these).
- **The old private method is deleted** — not left as dead code. `LuuHocKyAsync`'s two call sites
  (MonHoc-removed branch, Task-removed branch) now point at the shared helper. `SqliteStudyTaskRepository`
  calls it too, so the two delete paths cannot silently diverge — this fixes the *underlying* risk the review
  flagged, not merely the one missed call site.
- **`DeleteAsync` ordering is right.** Helper (removes Note/Links) → `db.StudyTasks.Remove(existing)` →
  single `SaveChangesAsync`. All three go `Deleted → Modified` + tombstone in one transaction. Order within the
  ChangeTracker is irrelevant — `SyncStamper` snapshots `Entries()` to a list before mutating, so nothing
  disturbs the batch.
- **The exit-check test is non-vacuous.** `StudyTaskRepository_DeleteAsync_CascadesToNoteAndLinks` seeds a
  task **with** a `TaskNote` + a `TaskReferenceLink`, deletes it, then asserts all three read back
  `IsDeleted == true` (against the raw tables, so a tombstoned row is visible to assert on — the right choice;
  a filtered read would return null and prove nothing). `IsDeleted` is `false` on insert and only the cascade
  flips it, so a missing cascade genuinely fails the note/link assertions — corroborating the report's
  RED-first claim without needing to reproduce it. The pre-existing childless round-trip test is retained.

### Completeness check — is `{TaskNote, TaskReferenceLink}` the *whole* cascade set? (yes)

The fix is only correct if Note/Links are the **complete** set of StudyTask's cascade children — G1 requires
tombstoning *all* live descendants, and a second missed child would be a second R1. The ground truth is
`AppDbContext.OnModelCreating` (the config that defined the pre-M1.2 DB-level `ON DELETE CASCADE`, now
annotated fixup-only). Enumerated:

| Relationship | `OnDelete` | Handled by |
|---|---|---|
| `HocKy → MonHoc` | Cascade | EF fixup on loaded children (no HocKy-delete path exists today) |
| `MonHoc → StudyTask` | Cascade | EF fixup on loaded children (`LuuHocKyAsync` MonHoc-removed branch) |
| `StudyTask → TaskNote` (1-1) | Cascade | **`TaskCascadeHelper`** (FK-only, no nav prop) |
| `StudyTask → TaskReferenceLink` (1-N) | Cascade | **`TaskCascadeHelper`** (FK-only, no nav prop) |
| `StudyLog` | **none** — standalone | intentionally retained (see below) |
| `StudyTimeOutcomeLog` / `DifficultyLabelLog` / `WeightChangeLog` | **none** — standalone, `MaTask` nullable ref only (line 90 comment) | intentionally retained |

`StudyLog` was the open name (it's a synced, soft-deletable entity that carries `MaTask`). The config
confirms it has **no cascade FK to StudyTask** — a hard-deleted task never removed its StudyLogs pre-M1.2, so
the tombstone-cascade correctly leaves them alone. Retaining historical logs across task deletion is the
pre-existing, intended behavior. **Conclusion: `{TaskNote, TaskReferenceLink}` is the complete FK-only cascade
set for StudyTask. The helper is exhaustive; no second orphan hides here.**

## Minor observations (non-blocking — noted, not findings)

1. **`DeleteAsync` re-tombstones an already-deleted task.** It loads via `FirstOrDefaultAsync(t => t.MaTask
   == maTask)` with no `!IsDeleted` filter, so calling it on an already-tombstoned task re-stamps `Rev` +
   `DeletedAtUtc`. End state is identical, it has zero production callers, and re-deleting is benign under
   last-write-wins. Not worth changing. (`LuuHocKyAsync` re-stamps the same way; it's a general property of
   the tombstone model, not this fix.)
2. **Forward note (not M1.2):** the same FK-only-children class of gap would reappear if a *delete-HocKy*
   path is ever added (removing a HocKy fixup-tombstones loaded MonHocs/StudyTasks but not their FK-only
   Note/Links). No such path exists today, so it is neither active nor latent-in-a-public-API. Flagging it so
   whoever adds cascade-delete of a HocKy remembers to route task children through `TaskCascadeHelper`.
