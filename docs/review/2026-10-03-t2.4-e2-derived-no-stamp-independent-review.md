## 5. Risks / watchouts (findings by severity)

### F-1 — MEDIUM — REPRODUCED — `Attach` + Derived-only set is not stamped, contrary to the ratified §1 clarification

- **Location:**
  - `SmartStudyPlanner/Data/SyncStamper.cs:101-116` @ `0c37d57`;
  - rulings `docs/specs/2026-10-03-fence-slice4-followup-owner-rulings.md:35-36`;
  - report `docs/reports/2026-10-03-e2-derived-no-stamp.md:148-149`.
- **What is wrong.** The clarification ratified on 2026-10-03 says *"when the stamper cannot trust original values
  (detached Update/Attach), it stamps as before; value comparison applies only to tracked entries with real
  originals."* Report §6.3 repeats "detached `DbSet.Update` / `Attach`".
  - The code has no notion of "entries with real originals". Its detector is property-level: *a property flagged
    modified whose value is unchanged, outside the SyncMetadata/Tombstone block*.
  - That catches `DbSet.Update` and `State = Modified` (P2d and P2e both stamp).
  - It cannot see `Attach`. `Attach` takes a snapshot of the attached object's current values as originals, so a
    later Derived-only set changes exactly one Derived property and nothing is flagged-but-equal.
  - The code comment (`SyncStamper.cs:93-95`) and the CHANGELOG row say only "detached `DbSet.Update`", and both
    are accurate.
- **How shown.** In probe P2a, a detached `StudyTask` is `Attach`ed, then `DiemUuTien += 2`, then saved on
  `Later`/`OTHER-LOCAL`.
  - At head the row stays `rev=1 mod=2026-05-01T10:00 by=LOCAL-DEVICE`: **not stamped** (`Expected: 2, Actual: 1`).
  - At `3c49924` the same probe is stamped.
- **Why only MEDIUM.**
  - There is **no `Attach(` anywhere in production** (OBSERVED, grep over `SmartStudyPlanner/**`).
  - P2b shows the gap cannot persist an unstamped Merge value: a POCO carrying an unsaved `TenTask` edit, attached
    and then given a Derived set, writes only `DiemUuTien`, because EF writes only modified columns. P2c shows
    `Attach` + Merge set is stamped.
  - So the only unstamped write is a Derived-only one, which is exactly what §1's main rule wants.
  - The defect is that two ratified texts disagree on this input, and the report/rulings describe a capability the
    code does not have.
- **Direction (not a patch).** This is the owner's call (OQ-1). Either:
  - narrow the clarification and report §6.3 to "detached `Update` / forced `State = Modified`", noting that `Attach`
    falls under the main rule; or
  - if `Attach` must stamp, add a source-scan guard that forbids `Attach` on `ISyncMetadata` entities in production,
    because the stamper cannot detect it.

### F-2 — MEDIUM — REPRODUCED — No test pins "a Tombstone-class value change on the unmarked Modified path stamps"

- **Reachability (INFERRED, grep).** No production code path sets `IsDeleted` on an unmarked tracked entity:

  - sync-apply tombstones are marked.
  - So this is a guarantee without a test, not live wrong behaviour.
- **Direction.** Adopt P3a/P3b-shaped tests next to `LocalDelete_StillBecomesStampedTombstone`. For contrast, MX2

## Decisions made

- **Reviewed `0c37d57`, not the addendum's `e9fb6cc`.**
  - *Why:* the addendum says to re-check the head, and the delta is docs-only. It records the ratification the
    addendum already cites.
  - *For:* reviewing the state the owner will actually merge.
  - *Experience:* always diff the named SHA against the live head before deciding whether a moved head is a stop
    condition.
- **Ran every probe at the merge base as well as at head.**
  - *Why:* a probe that passes at head proves nothing unless it can fail. P1b/P4/P6 RED at base show they
    discriminate.
  - *For:* evidence that the fix, not the fixture, produces the green.
  - *Experience:* P6 first stopped at the fingerprint assertion on base. I relaxed it in the base copy only, to show
    that the resolver itself returns `Rejected` there, so the end-to-end claim is measured and not inferred from the
    proxy.
- **Checked unmarked Sync-side *writers*, not only readers (attack 8).**
  - *Why:* `ConflictResolver` deliberately never marks (A2-c), so its writes run through the very branch this PR
    changed. A value-identical resolver write losing its `Rev++` would never reach a peer.
  - *What:* P7 measured all three Keep* kinds head vs base and found them identical.
  - *Experience:* a "readers of X" grep does not cover "writers that relied on X being bumped".
- **Rated F-1 MEDIUM, not BLOCKER, though it contradicts a ratified text.**
  - *Why:* no production `Attach` exists, and P2b shows the gap cannot persist an unstamped Merge value. Two
    ratified texts disagree on this input.
  - *For:* the template routes ratified-source conflicts to the owner (OQ-1) rather than having the reviewer
    resolve them.
- **Added my own mutants MX1/MX2 beyond the report's list.**
  - *Why:* the predicate has two class exemptions, and the report's mutants test neither class boundary.
  - *Experience:* MX1 survived. A mutant aimed at each branch of an exemption list is cheap and found the only
    untested guarantee.
