## 4. The integration decision (reframes items 3, 6, 7, 8)

**FACT:** every mechanism that makes R1/R2 hold, and the parent-liveness check residual 12 depends on,
is `private static` inside `SyncApplySession`:
`WriteAsync`, `InspectParentAsync`, `LoadParentAsync`, `LoadTrackedAsync`, `LoadNoTrackingAsync`,
`StructuralScopeKeyOf`, `UpsertBaselinesAsync`, `TryReadBaseline`, `LoadTaskNoteBaselineInScopeAsync`,
`OperationState` (nested private class). None of these are visible to a new PR-6 type, even in the
same assembly.

**FACT — reachable to PR-6 (public or `internal`, same-assembly):** `ConflictKeys`, `MergeOutcomes.cs`
types, `SyncBaseFingerprint` (a `public` top-level class declared alongside, but not nested inside, the
`internal` `ConflictStaging` — both in `ConflictStaging.cs`, same namespace; `SyncBaseFingerprint`
itself is fully public, no accessibility inherited from its file-mate), `SyncConflictRecordStore` (incl. `MarkResolvedAsync`),
`SyncBaseSnapshotStore`, `EntitySnapshotMapper` (`internal`, same-assembly reachable),
`IncomingChanges` (`public`), `AppDbContext.MarkSyncApplied` (`public`, unguarded).

**INFERENCE:** R1 is closed **inside PR-5's session**, by a private choke point (`WriteAsync`) — it is
**not** closed for any other writer. `MarkSyncApplied` remains public and, per the PR-2 residuals note
(R1, `2026-09-09-t2.4-pr5-pr2-residuals.md:37-70`), a mark-time tracked-state guard was *deliberately
rejected* because it would spuriously reject the legitimate mark-before-`Add()` ordering. So a PR-6
resolver that calls `db.MarkSyncApplied(entity)` directly gets **no compiler or runtime backstop**
against marking an `AsNoTracking` or otherwise wrong instance — it must re-derive the same discipline
`WriteAsync` encodes, or PR-6 must extract/reuse that method.

**INFERENCE:** the same applies to residual 12 (§6) — the parent-liveness check that a `KeepRemote`
resolution would need is `InspectParentAsync` + `LoadParentAsync`, both private. PR-6 cannot call them;
it must re-implement the same FK-lookup-by-child-type logic, or the seam must be refactored to expose
it.

**INFERENCE — the ContextLifetime amendment does not cover PR-6.** `T2.4-PR5-ContextLifetime-Amendment-2026-09-11.md`
states, verbatim: `**Scope** | T2.4 PR-5 only` and "it does not apply to any component outside PR-5's
sync-apply session." R2's structural fix (per-operation `AppDbContext`) is therefore **ratified for
PR-5's transaction loop only**. If PR-6's `ConflictResolver` runs its own database interaction outside
that loop (e.g., a user clicks "Keep Local" in the UI, off the sync path entirely), R2's hazard
(dirty/stale `ChangeTracker` state surviving a failed save) is **unratified territory** for that code
path — this is a governance gap parallel to residual #1 in the PR-5 review ("specs on no branch"), not
yet flagged anywhere else.

**RECOMMENDATION (for the design review, not self-authorised here):** the design review should decide
between two shapes before PR-6 starts:
1. **Extract the seam.** Promote `WriteAsync`, `InspectParentAsync`/`LoadParentAsync`, and the
   per-operation-context pattern into something PR-6 can call (a shared internal helper type, or move
   `ConflictResolver`'s write path into `SyncApplySession` itself as a new public entry point). This
   reuses proven, mutation-tested logic.
2. **Re-implement and re-prove.** PR-6 gets its own tracked-write choke point and its own
   context-lifetime discipline, independently mutation-tested the way PR-5's was (26/28 RED). This
   duplicates ~150 lines of careful logic but keeps `SyncApplySession` closed for modification.
   The D4/D9-T4 amendment precedent (PR-5 had to reach back into PR-1/PR-4 files) shows reaching back
   into PR-5 is not unprecedented, but each such reach should be reported the way that one was
   (`2026-09-10-t2.4-pr5-apply-session.md` §7 table), not silently absorbed.

Either way, this is a **design decision the owner must make**, not one this recon should default.

## 5. Item-by-item answers

### 1) What PR-5 already provides for PR-6, and what is still missing

**FACT** (direct quote, `2026-09-10-t2.4-pr5-apply-session.md:1`): *"PR-6 resolution orchestration was
NOT implemented. No `ConflictResolver`, no KeepLocal/KeepRemote/KeepBase/ManualMerge, no resolution
replay classification, no apply-time drift gate. The only PR-6-adjacent thing shipped is the shared
`SyncBaseFingerprint` primitive."* Confirmed independently: `grep -r "ConflictResolver"` across
production code returns zero hits (§ "Item 9" below has the exact grep). `ResolutionKind` enum values
(`KeepLocal`/`KeepRemote`/`KeepBase`/`ManualMerge`) exist in `MergeOutcomes.cs:19` as **data**, with no
orchestrator that produces or consumes them yet — `SyncConflictRecordStore.MarkResolvedAsync` (`:137-154`)
is the only production code that writes a resolution, and its own doc comment says explicitly it "does
NOT decide whether the resolution is valid... that orchestration is `ConflictResolver` (PR-6, DoR §13),
which this store deliberately does not own."

**What's provided:** the full staging/persistence boundary (§3 table), `SyncBaseFingerprint.Of`/`Matches`
for the drift check, `LocalRowRev` captured at staging time, `SyncConflictRecordStore.MarkResolvedAsync`
as a bare field-setter, and (per §4) several reachable helper types.

**What's missing:** the orchestrator itself, everything private inside `SyncApplySession` that a
resolver would need (§4), and any ratified context-lifetime rule for a resolution path that runs
outside `SyncApplySession`'s transaction loop.

### 2) Where ConflictKey replay can be classified in the current code

**FACT:** two independent replay-interception mechanisms exist today, and they do not fire on the same
inputs:

1. **ConflictKey dedup** — `SyncConflictRecordStore.StageAsync` (`:105-108`) checks `ConflictKey`
   equality first and returns `AlreadyStaged` with the *existing* record, discarding the replay's
   candidate/evidence. Directly tested at the store layer: `L_StageAsync_SameConflictKeyTwice_SecondCallIsNoOp`
   and `L2_ReplayedD4D9T4Candidate_IsRecognizedByConflictKey_IndependentlyOfScopeKey`
   (`SyncConflictRecordStoreTests.cs:401-420`, `439-527`).
2. **ScopeKey lock (D9-T6)** — `SyncApplySession.ApplyEntityAsync` checks
   `SyncConflictRecordStore.FindUnresolvedByScopeKeyAsync` (`SyncApplySession.cs:208-212`) **before**
   any staging call, for every entity-scoped Structural/Constraint operation. For those kinds, a
   replay is intercepted **here**, not at ConflictKey dedup, and the observed outcome is
   `Rejected(ScopeHasUnresolvedConflict)`, never `ConflictAlreadyStaged`.

**FACT — this is documented, not incidental.** `SyncApplySession.cs:446-449` (doc comment on
`StageAbsentLocalStructuralAsync`): *"Replay lands on the D9-T6 scope lock, not on `AlreadyStaged`...
The `AlreadyStaged` branch below is kept because this method must not depend on the caller's check
order to stay idempotent."* `SyncConflictRecordStoreTests.cs:394-398` states the same boundary from the
store's side: *"Resolution-REPLAY idempotency... is PR-6's `ConflictResolver` orchestration, not this
store."*

**INFERENCE for PR-6:** ConflictKey dedup is the operative mechanism only for kinds that never reach a
ScopeKey lock — i.e., the D9-T5 auto-evidence kinds (`Field`/`Tombstone`, entered directly as
`Resolved`), where `StageAutoEvidenceAsync` (`SyncApplySession.cs:522-535`) relies on it plus an
in-memory `HashSet<string> StagedKeys` for within-operation dedup. For Structural/Constraint
(Unresolved) kinds, ConflictKey dedup is real and tested but end-to-end **unreachable through the
apply session** — a PR-6 resolution-replay classifier for those kinds must be built against the
ScopeKey lock's outcome (`Rejected(ScopeHasUnresolvedConflict)`), not against `ConflictAlreadyStaged`.

### 3) Where D9-T6 / ScopeKey uniqueness is enforced, and where PR-6 integrates

Already covered fully in §3 and §4/item 2. **Integration point:** `SyncConflictRecordStore
.FindUnresolvedByScopeKeyAsync` is the read-side of the same invariant PR-6 needs when deciding whether
a resolution attempt is even legal (a resolved record has left the partial index's `WHERE Status = 0`
predicate, so a *second* attempt to resolve it hits the `ResolvedIsTerminal` trigger, not the ScopeKey
index). **The unresolved-scope-lock lookup is `public` and directly reusable.** The apply-side lock
*check* (`SyncApplySession.cs:208`) is private and not reusable as such — but PR-6 does not need it:
PR-6 acts on an already-staged record, and the record's `ScopeKey` column (`SyncConflictRecordRow.cs:44`)
is right there on the row it loaded.

### 4) Where the apply-time drift gate best fits (per the actual code)

**FACT — disambiguating the phrase "apply-time" (two different meanings in the sources):**
- **(a) Sync-apply path** (a peer's changeset arriving via `SyncApplySession`): `ConflictStaging.cs:168-172`
  states explicitly, in a doc comment on the shared drift primitive: *"There is NO apply-time drift
  gate. On the apply path Base comes from the baseline row and Local from the live row, and those are
  *supposed* to differ — that is what a three-way merge is for. Adding a gate here would be inventing
  policy the frozen record does not contain."* This is a stated design boundary, not a gap.
- **(b) Resolution-apply** (a human or auto process resolving an already-staged `ConflictRecord`):
  D8-H (`T2.3-T2.4-D1-D9-Decision-Record-updated.md:750-805`, "Đã chốt: D8-H = B" — Reject) and the
  frozen checklist item *"Live state drift from Base ⇒ reject resolution"* (`:1457`) place the gate
  **here**. `SyncApplySession.cs:46-49` cross-references this directly: *"Resolution orchestration...
  the D8-H drift precondition... is PR-6 / DoR §13"*.

**RECOMMENDATION:** the drift gate belongs in PR-6's `ConflictResolver`, immediately before it commits
a `KeepLocal`/`KeepRemote`/`ManualMerge` result, using `SyncBaseFingerprint.Matches(record.BaseFingerprint,
currentLiveSnapshot)` exactly as `SyncApplyConflictStagingTests.U_StoredBaseFingerprint_DetectsLiveStateDrift`
(`:558-599`) already demonstrates the primitive doing. **Do not** add anything to `SyncApplySession` —
that would cross into modifying semantic authority the frozen record already settled at (a).

### 5) Where SyncBaseFingerprint and LocalRowRev exist; are they sufficient for PR-6?

**FACT — creation:** both are written once, at staging time, inside `ConflictStaging.ToRow`
(`ConflictStaging.cs:60-71`): `BaseFingerprint = candidate.Base is null ? null :
CanonicalJson.Fingerprint(candidate.Base)`; `LocalRowRev = localRowRev` (passed in from the caller —
`localEntity.Rev` for S1/S2, `null` for the D4/D9-T4 absent-local case and for auto-evidence).

**FACT — reads:** `BaseFingerprint` is read by `SyncBaseFingerprint.Matches` (`ConflictStaging.cs:185-186`),
tested end-to-end in `U_StoredBaseFingerprint_DetectsLiveStateDrift`. `LocalRowRev` is read today **only**
by the M5 precondition (`ConflictStaging.cs:146`, "`... || record.LocalRowRev is null` -> throw") — it
gates the audited hard-delete, nothing else.

**FACT — the intended future read is documented, not yet built:** `docs/review/2026-09-08-t2.3-t2.4-engineering-dor.md:785`:
*"write result: existing row ⇒ update fields+tombstone block; absent row ⇒ Add (for S3 KeepLocal: Rev
seeded from `rec.LocalRowRev` before the seam's `++`)"*. **No code today seeds an entity's `Rev` from a
stored `LocalRowRev`** — `SyncStamper.ApplyPreservingProvenance` only ever does `meta.Rev++`
(`SyncStamper.cs:93`), and `EntitySnapshotMapper.ApplyTo` leaves `Rev` untouched by design (`:96`, "Rev
is deliberately untouched"). This is **not a contradiction or a bug** — it is PR-6's own scope, already
named in the engineering DoR as the consumer that will do the seeding. Confirmed by grep: no other
production site references `LocalRowRev` for anything but storage and the M5 guard.

**Answer:** both primitives are **present, immutable-once-staged (DB trigger), and correctly captured
at the moment PR-6 needs them (staging time, before any subsequent drift)** — sufficient as *data*.
The *consuming logic* (drift comparison at resolution time; Rev-continuity seeding on `KeepLocal`) does
not exist yet and is exactly PR-6's job, not a residual gap in PR-5.

### 6) Where R1 is guaranteed or still exposed

Covered in §4. **Guaranteed** inside `SyncApplySession.WriteAsync` only. **Exposed** everywhere else:
`AppDbContext.MarkSyncApplied` is `public`, takes `object`, and is keyed by reference identity with no
tracked-state check (`AppDbContext.cs:56`; rationale for the missing check is in the PR-2 residuals
note, R1, `2026-09-09-...residuals.md:50-57` — a mark-time guard would spuriously reject legitimate
mark-before-`Add()` ordering). Any PR-6 code path that calls `MarkSyncApplied` directly re-opens R1
unless it reproduces `WriteAsync`'s own discipline (resolve the tracked instance; assert not
`Detached`; only then mark).

### 7) Where R2 is handled or still missing

Covered in §4. **Handled** for PR-5's own transaction loop via the ratified per-operation
`AppDbContext` lifetime (`T2.4-PR5-ContextLifetime-Amendment-2026-09-11.md`), measured against real
failure injection (`SyncApplyFailedSaveStateTests.cs`, Case A / Case B, both confirmed — see the PR-5
review §5, reproduced verbatim above). **Missing/unratified** for any PR-6 code path that does not run
inside `SyncApplySession`'s own `BeginTransactionAsync`/dispose cycle — the amendment's own scope line
says "PR-5 only" and "does not apply to any component outside PR-5's sync-apply session." This is a
governance question for the design review (§8, blocker B2), not something this recon can resolve.

### 8) Where residual 12 (ParentTombstoned / KeepRemote) is represented or enforced

**FACT — exact source, verbatim:** `docs/review/2026-09-10-t2.4-pr5-apply-session.md:385` (risk table
row 12): *"**PR-6 must not execute `KeepRemote` on a `ParentTombstoned` record without first resolving
the parent`** | Medium (pre-existing, not PR-5's to fix) | `KeepRemote` would materialise the child
under a still-tombstoned parent — exactly what the amendment says D9-T4 continues to forbid. The hazard
already exists for the S1 record shape; the amendment adds a second shape carrying it, and these notes
are where PR-6's author will look."*

**FACT — mechanism that would need to exist for PR-6 to check this itself:** the only production code
that determines "is the parent still tombstoned" is `SyncApplySession.InspectParentAsync` /
`LoadParentAsync` (`:677-715`), both `private static`. **PR-6 cannot call them.** The record itself
carries enough identity to redo the check (`EntityType` + the structural field encoded in
`ConstraintKey`/`FieldName`, or the parent id embedded in the stored `LocalSnapshotJson`/`BaseSnapshotJson`),
but the FK-to-parent-type mapping (`StageAbsentLocalStructuralAsync`'s `StructuralFieldOf`,
`:786-791`) is also private.

**RECOMMENDATION:** this is not enforced anywhere today (correctly — it is out of PR-5's scope), and it
is not representable by the existing schema/columns as a precondition — it requires a **fresh read of
the current parent row's `IsDeleted`** at resolution time, which is exactly the kind of live-state
check D8-H already requires for the general drift gate (item 4). The design review should decide
whether "parent still live" is folded into the same `SyncBaseFingerprint.Matches` drift check (the
parent's current state is part of what "Base still matches live" would need to mean for a
`ParentTombstoned` record) or is a separate, explicit precondition in `ConflictResolver`. Either way it
needs its own parent-lookup helper, reachable from PR-6 — which does not exist today (§4).

## 7. Blockers / questions for the design review

1. **B1 — extraction vs. re-implementation (§4).** Does PR-6 get a refactored, exported seam from

   context-lifetime discipline? This is the single decision most of the other answers depend on.
2. **B2 — context-lifetime ratification scope (§4, item 7).** Is `ConflictResolver`'s write path
   required to run inside a `SyncApplySession`-style transaction loop (in which case the existing
   amendment already covers it), or can a resolution be triggered from the UI off that path (in which
   case R2 is unratified there and needs its own amendment)?
3. **B3 — residual 12's mechanism (item 8).** Is "parent still live" folded into the D8-H drift check,
   or a separate named precondition? Both need a parent-lookup helper that does not exist yet in a
   PR-6-reachable form.
4. **B4 — governance docs (§1 caveat).** Are `current-code-design-notes.md` / `owner-triage.md` meant
   to be authoritative for PR-6? If so they need to be committed before implementation starts, per the
   pattern the PR-5 review already established for three earlier specs.
5. **B5 — `LocalRowRev` seeding mechanics (item 5).** DoR engineering notes say "Rev seeded from

   `EntitySnapshotMapper` has a hook for "set Rev to X, then still increment," and inventing one is a
   seam change, not something this recon should default.

## Decisions made

### Treating "is X handled" as "is X reachable from PR-6" for items 3/4/6/7/8

*Why it had to be made:* the brief's phrasing ("is R1 guaranteed?", "is R2 handled?") reads naturally
as a yes/no about PR-5's own correctness, which PR-5's own review already answered in the affirmative
for PR-5's scope. Answering only that would tell PR-6's author nothing new and would miss that every
guaranteeing mechanism is `private static` inside a sealed class.
*What it's for:* converts eight separately-phrased questions into one integration decision (§4, B1)
the design review actually needs to make, instead of eight independent "yes, but" answers that bury
the one thing that matters.
*Experience for future development:* when a recon task asks "is invariant X handled" about a
mechanism owned by a different, already-shipped PR, check reachability (`public`/`internal` vs.
`private`, sealed vs. extensible) before answering the invariant question — a correct-but-unreachable
guarantee is not evidence the next consumer inherits it.

### Reporting the GitNexus `includeTests` discrepancy rather than substituting a number

*Why it had to be made:* re-running the same query with `includeTests: false` returned byte-identical
output to the default call, which contradicts the parameter's documented purpose.
*What it's for:* the PR-5 review already established the norm of stating a tool's limitation rather
than working around it silently (its own §9, on the canonical index returning a deleted method); this
note follows the same convention rather than quietly reporting a "cleaned" 35/43 as if it were a
production-only figure I had actually verified.
*Experience for future development:* verify a filter parameter changed the output before reporting
the filtered number — an unchanged result after toggling a flag is itself a finding, not something to
paper over.

### Not proposing a fix for LocalRowRev seeding mechanics (B5) beyond naming the question

*Why it had to be made:* the engineering DoR names the intended behavior ("Rev seeded from
`rec.LocalRowRev` before the seam's `++`") but no code implements the seam hook that would make it
possible without touching `SyncStamper` or `EntitySnapshotMapper` — both PR-5-adjacent, already-merged
files.
*What it's for:* this recon's boundary forbids proposing seam changes as if they were already decided;
naming the open mechanics question (B5) hands it to the design review instead of pre-empting it.
*Experience for future development:* when a spec names an intended data flow but the reading of the
current code shows no hook for it, that is a design-review question, not something to resolve by
inventing the missing hook and reporting it as the answer.
