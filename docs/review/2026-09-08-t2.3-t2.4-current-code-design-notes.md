## B. Stamping-seam anatomy and the candidate apply seams

### B.1 What happens today on every save

```text
caller ──► db.SaveChangesAsync(ct)
              │  (non-virtual wrapper)
              ▼
        AppDbContext.SaveChangesAsync(bool, ct)          Data/AppDbContext.cs:133-137
              │
              ├─► SyncStamper.Apply(ChangeTracker, Clock, DeviceIdProvider())
              │        for every entry (snapshot list):
              │          entity is ISyncMetadata ?
              │            Added/Modified : Rev++ ; ModifiedAtUtc = utcNow() ; ModifiedByDeviceId = deviceId
              │            Deleted        : State=Modified ; Rev++ ; IsDeleted=true ; DeletedAtUtc=utcNow()
              │                             ModifiedAtUtc = utcNow() ; ModifiedByDeviceId = deviceId
              │          else skip (SyncBaseSnapshotRow, telemetry rows)
              ▼
        base.SaveChangesAsync(...)   ← implicit SQLite transaction unless one is already open
```

`utcNow`/`deviceId` are resolved **once per call** and applied to **every** eligible entry. That is
why "temporarily set `db.Clock`/`db.DeviceIdProvider` to the remote values" is wrong by
construction: a genuine local edit tracked in the same context would be stamped as the remote
device.

### B.2 Where a merge-apply write enters the seam today

`SyncChangeEnumerator.GetChangesForPeerAsync(db, peer)` returns `ChangedEntity<T>` whose `Entity`
is the tracked instance loaded from `db`. Any mutation of it followed by `db.SaveChangesAsync()`
lands in B.1 with no marker. `SyncBaseSnapshotStore.SetAsync(db, ...)` also ends with
`db.SaveChangesAsync(ct)`, so calling it while merged rows are still `Modified` in the same
context stamps them as a side effect.

### B.3 Candidate seams that exist in the current code (engineering, not policy)

```text
Option A — per-entry marker honoured by SyncStamper (recommended shape)
   apply code:   entry = db.Entry(row); MarkRemoteApplied(entry, remoteMeta);   // e.g. ChangeTracker annotation / explicit set
   SyncStamper:  if (IsRemoteApplied(entry)) { meta.Rev++; /* keep ModifiedAtUtc/ModifiedByDeviceId/DeletedAtUtc as set */ }
                 else { existing behaviour }
   + Deleted branch: a remote tombstone is applied as IsDeleted=true + remote DeletedAtUtc on a Modified entry, never via Remove()
   + unmarked entries in the same batch keep full local stamping   → the "mixed batch" test
   Collateral: none for existing callers (no marker ⇒ unchanged path). SetAsync self-save is harmless once apply-save has run first.

Option B — dedicated apply method that calls base.SaveChangesAsync
   AppDbContext.ApplyRemoteAsync(...) { /* no SyncStamper.Apply */ return base.SaveChangesAsync(...); }
   Must re-implement Deleted→tombstone conversion (or forbid Remove() on that path), must be the only bypass, must be audited.
   Collateral: two save paths to keep in sync; every future stamping rule must be added twice.

Option C — raw SQL / ExecuteUpdate
   Excluded as a silent shortcut by D9 §20; only acceptable as an audited exception (see C.2 option B for the one place it may be needed).
```

Rev on apply (OPEN-4, engineering): bump local `Rev` on apply (it is a local write and must be
re-offered to *other* peers), then within the same transaction record the **post-apply** `Rev` and
the merged snapshot as the new baseline for the peer the change came from — otherwise the row
re-enumerates to that peer on every round.

## C. The TaskNote constraint scenario, walked through

### C.1 Setup (D5 / D6-B)

```text
Base   (per-peer snapshot for MaTask=T1)  : none              → Base = null
Device A live                             : N1 { Id=n1, MaTask=T1, Content="a" }   (A authored it, Rev=1)
Device B live                             : N2 { Id=n2, MaTask=T1, Content="b" }   (B authored it, Rev=1)
```

Both devices run the same merge when they exchange changesets, so each sees
`Local = own note, Remote = other note` and must derive the **same** `ConflictKey`
(hence the min/max fingerprint ordering in E.3).

### C.2 What "live = Base" (D5-D) means on device A, per option

```text
Option (A) partial unique index  UNIQUE(MaTask) WHERE IsDeleted = 0
   stage:   N1.IsDeleted = true  (via seam)         → Rev 2, enumerated to B as "A deleted n1"  ✗ semantically false signal
   resolve KeepRemote: insert N2 → allowed (partial index)          ✓
   resolve KeepLocal:  N1.IsDeleted = false  → "resurrection", a lifecycle the record does not have   ✗ new semantics
   schema:  DROP INDEX + CREATE UNIQUE INDEX ... WHERE IsDeleted = 0 at startup, EF HasFilter("IsDeleted = 0")

Option (B) audited hard delete of the staged local candidate (recommended for v1 two-peer)
   stage (one transaction):
        INSERT ConflictRecord{ Base=null, Local=N1(full row incl. provenance), Remote=N2, ConstraintScope=(TaskNote, MaTask, T1) }
        DELETE FROM TaskNotes WHERE Id = n1            ← ExecuteDelete, bypasses SyncStamper on purpose, audited
        DELETE SyncBaseSnapshots row for n1 if any (SyncBaseSnapshotStore.DeleteAsync)
   live after stage: no note for T1 = Base                          ✓ D5-D, D6-G, D8-B
   enumeration to B: n1 no longer exists → nothing propagates       ✓ no false delete
   resolve KeepLocal : re-insert N1 with Id=n1 from evidence (Rev restarts at 1 via stamper or seam)   ✓ UNIQUE free
   resolve KeepRemote: insert N2 with Id=n2                                                             ✓
   resolve KeepBase  : nothing (ResultSnapshot = null, D7-G)                                            ✓
   resolve ManualMerge: insert D with explicit Id (E14)                                                 ✓
   cost: one documented exception to "no real DELETE on synced entities"; a third peer that already
         received n1 is not told it vanished (D7-H is OPEN anyway)

Option (C) amend D5-D: authoring device keeps its own candidate live, only the incoming candidate is withheld
   stage: INSERT ConflictRecord only. Live on A = N1, live on B = N2 until resolution.
   resolve KeepRemote on A: tombstone or hard-delete N1 first (UNIQUE) → same mechanism question returns, but later and only once
   cost: rewrites D5-D/D6-G; peers diverge until resolution
```

### C.3 D8-H drift check with `Base = null`

```text
at resolution time on A:
   liveScope = SELECT * FROM TaskNotes WHERE MaTask = T1      (raw DbSet, tombstones included — because UNIQUE counts them)
   compatible ⇔ liveScope is empty                            (Base = null ⇒ "no row of any state in scope")
   otherwise reject (no force, no rebase)
```

### C.4 Structural conflict under D6-G (same un-materialisation shape)

```text
Base: task.MaMonHoc = A ; Local → B ; Remote → C ; B ≠ C   → StructuralConflict, no auto-winner
"live = Base" on the local device ⇒ write task.MaMonHoc = A back
   • that write is local: stamped, Rev++ → enumerated to the peer as "moved back to A"   (spurious reparent)
   • unless the seam writes it without a Rev bump AND the baseline is updated to the reverted state in the same transaction
   • A may itself be tombstoned by now (FK still satisfied, F6-D) → orphan under dead parent unless D9-T4 says otherwise
This is why D9-T1 lists option (D) "never revert the local FK; keep local live, record the conflict" for D4 specifically.
```

## D. Minimum viable `ConflictRecord` shape (proposal for triage, not implemented)

Idiom: standalone table `ConflictRecords`, `Guid` PK, **not** `ISyncMetadata`, created by a raw-SQL
`ConflictRecordSchema.EnsureTable` (+ dual-path test + `AppStartup` call-site guard), no
`DbBackup` (new empty table). Same lineage as `SyncBaseSnapshotRow` and the telemetry rows.

| Column | Type | Forced by | Purpose |
|---|---|---|---|
| `ConflictId` | TEXT PK (Guid) | D7-A | persisted record identity |
| `ConflictKey` | TEXT NOT NULL **UNIQUE** | D7-A/B, D5-G | logical idempotency identity (E.3) |
| `ConflictKind` | INTEGER NOT NULL | D6-C, D9 §14 | Field / Structural / Constraint (+ Tombstone per D9-T5) |
| `EntityType` | TEXT NOT NULL | D6-C | `SyncEntityTypes` value |
| `EntityId` | TEXT NULL | D6-C | present for Field/Structural/Tombstone; null for Constraint |
| `FieldName` | TEXT NULL | D9 §15 | field or relationship name (Field/Structural) |
| `ConstraintKey`, `ConstraintValue` | TEXT NULL | D6-D | e.g. `MaTask`, `T1` |
| `LocalCandidateId`, `RemoteCandidateId` | TEXT NULL | D9 §15 | candidate identities for Constraint conflicts |
| `PeerDeviceId`, `LocalDeviceId` | TEXT NOT NULL | D6-E (provenance) | which exchange produced it |
| `SnapshotContractVersion` | INTEGER NOT NULL | D2 | how to parse the three snapshots |
| `BaseSnapshotJson` | TEXT NULL | D6-B | null allowed |
| `LocalSnapshotJson`, `RemoteSnapshotJson` | TEXT NOT NULL | D6-B/E | full candidate incl. `EntityId` and the five provenance fields (evidence, not merge fields) |
| `BaseFingerprint` | TEXT NULL | D8-H | canonical hash of Base (null ⇒ "no live row in scope") |
| `Status` | INTEGER NOT NULL | D7-D | Unresolved / Resolved |
| `DetectedAtUtc` | TEXT NOT NULL | inferred (audit) | — |
| `ResolutionKind` | INTEGER NULL | D6-H (+ D9-T5 auto kinds) | KeepLocal / KeepRemote / KeepBase / ManualMerge / AutoLww / AutoTombstone |
| `ResultSnapshotJson` | TEXT NULL | D6-H, D7-G | null allowed for KeepBase with Base = null |
| `ResultFingerprint` | TEXT NULL | D7-C | replay no-op check |
| `ResolvedAtUtc`, `ResolvedByDeviceId` | TEXT NULL | inferred (provenance) | — |

**Forced by D1–D9:** identity pair, kind, scope columns, three snapshots with nullable Base,
status, resolution kind/result, immutability of the three snapshots after resolution (enforce in
code: the resolve path updates only `Status`/`Resolution*` columns).
**Inferred from current code:** `SnapshotContractVersion` (D2 versioning meets a TEXT column),
`BaseFingerprint` (D8-H needs a `Rev`-free comparator), `Peer/LocalDeviceId` (symmetric detection
on both devices), `UNIQUE(ConflictKey)` (SQLite gives transaction-safe dedupe for free).
**Optional / future:** `SupersededBy`, `ReopenedAtUtc` (no reopen in v1), propagation columns
(D7-H OPEN), a `Reason` enum for structural conflicts (D4 names are not frozen).

## E. `SnapshotJson` v1 sketch and the canonical key

### E.1 Envelope

```json
{ "v": 1, "entityType": "StudyTask",
  "fields": { "MaMonHoc": "…guid…", "TenTask": "…", "HanChot": "2026-09-08T00:00:00.0000000",
              "TrangThai": "Chưa làm", "LoaiTask": 0, "DoKho": 2, "ThoiGianDaHoc": 0, "NgayHoanThanh": null } }
```

Rules (engineering, all policy-free once the §4 table is ratified): field order = the registry's
declaration order (deterministic ⇒ canonical); `DateTime` written as `yyyy-MM-ddTHH:mm:ss.fffffff`
with **no offset** after `Kind` normalisation; enums as integers; no PK, no `Rev`, no provenance,
no derived or `[NotMapped]` members, no navigation collections. Reader: `v ≠ 1` → throw;
unknown `entityType` → throw; any registered field absent → throw; extra field → throw (fail
closed both ways). A snapshot row whose `SnapshotJson` is `NULL` but `Rev` is set → throw.

Structural fields (`MaHocKy`, `MaMonHoc`) **are** in the snapshot (the three-way structural
compare needs Base), but the registry tags them `Structural` so the merge routes them to D4, not
LWW. The constraint scope field `TaskNote.MaTask` is tagged `ConstraintScope`.

### E.2 Reflection guard (L7)

For each of the six entities: every EF-mapped, non-navigation property must appear either in the
registry (with a treatment tag) or in an explicit exclusion list with a reason string. Adding a
property to `StudyTask` without registering it turns the guard red.

### E.3 `ConflictKey`

```text
fp(x)        = SHA256hex( canonicalJson(x) )           // x = candidate snapshot incl. EntityId + provenance
scope        = EntityType + "|" + (EntityId + "|" + FieldName   |  ConstraintKey + "=" + ConstraintValue)
ConflictKey  = Kind + "|" + scope + "|" + min(fp(local), fp(remote)) + "|" + max(fp(local), fp(remote))
```

Order-independent (min/max), `Rev`-free, GUID-free, stable across retries as long as candidate
state is unchanged (the D9-T6 question is exactly what happens when it is not).

## F. Transaction and drift-check sequences

### F.1 One logical operation (D8-G / D9 §18)

```text
using var db = factory();                       // Sync layer owns the context; no Sqlite*Repository involved
using var tx = await db.Database.BeginTransactionAsync(ct);
   local  = raw DbSet read (tombstones included) → value snapshot
   base   = SyncBaseSnapshotStore.GetAsync(...) → parse (fail closed) or null
   result = Merge.ThreeWay(base, local, remote)          // pure, D1
   switch result:
      merged rows       → apply via seam (B.3 option A), bump Rev
      Field/Tombstone   → ConflictRecords.Add(evidence, Status=Resolved, AutoLww/AutoTombstone)     (D9-T5)
      Structural/Constr → ConflictRecords.Add(Unresolved) ; live stays Base per D9-T1 ruling
   await db.SaveChangesAsync(ct)                 // seam-aware stamping
   await SyncBaseSnapshotStore.SetAsync(db, peer, type, id, postApplyRev, mergedSnapshotJson, now, ct)
await tx.CommitAsync(ct);                       // failure anywhere → rollback of this operation only
```

Independent operations in one changeset = independent `tx` blocks; a parent tombstone and its
cascade children share one block (`TaskCascadeHelper` + EF fixup inside it). SQLite's single
writer makes a concurrent UI `LuuHocKyAsync` wait rather than interleave.

### F.2 Resolution (D8-E / D8-H)

```text
using var tx = ...
   rec = ConflictRecords.Single(ConflictId)
   if rec.Status == Resolved: return rec.ResolutionKind == req.Kind && rec.ResultFingerprint == fp(req.Result) ? NoOp : Reject
   live = raw read of scope (tombstones included)
   if fp(live merge-surface) != rec.BaseFingerprint (or live non-empty when BaseFingerprint == null): Reject   // D8-H, no force, no rebase
   apply req.Result via seam (insert/update/none) ; rec.Status = Resolved ; rec.Resolution* = ... ; snapshots untouched   // D7-F
   await SaveChangesAsync ; SetAsync baseline for the result row
await tx.CommitAsync()
```

## I. How the six entities reach the merge as value snapshots (D1)

```text
SyncChangeEnumerator (T2.2) ──► ChangedEntity<T>{ EntityId, Entity (TRACKED), Rev, IsDeleted }
                                                   │
                                                   ▼  project (never pass tracked instances into the core)
                                          EntitySnapshot { EntityType, EntityId, Fields[registry order], Provenance{ModifiedAtUtc(ticks), ModifiedByDeviceId, IsDeleted, DeletedAtUtc} }
Base  ← SyncBaseSnapshotRow.SnapshotJson (parse, fail closed) or null
Local ← raw DbSet row → EntitySnapshot
Remote← peer's row → EntitySnapshot
                                                   │
                                                   ▼
        Merge.ThreeWay(base, local, remote) → MergedSnapshot (per-field outcome: Base / Local / Remote / Common / LwwLocal / LwwRemote / Structural / Constraint)
                                            + ConflictCandidate[] (immutable records)
```

Navigation collections (`HocKy.DanhSachMonHoc`, `MonHoc.DanhSachTask`) never enter the snapshot;
child adds/removes are separate rows of their own entity type. `[NotMapped]` members of `HocKy`
are recomputed by the UI from `NgayBatDau` and are outside the contract. Provenance travels next
to, not inside, `Fields`, so a generic diff cannot mistake `Rev` or `ModifiedAtUtc` for data and
`StudyLog.DeviceId` (a business/creation field) cannot be confused with `ModifiedByDeviceId` by
name.
