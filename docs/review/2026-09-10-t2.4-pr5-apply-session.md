## 2. Architecture and transaction boundary

```
ApplyAsync(IncomingChangeSet)
  plan (§12.5)           phase 1: parent tombstones HocKy -> MonHoc -> StudyTask
                         phase 2: creates/updates HocKy -> MonHoc -> StudyTask
                                  -> {StudyLog, TaskNote scopes, TaskReferenceLink}
                         phase 3: one retry pass for deferred MissingParent
  for each operation:
      db = factory()                       <- ONE context per logical operation
      await using tx = BeginTransaction()
          load Base (baseline row)          fail closed if unreadable
          load Local (raw DbSet, AsNoTracking)
          ThreeWayMerge / ConstraintMerge   (pure)
          scope-lock check (D9-T6)
          parent check (D9-T4 / A2-a)
          apply result  OR  stage conflict  OR  reject
          SaveChanges                       <- save #1, Rev++ on marked entries
          baseline Upsert (POST-apply Rev)
          SaveChanges                       <- save #2, same transaction
      commit (or rollback)
      db.DisposeAsync()                     <- context lifetime ends, every path
```

No repository is used anywhere in the session: every repository creates its own `AppDbContext` from a
factory and therefore cannot join the caller's transaction. The session reads and writes raw DbSets
only, which is also what keeps tombstones visible.

### Context lifetime — the residuals-note OPEN, resolved

`docs/review/2026-09-09-t2.4-pr5-pr2-residuals.md` (R2, "OPEN") records that DoR §12.1's written
mechanism — one context for the whole run — cannot coexist with "dispose the failed context", and
requires PR-5 to have the owner ratify one shape before implementing.

**Ratified by the PR-5 brief, per-operation context.** Verbatim from the brief: the apply session
"should own: one DbContext; one logical sync-operation transaction"; "After a failure: context
lifetime ends"; the transaction sketch opens with `using var db = CreateDbContext();`; and R2's
instruction is "dispose the context; retry must use a fresh DbContext". Run-scoped ownership is
incoherent with that last clause, because disposing on failure would end the whole run while §12.1
also says "continue with next op". The `[FROZEN]` tag on §12.1 is on its *unit* claim (one logical
operation = one transaction), which is preserved exactly; context lifetime appears in neither D1–D9
nor D9-T1..T6.

Consequence designed for: "use the operation's intended final state for a parent in the SAME logical
operation" now scopes within one operation only. Across operations, §12.5 ordering plus committed
state does the work — there is deliberately no cross-operation in-memory "intended state" map, which
would span disposed contexts.

## 3. Entity apply order, tombstones, parent handling

**Order.** Phase 1 tombstones the three parent-owning types top-down so §12.2's parent check in phase
2 evaluates against committed state. Phase 2 applies everything else top-down; `TaskNote` is planned
as a whole uniqueness scope, never as a bare row. Phase 3 retries deferred `MissingParent` once, so a
child whose parent arrives in the same change set is applied rather than falsely rejected (tested with
the child listed *before* its parent).

**Tombstones.** A winning tombstone is an ordinary tracked update: `IsDeleted = true`, plus
`DeletedAtUtc` / `ModifiedAtUtc` / `ModifiedByDeviceId` from the winning provenance, then
`MarkSyncApplied`. `Remove()` is never called and `EntityState.Deleted` is never set, so the row stays
physically present (asserted).

**Parent handling.**

| Reference | Parent live | Parent tombstoned | Parent missing |
|---|---|---|---|
| `MonHoc.MaHocKy`, `StudyTask.MaMonHoc` (D4) | apply | `StructuralConflict(ParentTombstoned)`, live = Base; **no local row ⇒ not materialised, staged with an absent local candidate** (§7) | deferred, then `Rejected(MissingParent)` |
| `TaskNote.MaTask`, `TaskReferenceLink.MaTask` (FK-only) | apply | **cascade tombstone** with parent provenance (ACK A2-a) | deferred, then `Rejected(MissingParent)` |
| `StudyLog.MaTask` (no FK) | apply | apply as-is, **no evidence** | deferred, then `Rejected(MissingParent)` |

**Cascade edges are exactly the four the model already has** — `HocKy→MonHoc`, `MonHoc→StudyTask`
(`OnDelete(Cascade)`) and `StudyTask→{TaskNote, TaskReferenceLink}` (`TaskCascadeHelper`). `StudyLog`
is deliberately excluded: no FK, and Epic-1's cascade never touched logs. Children are located by FK
through raw DbSet queries, never `Include` — EF fixup only reaches already-loaded children, which is
the documented Epic-1 gap. The **originating** tombstone's provenance is propagated unchanged down the
whole cascade (ACK A2-b), so both peers write identical bytes for one causal deletion. Cascade only
fires on the live→dead transition, so a replay does not re-stamp descendants.

## 4. TaskNote null-Base staging (M5) and conflict staging

**S3 (Base = null, Local = N1, Remote = N2, same MaTask, different Ids).** Evidence is staged, saved,
and only then is N1 physically removed through the single audited site
`ConflictStaging.HardDeleteWithdrawnTaskNoteAsync`.

**Ordering choice, stated because T-5 does not discriminate it.** `Add record → SaveChanges → DELETE`
rather than `Add → DELETE → SaveChanges`. Raw SQL executes immediately against the connection while an
EF `Add` only materialises at `SaveChanges`, so the second order would put the physical delete on the
wire *before* the evidence. Both orders are inside the one transaction and roll back together, so
neither loses data on a crash — but only the chosen order makes the method's precondition ("the
evidence row is persisted") checkable at delete time, and only it keeps the invariant true at every
instant the connection is observable.

Preconditions are enforced, not documented: inside a transaction, TaskNote only, constraint-conflict
record only, `LocalWithdrawal = HardDeleted`, record `Unchanged` (i.e. already saved), `Id` matches
`LocalEntityId`, snapshot and `LocalRowRev` present, and the target row not tracked.

**The destructive direction, tested separately.** `J_WhenStagingIsRejected_TheLocalCandidateIsNotDeleted`
rejects at `StageAsync`, i.e. *before* the delete is reached, so it proves "reject ⇒ no delete" — and
DoR §17 T-5 is worded the same way ("fail the record insert ⇒ N1 still present"). That is not the
direction in which data is lost. `J_TheAuditedHardDelete_EnlistsInTheTransaction_SoRollbackRestoresTheRow`
covers the other one: if the raw `DELETE` did not enlist in the ambient transaction, N1 would be
physically gone while the ConflictRecord holding its only recoverable copy rolled back — the one
invariant in PR-5 that fails destructively rather than closed, and the thing the entire A1 approval
assumes cannot happen. The row is asserted gone *inside* the transaction first (so the test cannot pass
vacuously) and present again after the rollback. Sensitivity demonstrated by replacing the rollback with
a commit: `Assert.NotNull() Failure: Value is null`.

**Audit fence.** `SyncApplyAuditFenceTests` scans the production project directory *by exact name*
(`SmartStudyPlanner`, not a prefix — `SmartStudyPlanner.Tests` contains the same literal in its own
trigger tests and would make the fence self-failing or vacuous) and asserts exactly one physical-delete
site, inside the named method. Red-capable: verified (§6, mutation `fence`).

**Other staging shapes.** S1/S2 rewrite the local row to the **whole** Base row, not just the
conflicting field — "live = Base" read literally. `AutoLww` / `AutoTombstone` evidence is written
directly as `Status = Resolved` and deduped by `ConflictKey` within the operation, because PR-4's
`StageAsync` check is a DB query and cannot see rows added to the tracker earlier in the same unit of
work. `LocalRowRev` is stored at staging for PR-6's KeepLocal Rev continuity.

## 5. Baseline semantics and R1/R2

**Baseline.** Written after save #1, reading `Rev` off the tracked instance, so it is always the
POST-apply value; the pre-apply value would leave `row.Rev > baseline.Rev`, which is exactly
`SyncChangeEnumerator`'s predicate, and the row would be re-emitted to that peer forever. Per DoR
§11.2: applied ⇒ `(Rev_post, canonical(merged))`; no-op ⇒ `(Rev_current, canonical(current))` only if
the baseline was missing or behind, else untouched; structural staging ⇒ `(Rev_post, canonical(Base))`;
S3 hard delete ⇒ nothing written; rejected ⇒ nothing (rolled back).

Baselines are also written for cascade children. §12.1 includes "its baseline rows" (plural) in the
operation, and without them §11.2's own no-re-emission property would not hold for the child
tombstones. Recorded as an engineering consequence, not a semantic change.

**R1 — closed by construction, not discipline.** Every write goes through one private `WriteAsync`
that resolves the *tracked* instance, asserts it is not `Detached`, and only then marks. The merge
always reads `AsNoTracking` and those instances are never marked. `DbSet.Update(detachedPoco)` appears
nowhere — that is precisely the PR-A defect shape.

**R2 — reproduced first, then made structurally impossible.** The residuals note labelled both cases
inference and required measurement before design. Both are now measured
(`SyncApplyFailedSaveStateTests`):

- **Case A confirmed.** A valid marked entry validated before an invalid one has already taken its
  in-memory `Rev++` when `SyncStamper.Apply` throws. The intent map is cleared in the `finally`, so the
  still-`Modified` instance reaches the next ordinary save **unmarked** and is committed with a second
  `Rev` bump *and local provenance* — measured: `Rev` 1 → 2 (failed) → 3, `ModifiedByDeviceId` =
  LOCAL-DEVICE, not the remote it was meant to preserve.
- **Case B confirmed.** With two saves in one transaction, a failure on the second leaves the instance
  `Unchanged` and ahead of the rolled-back database, and EF identity resolution hands that same stale
  instance back to a later read on the context (`Assert.Same` holds).

Per-operation context lifetime makes both unreachable for a subsequent operation: the object that held
the dirty or stale-but-clean state no longer exists. No in-memory `Rev` rollback was added to
`SyncStamper` — the residuals note's instruction, and the measurement shows context recreation is
sufficient.

## 7. D4 / D9-T4 amendment — pure create under a tombstoned structural parent (RESOLVED)

PR-5 first shipped this case as a **semantic blocker**: D9-T4 demands a `StructuralConflict`, but for a
remote pure *create* there is no Base and no local row, so there is no competing local candidate — while
`ConflictCandidate.Local` and `SyncConflictRecords.LocalSnapshotJson` were both non-nullable. Staging
would have meant writing a local candidate that never existed into an append-only, immutable evidence
table (D7-F). PR-5 therefore kept the invariant that matters (the child is not materialised), rejected,
and escalated instead of inventing a representation.

**The owner ruled on 2026-09-10.** The ruling is recorded verbatim, with its full consequences, in
`docs/specs/T2.3-T2.4-D4-D9-T4-Amendment-2026-09-10.md` — a new dated spec file; the frozen Decision
Record is not edited. In short: the operation MUST resolve as `StructuralConflict`, the child MUST NOT be
materialised, `Local`/`LocalSnapshotJson` MUST be absent, absence MUST NOT be represented by a fabricated
placeholder, and the record is subject to the existing D9-T6 scope-lock semantics.

### What changed, and why each slice had to be touched

This is the one part of PR-5 that modifies already-merged slices. It is reported rather than quietly
absorbed — the brief's "report rather than silently broaden" applies to *silent* broadening, and the
change is authorised in substance by the ruling itself.

| Slice | File | Why it was unavoidable |
|---|---|---|
| PR-1 | `Sync/Merge/MergeOutcomes.cs` | `ConflictCandidate.Local`/`LocalEntityId` → nullable. The ruling names this type directly. Source-compatible: the core's only producer (`ThreeWayMerge.cs:164`) passes non-null. |
| PR-1 | `Sync/Merge/ConflictKeys.cs` | A `ConflictKey` must still be computable and deterministic with no local candidate, and half-absent evidence must fail closed. Adds the `AbsentCandidate` sentinel + two contract guards. |
| PR-4 | `Sync/SyncConflictRecordRow.cs` | The three local-candidate columns → nullable. |
| PR-4 | `Data/SyncConflictRecordSchema.cs` | `NOT NULL` cannot express "absent only for a StructuralConflict". Replaced by `CK_SyncConflictRecords_LocalCandidate`, plus a transactional table rebuild because SQLite can neither drop a `NOT NULL` nor add a CHECK in place. |
| PR-4 | `Data/AppDbContext.cs` | The same CHECK on the EF creation path, or the two paths diverge and "fails closed" would hold on only one kind of database. |
| PR-5 | `Sync/Apply/ConflictStaging.cs` | Map an absent candidate to absent columns — never to the remote row. |
| PR-5 | `Sync/Apply/SyncApplySession.cs` | A dedicated staging path (see below) and a renamed typed rejection for the remaining sub-case. |

**Why a dedicated path, not a reuse of `StageStructuralAsync`.** That method is D9-T1 shape S1, and it
already guards the no-local-row case: `if (baseSnapshot is null || localEntity is null) return
Rejected(StructuralConflictWithoutBase);` — routing the absent-local case through it would not throw.
Mutation 17 (route it back through S1) is still **RED**, but for a different reason than a crash: the
guard fires first, so the test — which asserts `ConflictStaged` — instead observes `Rejected`, and the
mutation is caught. The mutation result and the split's correctness both stand: `StageStructuralAsync`
rewrites the local row to Base and never stages a no-local-candidate conflict, so reusing it can only
ever reject the pure-create case, not service it. `StageAbsentLocalStructuralAsync` stages the evidence,
saves once, and writes nothing else — that remains the correct, and only, path that honours the ruling.
No production code change follows from this correction; it fixes the causal narrative only.

**No baseline is written.** Nothing reaches `st.Written`, and a baseline records what was *applied*
(DoR §11.2); one here would tell `SyncChangeEnumerator` that a row we never materialised is in sync. The
test asserts its absence so a later refactor cannot add one silently.

**Replay is stopped by the scope lock, not by dedup.** For an entity operation the scope-lock key IS the
staged record's `ScopeKey`, and `ApplyEntityAsync` checks it before parent inspection — so a re-offered
create yields `Rejected(ScopeHasUnresolvedConflict)`, never `ConflictAlreadyStaged`. Both replay shapes
are tested (remote unchanged, same `ConflictKey`; remote edited, new `ConflictKey` in the same scope) and
both converge on: one record, unchanged evidence, no child row. Stated explicitly because the outcome is
observable and would otherwise read as a bug.

**The `ConflictKey` symmetry rationale does not apply here, and that is fine.** D5-G/D7-B's mirroring
argument assumes both peers see mirrored Local/Remote input; this case is asymmetric by construction (one
peer has the row, the other has a tombstoned parent and no row). What the replay path actually needs is
determinism, which is preserved and tested.

### Residual, still rejected

A local row that exists **with no Base** under a tombstoned structural parent is a different case: there
*is* a competing local candidate, so absence cannot represent it, but "hold the local row at Base" has no
Base, and no audited withdrawal mechanism exists outside M5's TaskNote scope. It fails closed as
`Rejected(ParentTombstonedLocalRowWithoutBase)` — renamed from `ParentTombstonedNoLocalRow`, which now
describes the opposite of what it used to. Believed unreachable (phase-1 parent tombstones cascade before
phase-2 children are applied, so the local child is already a tombstone), and no test constructs it.

Related, handled the same way and also unreachable by construction:
`Rejected(StructuralConflictWithoutBase)` for a ConcurrentReparent with a null Base — two devices cannot
independently mint the same Guid, and no audited withdrawal mechanism exists for anything but a TaskNote,
so it fails closed rather than inventing one.
