## 7. Conflict / resolution state transitions

### 7.1 Record lifecycle (FACT + frozen)

```text
                 staging (PR-5)                                resolution (PR-6)
candidate ──┬─ AutoResolution != null ──► Resolved(AutoLww|AutoTombstone) ── any request ──► Rejected(NotResolvable)
            └─ AutoResolution == null ──► Unresolved ──┬─ drift ─────────────────────────► Rejected(LiveStateDrift), stays Unresolved
                                                        ├─ result check fails ─────────────► Rejected(<reason>), stays Unresolved
                                                        └─ KeepLocal|KeepRemote|KeepBase|ManualMerge ──► Resolved
Resolved(human) ── same (Kind, ResultEntityId, ResultFingerprint) ──► NoOpReplay (writes nothing)
                └─ anything else ────────────────────────────────────► Rejected(MismatchedReplay)
```

### 7.2 Classification order inside one call (RECOMMENDATION for the order, which is load-bearing; the outcomes of steps 5, 7 and 8 marked B-n are owner rulings)

| Step | Check | Outcome on failure | Why here |
|---|---|---|---|
| 0 | request shape: `Kind ∈ {KeepLocal, KeepRemote, KeepBase, ManualMerge}`; ManualMerge carries result + id; others carry neither | `Rejected(InvalidRequest)` | `ResolutionKind` includes the auto kinds (`MergeOutcomes.cs:19`); a caller must not be able to request one |
| 1 | load by `ConflictId` | `Rejected(UnknownConflict)` | D7-A: `ConflictId` is the addressing identity |
| 2 | record is auto (`ResolutionKind ∈ {AutoLww, AutoTombstone}`) | `Rejected(NotResolvable)` | **before** replay: D9-T5 forbids re-resolution even for a request that "matches" |
| 3 | record `Resolved` → compare request identity | `NoOpReplay` / `Rejected(MismatchedReplay)` | **before** drift: a legitimate replay after the row has since moved on must still be `NoOpReplay`, not `LiveStateDrift` (tested, §13 Z-R1) |
| 4 | Unresolved record has `Kind ∈ {Structural, Constraint}` | `Rejected(ContractViolation)` | §2: nothing else can be Unresolved |
| 5 | kind applicable to shape: `KeepLocal` requires a local candidate (AL-PT has none) | `Rejected(KindNotApplicable)`, never reinterpreted as a null result | **B-4, owner ruling.** Keying the check on "local candidate absent" instead of on AL-PT by name is E-11 |

## 8. Transaction, context, R1, R2, Rev

### 8.1 Context lifetime — B-1, owner ruling (blocking in rev 1, closed in rev 2)

- **FACT.** DoR §13.1 says "one transaction per call" and is silent on context ownership.
- **FACT.** The Option A amendment is explicitly PR-5-only: *"It does not apply to any component
  outside PR-5's sync-apply session"* (`T2.4-PR5-ContextLifetime-Amendment-2026-09-11.md`, §"Relationship
  to DoR §12.1"). That is why rev 1 found PR-6 had no ratified context lifetime. The amendment is
  still PR-5-only; B-1 is a separate ruling, not a widening of it.
- **OWNER RULING (B-1, 2026-09-11).** Each `ResolveAsync` operation owns exactly one `AppDbContext`.
  The context is disposed on every success and failure path. A failed operation must not reuse the
  failed context. A retry is a new `ResolveAsync` call with a fresh context.
- **INFERENCE — the resolver's R2 exposure is narrower than PR-5's, but not zero.** The resolver never
  marks, so `SyncStamper` cannot throw on its entries (the throw is only on the marked path,
  `SyncStamper.cs:80-94`). The remaining shape is: the ordinary path has already done `Rev++` and
  written `ModifiedAtUtc`/`ModifiedByDeviceId` in memory (`SyncStamper.cs:54-59`), then
  `base.SaveChangesAsync` fails (trigger ABORT on a racing resolve, UNIQUE(MaTask), CHECK, FK). The
  context is left holding a stamped, dirty instance ahead of the database — R2 Case A's state, reached
  by a different trigger. The resolver has one save, so R2 Case B (two saves) does not arise.
  The ruling makes that failure state unreachable across calls by construction.
- **RECOMMENDATION (implementing B-1).** `ConflictResolver` takes the composition-root
  `Func<AppDbContext>`, preserving `DeviceIdProvider` identity exactly as PR-5 does. It holds the
  context with `await using` inside `ResolveAsync` and never stores it in a field. A retry re-reads
  the record, so it correctly classifies as `NoOpReplay` if the earlier attempt actually committed.
  Acceptance: Z-L1 and Z-R3 (§13).

### 8.2 R1 and the seam — the resolver does not mark

- **FACT.** ACK A2-c (DoR §13.4, frozen by the 2026-09-08 amendment): the result is written as an
  ordinary local write, `SyncStamper` stamps `ModifiedAtUtc = now`, `ModifiedByDeviceId = this device`,
  `Rev++`. `SyncApplySession.WriteAsync` marks unconditionally (`SyncApplySession.cs:566`) and is
  therefore **not reusable** by the resolver.
- **RECOMMENDATION.** R1 becomes a *negative* invariant for PR-6: **zero** `MarkSyncApplied` calls in the
  resolver. The resolver keeps R1's *positive* half anyway — it writes onto the tracked instance
  (`LoadTrackedAsync`-style raw-DbSet query), never onto the `AsNoTracking` drift snapshot, and never
  via `DbSet.Update(detached)` (the PR-A defect shape). The write helper should assert
  `Entry(entity).State != Detached` before save for the same reason PR-5's does.
- **INFERENCE.** Provenance on the written row: `ApplyTo` copies the snapshot's provenance block
  (`EntitySnapshotMapper.cs:220-226`), then the ordinary stamper overwrites `ModifiedAtUtc` and
  `ModifiedByDeviceId` but **not** `IsDeleted`/`DeletedAtUtc` (`SyncStamper.cs:54-59`). A tombstone
  result therefore keeps the candidate's `DeletedAtUtc` and gets a local `ModifiedAtUtc` — valid
  provenance (§11.4).

### 8.3 Rev (engineering; D9 §21 delegates it)

| Write | Rev after | Label |
|---|---|---|
| update of an existing row (S1-CR, S1-PT, S2 same-Id) | `Rev_live + 1` (ordinary Modified path) | FACT |
| KeepBase with Base present | unchanged (entry stays `Unchanged`; stamper visits only Added/Modified, `SyncStamper.cs:54`) | FACT for the stamper; INFERENCE for EF's no-change detection (the same property PR-5 residual 8 relies on) |
| S3 re-insert of `LocalEntityId` (KeepLocal, or ManualMerge choosing `N1`) | seed `Rev = LocalRowRev` before `Add`; stamper's Added path ⇒ `LocalRowRev + 1` | RECOMMENDATION (E-2) |
| insert of an Id new to this device (S3 KeepRemote `N2`, fresh ManualMerge id, AL-PT ManualMerge) | 1 | FACT |

**Why E-2 covers ManualMerge-with-`N1`, not only KeepLocal (INFERENCE).** DoR §13.2 seeds only for
KeepLocal. But `SyncBaseSnapshots` rows for `N1` held for *other* peers survive the M5 delete (DoR §9.1
M5 row). `SyncChangeEnumerator` emits `row.Rev > snapshot.Rev` (`SyncChangeEnumerator.cs:30`). Any
re-insert of `N1` at `Rev = 1` would sit at or below those baselines and never be emitted to those
peers. The rule is about the *identity* being re-materialised, not the resolution kind.

### 8.4 Rollback rule R2 applied

On any exception: roll back (explicitly, and by `await using` disposal — PR-5 mutation #14 measured that
disposal alone is sufficient), dispose, return `Failed`. On a typed rejection: roll back, dispose,
return `Rejected`. The record stays `Unresolved`; nothing partial is visible because the domain write
and the record update share one save (I-4).

## 9. Replay behaviour

### 9.1 Resolution replay (the resolver's own idempotency)

- **FACT.** DoR §8.4: identity of a resolution = `(ResolutionKind, ResultFingerprint, ResultEntityId)`.
- **INFERENCE — the stored result must be the requested/selected result, pre-stamp.** Under A2-c the
  persisted row carries `Clock()` provenance. If `ResultSnapshotJson`/`ResultFingerprint` were the
  post-stamp row, a replayed request could never recompute them, and every replay would classify as
  `MismatchedReplay` — violating D7-C. **RECOMMENDATION (E-1):** store `canonical(selected result)`
  exactly as chosen (KeepLocal ⇒ `rec.LocalSnapshotJson`, KeepRemote ⇒ `rec.RemoteSnapshotJson`,
  KeepBase ⇒ `rec.BaseSnapshotJson` or null, ManualMerge ⇒ `canonical(req.ManualResult)`), and state in
  the code that the live row's provenance intentionally differs (A2-c).
- `ResultEntityId`: KeepLocal ⇒ `LocalEntityId`; KeepRemote ⇒ `RemoteEntityId`; KeepBase ⇒
  `BaseEntityId` (null when Base is null); ManualMerge ⇒ request id.
- `NoOpReplay` writes nothing: no domain change, no `ResolvedAtUtc` update (the terminal trigger would
  abort one anyway).
- **A rejected request leaves no trace on the record (INFERENCE, from I-4 and §8.4).** Repeating it is
  not a replay: it is classified again from step 0. Once a record is `Resolved`, step 3 runs before
  steps 5–8. A request that B-2, B-3 or B-4 would reject against an `Unresolved` record therefore
  classifies as `MismatchedReplay` against a `Resolved` one. Example: `KeepLocal` on an AL-PT record
  that was resolved by `KeepBase(null)`. None of the rev 2 rulings changes the replay identity (E-1).

### 9.2 Roles of the three identities in PR-6

| Identity | PR-6 use | Not used for |
|---|---|---|
| `ConflictId` | addressing the record (`GetAsync`) | replay (D7-A: never interchanged) |
| `ScopeKey` | drift-gate scope; scope-lock check on the result with this record excluded; freed on `Resolved` (partial index) | identity of the resolution |
| `ConflictKey` | **not read by the resolver.** It matters *after* resolution, on the sync path (§9.3) | resolution replay |

### 9.3 Sync replay after a resolution (FACT from code paths; INFERENCE where noted)

- **Same candidate re-offered after resolution collapses on `ConflictKey`.** Example AL-PT resolved
  with KeepBase(null): the same remote create arrives again ⇒ no local row, no lock (record now
  Resolved) ⇒ parent still tombstoned ⇒ `StageAbsentLocalStructuralAsync` ⇒ `StageAsync` finds the same
  `ConflictKey` (any status) ⇒ `ConflictAlreadyStaged`; nothing materialised
  (`SyncConflictRecordStore.cs:105-108`; `SyncApplySession.cs:459-463`).
- **Edited candidate after resolution creates a new Unresolved record** in the same scope (allowed:
  DoR §8.4 row 3, prior record Resolved).
- **Durability of a resolution against the peer's still-live state (INFERENCE, §15.3 W-3).** In the
  common asymmetric case the device that receives first stages, holds live at Base, and writes the
  peer baseline as `(Rev_post, canonical(Base))` (`SyncApplySession.cs:368-371`), so it never emits its
  withdrawn local candidate to the peer. The peer keeps its competing state live and keeps offering it
  (its `row.Rev` exceeds its baseline for us). After **KeepBase**, the lock is gone and the next pull
  applies the peer's state as an ordinary one-sided change — the human KeepBase is overridden on the
  same device. After **KeepLocal**, the locally stamped row is emitted to the peer, which stages its own
  conflict (DoR §13.6). After **KeepRemote**, both converge. This is a sharper, single-device statement
  of DoR §13.6 / OPEN-2; PR-6 must not solve it (no propagation, no baseline advance — §14).

**FACT — the positive leg is partly measured in-tree.** `U_StoredBaseFingerprint_DetectsLiveStateDrift`

### 10.2 There is no drift gate on the sync-apply path — and PR-6 must not add one

**FACT.** `ConflictStaging.cs:168-172`: *"There is NO apply-time drift gate. On the apply path Base comes
from the baseline row and Local from the live row, and those are supposed to differ … Adding a gate here
would be inventing policy the frozen record does not contain."* The brief's "apply-time drift gate" is
read here as the gate at the time a **resolution** is applied (DoR §13.2), which is the only drift gate
the frozen record contains.

### 10.3 Finding F-1 — a drifted record can never be resolved (High; §15.3 W-1)

The legs, labelled separately:

| Leg | Evidence |
|---|---|
| An ordinary local edit to a row held at Base changes its fingerprint | **measured**, `SyncApplyConflictStagingTests.cs:585-594` |

## 11. Parent tombstone and cascade-tombstone behaviour

### 11.1 Residual 12, generalised

- **FACT.** PR-5 §8 row 12: *"PR-6 must not execute `KeepRemote` on a `ParentTombstoned` record without
  first resolving the parent."*
- **FACT.** In v1 a tombstoned parent can never become live again: no resurrection path exists (DoR §19),
  and the merge core fails closed on a live side over a dead Base (`ThreeWayMerge.cs:45-53`).
- **INFERENCE.** "Until the parent is resolved" therefore means "never" in v1: KeepRemote on an AL-PT or
  S1-PT record whose Remote points at a still-tombstoned parent is **permanently** invalid, not deferred.
- **INFERENCE — Residual 12 is one instance of a general rule.** DoR §13.2 already requires a "parent
  check (§12.2) … on the result". Any result — KeepLocal, KeepRemote, KeepBase, ManualMerge — whose
  structural parent (MonHoc.MaHocKy, StudyTask.MaMonHoc) or FK parent (TaskNote.MaTask) is tombstoned or
  missing *at resolution time* would create what D9-T4 / A2-a forbid. The parent may also have been
  tombstoned **after** staging (e.g. S3 note, then its task is tombstoned by a later sync: the scope is
  empty, so the drift gate passes, and KeepLocal/KeepRemote would insert a live note under a dead task).
- **FACT — the gap that made this blocking in rev 1.** §12.2's outcomes are apply-time actions (stage a
  StructuralConflict; cascade-tombstone the child). At resolution time the record *is* the conflict, so
  "stage a StructuralConflict" is incoherent and "cascade-tombstone" silently changes the requested
  result. The typed outcome was unspecified, which became **B-2**.
- **OWNER RULING (B-2, 2026-09-11): Option A, with KeepBase subcase (i) exempt.**
  - Reject resolution if the requested materialised result would have a tombstoned or missing
    structural parent. The ConflictRecord stays `Unresolved` and nothing is written.
  - `KeepBase` is exempt when it produces no domain write. A `KeepBase` path that would actually
    write is checked like any other kind.
  - A requested result is **not** materialised merely to satisfy FK-only children.
  - The typed reasons `ResultParentTombstoned` and `ResultParentMissing` are engineering names.
- **INFERENCE — the FK parent is covered by derivation, not by the ruling's wording.** The ruling's
  first sentence says *structural* parent. Take a TaskNote result whose task, an FK-only parent, is
  tombstoned. Materialising it live is forbidden by frozen ACK A2-a (I-9). Materialising it as a
  tombstone is forbidden by the ruling's last sentence, which rejects rev 1's option (b). Rejection is
  the only outcome left, so the resolver applies the same check and the same typed reasons to
  `TaskNote.MaTask`. Z-PT2 pins this.
- **RECOMMENDATION (E-12) — key the exemption on the write plan, not on the kind.** The parent check
  is skipped only when the derived write plan is empty. It is not skipped whenever
  `Kind == KeepBase`. Under E-5 and the drift gate, no reachable input makes `KeepBase` write: with
  Base present, live equals Base, so no field changes; with Base null, there is nothing to write. The
  ruling's "would actually write" clause is therefore a **structural guard with no discriminating
  test**: no reachable input can tell "exempt by kind" apart from "exempt by empty plan". This is
  stated here rather than covered by a test that cannot go red. If the owner ever overrides E-5 and
  `KeepBase` starts forcing `Modified`, the clause becomes live, and this keying applies the check
  with no further change.
- **RECOMMENDATION (E-13) — a result that is itself a tombstone is checked too.** The ruling covers
  "the requested materialized result". It does not exempt a result that is itself a tombstone, for
  example S3 `KeepRemote` of a tombstoned `N2` whose task has since been tombstoned. The literal
  reading is to reject. That fails closed, and `KeepBase(null)` still frees the scope. The owner may
  override.
- **FACT — the test-M shape.** Test M's S1-PT shape (`SyncApplyParentHandlingTests.cs:112-141`)
  tombstones the parent locally without reaching the child, which is the documented Epic-1 gap. So
  Base, Local and Remote all point at the same tombstoned MonHoc, and the row held live at Base is
  *already* a live child under a tombstoned parent.
  - Under B-2, `KeepLocal` and `KeepRemote` are rejected there.
  - `KeepBase` is **accepted**, because it writes nothing (B-2 (i)).
  - A ManualMerge that reparents to a live parent is accepted.
  - **INFERENCE:** resolving by `KeepBase` leaves the pre-existing live child under the tombstoned
    parent exactly as it was. B-2 (i) exempts it because it creates no *new* orphan. It does not
    repair the Epic-1 gap, which is not PR-6's to fix (§14).

### 11.2 Missing parent at resolution time

No deferral exists (the resolver is not a run). **OWNER RULING (B-2):** reject; the record stays
`Unresolved` and nothing is written. The typed reason `ResultParentMissing` is an engineering name.
**INFERENCE:** this is reachable only through ManualMerge, because a candidate's parent cannot vanish
without a hard delete, and none exists outside M5.

### 11.3 Finding F-2 — cascade tombstones write into locked scopes (Medium; §15.3 W-2)

- **FACT.** `CascadeTombstoneAsync` selects live children by FK and tombstones them via the marked path
  with no scope-lock lookup (`SyncApplySession.cs:589-645`); the lock is checked only for the operation's
  own entity scope (`:205-212`, key from `StructuralScopeKeyOf` `:798-801`).
- **INFERENCE (not measured).** A remote tombstone of the Base parent of a StudyTask held at Base in an
  S1 record cascades onto that task while its record is Unresolved ⇒ live ≠ Base (D9-T1 no longer holds)
  ⇒ at resolution every kind is rejected as drift ⇒ same end state as F-1. Two frozen rules collide
  here: D9-T1 ("live = Base while Unresolved") and D9-T4 / the Epic-1 cascade ("no live child under a
  dead parent"). Which wins is an owner question; PR-6's job is only to reject cleanly on the result.
- **Reproduction recipe** (for PR-6 as characterization Z-C2, or a separate follow-up), following the
  precedent of the PR-2 residuals note, which shipped labelled inference plus a recipe when its boundary
  forbade measurement and PR-5 then measured it: seed HocKy → MonHoc `M` → StudyTask `T`, baseline for
  the peer; local reparent `T → B`, remote reparent `T → C` ⇒ S1-CR staged, `T` held at `MaMonHoc = M`;
  then apply a remote tombstone of `M` (phase 1). Expect: `T.IsDeleted == true`, record still
  `Unresolved`, `Matches(record.BaseFingerprint, snapshot(T)) == false`. **Not written here because this
  task forbids test code.**
- PR-6 must **not** change the cascade (§14).

### 11.4 Tombstone results

- **FACT.** Structural candidates are always live (tombstones are resolved first by tombstone-wins,
  `ThreeWayMerge.cs:37-90`), and the AL-PT/S1-PT remote result is staged only when live
  (`SyncApplySession.cs:217`).
- **FACT.** `ConstraintMerge` tests only the **local** side for a tombstone (`ConstraintMerge.cs:41-45`),
  so an S3 record can carry a tombstoned `Remote` (peer created then deleted `N2`). KeepRemote then
  materialises a tombstone `N2` — valid provenance (§8.2), no cascade needed (TaskNote has no children).
  Test it; no owner decision needed (D6-H: Result = Remote). **B-3 does not reach this case**: B-3
  governs ManualMerge only, and this is KeepRemote. The B-2 parent check still applies to it (E-13).
- **INFERENCE (rev 1; what made this blocking).** The only way to produce a tombstone for a
  parent-owning type (MonHoc, StudyTask) is a ManualMerge result with `IsDeleted = true`. D6-H allows
  "a brand-new state", and a tombstone is a state. Honouring it requires the Epic-1 cascade *and*
  A2-b's rule that cascade children copy the parent's tombstone provenance. But under A2-c the
  parent's provenance is stamped by `SyncStamper` at save time, so the children's values are not known
  before the save. DoR §13 never contemplates this.
- **OWNER RULING (B-3, 2026-09-11).** Reject every ManualMerge result with `IsDeleted = true` in PR-6
  v1. This applies to every entity type, TaskNote included (no leaf-type exception), and PR-6 has no
  cascade semantics. The typed reason `ManualTombstoneNotSupported` is an engineering name (E-10).
  The A2-b vs A2-c provenance question therefore never arises in PR-6.
- **INFERENCE.** In PR-6 v1 the only way a resolution can materialise a tombstone is S3 `KeepRemote`
  of an already-tombstoned `N2`, as above.

## 13. Required test matrix

Repo convention: every test names a production mutation that must turn it RED, observed and recorded in
the PR. DoR §17's Z-1..Z-9 are almost entirely **negative** assertions — a resolver that rejects
everything passes all of them. The matrix therefore **leads with positive discriminators**.

**Assertion-design traps the repo has already been bitten by:** (a) use a peer device id, a local
device id and a Base-provenance device id that are all distinct — with shared identities, "stamped
locally" and "kept candidate provenance" produce identical bytes (PR-5 §6); (b) never compute an expected
fingerprint the same way production does — assert the observable consequence (outcome, unchanged row,
unchanged `Rev`, unchanged `ResolvedAtUtc`) instead (the residuals note's degenerate-assertion warning;
PR-5's test M that stopped discriminating); (c) every rejection test needs a positive twin on the same
fixture.

## 16. Strengths · Risks · Follow-ups · Final notes

**Strengths.** PR-4 and PR-5 left PR-6 an unusually small job: every primitive in DoR §13.2 exists and
is database-enforced (terminal status, immutable evidence, one-Unresolved-per-scope, local-candidate
CHECK), so an orchestration bug in the resolver fails closed at `SaveChanges` rather than corrupting
evidence. The resolver can be purely additive — it calls the CRITICAL seams and modifies none of them.
A2-c removes the hardest part of PR-5 (provenance preservation) from PR-6 entirely: no marking, no R1
hazard on the write path, no R2 Case B.

**Risks / watchouts.**

| Risk | Severity | Where |
|---|---|---|
| A resolver that rejects everything passes DoR §17's Z tests | High (test design) | §13 — lead with Z-P*, Z-F1, Z-R1 |
| Round-trip infidelity between staging's `BaseFingerprint` and the resolver's live fingerprint ⇒ every resolution silently rejected as drift | High | §10.1, Z-F1 |
| Storing the post-stamp result ⇒ every replay `MismatchedReplay` (violates D7-C) | Medium | §9.1, E-1 |
| Re-inserting `N1` at `Rev = 1` ⇒ never emitted to peers holding older baselines | Medium | §8.3, E-2 |
| F-1 / F-2 / W-3 are properties of the frozen design, not PR-6 bugs; a PR-6 author may be tempted to "fix" them | Medium | §14 fences |

**Suggested follow-ups (non-blocking).** Prune worktree-derived GitNexus entries and re-analyze the
canonical path (W-5). Open an owner ticket for W-1/W-2 before M2.2 planning, with Z-C1/Z-C2 as its
measured baseline. Retire the stale Decision Record copy (W-6). Append the R2 measurement to the
residuals note as the dated amendment PR-5 §11 asked for, now that the note is tracked.

**Final notes.** rev 1 found the design implementation-ready except for four owner decisions that the
frozen text genuinely left open:

- context lifetime, a governance gap left by Option A's self-scoping;
- the resolution-time parent-check outcome, because §12.2 was written for apply time;
- ManualMerge tombstones, which were never contemplated;
- KeepLocal on the amendment's new record shape.

The owner ruled all four on 2026-09-11 (§15.1), and E-3 was acknowledged. **PR-6 is READY FOR
IMPLEMENTATION.** What remains is the non-blocking engineering choices in §15.2, which the owner may
override, and the pre-implementation GitNexus step in §5. Neither gates starting.

The more important long-term message is still §15.3. Under D8-H + D7-D + D9-T6 as frozen, a conflict
whose scope drifts can never be resolved, and a KeepBase does not survive the peer's next offer. The
rev 2 rulings do not change either property, and they were not asked to. PR-6 should implement the
frozen rules and the rulings faithfully, and pin those properties with characterization tests rather
