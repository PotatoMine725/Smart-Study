## Refine requests

### R1 — BLOCKER — Flaky A6 fault tests (test defect, not production)

**Files:** `SmartStudyPlanner.Tests/ViewModels/FocusViewModelA6Tests.cs`
**Tests:** `HoanThanh_RepoThrows_FaultIsObservableViaExecutionTask`, `ThoatKhanCap_RepoThrows_FaultIsObservableViaExecutionTask`

**Problem.** Both tests do `Command.Execute(null); await Task.Yield();` then assert `ExecutionTask.IsFaulted`. The `FakeStudyLogRepository` faults *after* an `await Task.Yield()` (correct, deliberate). That creates a race: the test's single `await Task.Yield()` continuation and the repo's fault-propagation continuation are both queued on the thread pool with **no ordering guarantee**. When the test continuation wins, `IsFaulted` is still `false` → failure. Reproduced **2/8** then **2/6** in isolation; the failing case observed is `HoanThanh_RepoThrows_…`.

**Impact.** Fails the M1.1 DoD "tests green" non-deterministically. The report's "291/291 passed" is not reproducible — that green was timing luck.

**This is NOT a production bug.** The `async`/`await` propagation through `LuuThoiGianThucTe` → `HoanThanh`/`ThoatKhanCap` is correct. Do not go hunting for a ViewModel fault. The fix is entirely in the test: stop sampling `IsFaulted` at an arbitrary yield point; deterministically await the command's task.

**Fix (per test).** Capture `ExecutionTask` right after `Execute` (it is set synchronously), then await it:

```csharp
vm.HoanThanhCommand.Execute(null);
var execTask = ((IAsyncRelayCommand)vm.HoanThanhCommand).ExecutionTask;
Assert.NotNull(execTask);
await Assert.ThrowsAsync<InvalidOperationException>(() => execTask!);
```

This waits for real completion and also strengthens the assertion (asserts the specific fault, not just "some fault"). Drop the `await Task.Yield()` lines.

**Do NOT touch** `HoanThanh_NewStudyLog_HasDeviceIdStamped` — it is **not** flaky (its non-throwing path completes synchronously through the `NullStudyTimeOutcomeLogRepository` and a fake that returns synchronously). Only the two throwing tests race.

**Exit check.** Run the two tests ≥ 20× in isolation with zero failures before re-claiming green.

### R5 — BLOCKER FOR ACCEPTANCE — Decide what "surface failures" means for A6

**File:** `SmartStudyPlanner/ViewModels/FocusViewModel.cs` (commands + `LuuThoiGianThucTe`)

**Finding.** The commands use `[RelayCommand(FlowExceptionsToTaskScheduler = true)]`. With that flag the command does **not** await/rethrow — the fault lives only on `ExecutionTask`. The tests see it because they inspect `ExecutionTask` directly. At runtime, a grep of the whole production project shows **no subscriber** to any command's `ExecutionTask`/faulted state, and **no** `TaskScheduler.UnobservedTaskException`, `DispatcherUnhandledException`, or `AppDomain.UnhandledException` handler. So a failed autosave becomes an **unobserved task exception that nothing observes → still silent to the user.**

The plan's T1.5 goal was *"surface failures instead of swallowing them."* Current state:

- No longer fire-and-forget — ✓ (the write is awaited; fault is capturable)
- Surfaced to the user — ✗ (nothing observes the fault at runtime)

The report's crash-vs-swallow tradeoff reasoning is sound, but it stops at "observable," which is a test property, not a runtime one.

**Decision needed (owner).** Does A6's Definition of Done mean:

- **(a) "capturable"** — the fault must be observable via `ExecutionTask` (a later sync/merge layer will consume it). Then A6 is **met**; add one line to the report/DoD stating "user-facing surfacing is deliberately deferred," and R5 closes with no code change.
- **(b) "user-visible"** — a failed autosave must reach the user (toast/dialog) or at least a durable sink (`_telemetry.Track("autosave_failed", …)` / log). Then A6 is **not met**; add an observer on the faulted `ExecutionTask` (or route the failure at the call site) before M1.1 is accepted.

My recommendation: **(b)** with a minimal `_telemetry` + non-blocking user notice — a silently-lost study-session autosave is exactly the failure a student would want to know about, and A6 exists to kill silent loss. But this is the owner's call.
