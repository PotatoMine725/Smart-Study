It already encodes a deliberate discrimination guard, quoted from its own header:

> "The session's own local identity (`LocalDevice` / `LocalNow`) is kept deliberately distinct from
> the peer's (`PeerDevice`): if they matched, 'provenance preserved from the remote' and 'provenance
> re-stamped locally' would produce identical bytes and most assertions in this suite would pass
> against a broken implementation."

**Limitations for T2.5 (FACT):**

1. **One `SqliteConnection`, therefore one database.** The fixture models a peer as *snapshots
   handed in*, never as a second store. It cannot run `SyncChangeEnumerator` on a peer side.
2. **`From(params ISyncMetadata[])` hand-builds the change set**, bypassing T2.2 entirely. Fine for
   T2.4's scope; insufficient for T2.5, whose stated job is to exercise T1.4+T2.2 *together* with
   the rest.
3. **Fixed scalar clock** (`LocalNow`, `LocalEarlier`, `RemoteLater`). A generated suite needs a
   clock it can advance per generated step.
4. **No convergence comparator.** There is no helper that reduces a whole database to a canonical,
   derived-field-excluded value for equality assertions.

**`SmartStudyPlanner.Tests/Sync/Merge/MergeTestData.cs`** (5 603 B) — registry-driven snapshot
builders for the pure core: `Snap(entityType, prov, overrides…)` fills every `SnapshotFields` entry
from `MergeSurfaceRegistry`, plus `With`, `WithProv`, `Shuffled(seed)`, `FirstMergeField`, `Bump`,
`Prov/Live/Dead`. **This is already a deterministic, registry-driven generator substrate** — it
enumerates fields from the frozen registry rather than a hand-written list, so it cannot silently
drift from the merge surface. §4 recommends extending this rather than replacing it.

No redesign of any existing component is proposed. No blocker was found in any of them.

### 4.3 Recommendation — **Hybrid, deterministic-first; do not add FsCheck in T2.5's first PR**

1. **Exhaustive, registry-driven `[Theory]` + `[MemberData]` enumeration** for everything whose
   lattice is small and known: entity type × merge outcome × conflict shape × tombstone state ×
   resolution kind × LWW tie-break leg. This *dominates* random sampling here — at these
   cardinalities enumeration gives 100 % coverage of the lattice with zero sampling variance, and
   `MemberData` generated from `MergeSurfaceRegistry` stays in lockstep with the frozen surface.
2. **Seeded deterministic pseudo-random generators** (plain `Random(seed)` with the seed **in the
   test display name**, the idiom `MergeTestData.Shuffled(seed)` already uses) for the genuinely
   open dimensions: change-set permutations (P2), multi-step edit/sync interleavings (P3/P4), and
   adversarial `Rev` values (P11). Failures are reproducible by seed; a failing seed gets promoted
   into an `[InlineData]` regression case — a manual but effective shrink.
3. **Defer FsCheck to a separately-approved slice.** Reasons: (a) it is a new package on a solo repo
   with branch protection and CI, and the task forbids adding it now; (b) its main advantage —
   automatic shrinking — pays off on large/unbounded spaces, and this space is small enough to
   enumerate; (c) FsCheck's default `Arbitrary` instances cannot construct `EntitySnapshot` against
   the frozen registry without custom generators, so most of the work (the registry-driven builders)
   would be written either way; (d) it would be the first non-xunit test dependency, against a
   633-`[Fact]` house style.

**If FsCheck is later wanted**, the deterministic generators in (1)–(2) are exactly the custom
`Arbitrary` bodies it would need — nothing is thrown away.

*No framework was added. `SmartStudyPlanner.Tests.csproj` is unchanged.*

## 5. Fixture-peer model

### 5.1 The question: is a second `AppDbContext`/database required?

**FACT.** `SyncChangeEnumerator` is *not* snapshot-based:

```csharp
public static async Task<List<ChangedEntity<T>>> EnumerateChangesAsync<T>(
    AppDbContext db, string entityType, IEnumerable<T> allRows, …, string peerId, …)

public static async Task<PeerChangeSet> GetChangesForPeerAsync(
    AppDbContext db, string peerId, CancellationToken ct = default)
{
    return new PeerChangeSet(
        await EnumerateChangesAsync(db, SyncEntityTypes.HocKy, await db.HocKys.ToListAsync(ct), …),
        … );
}
```

It takes an `AppDbContext` and reads raw `DbSet`s, comparing each `row.Rev` against **that peer's own
baseline** from `SyncBaseSnapshotStore`.

**Therefore (INFERENCE, from the two FACTs above):**

- To exercise **T2.2 as the producing side** — which T2.5's charter explicitly requires ("exercises
  T1.4+T2.2+T2.3+T2.4 together") — a **second `AppDbContext` over a second `SqliteConnection` is
  required**. There is no snapshot-only path that produces a `PeerChangeSet`.
- To exercise **apply only**, a second database is **not** required: the remote side crosses the
  boundary as inert `EntitySnapshot`s, exactly as `IncomingChanges` documents (*"a snapshot is inert
  … and is the same shape a future T2.1 transport would deserialize into"*).

**Conclusion:** a **two-database fixture**, still with **no networking**. This is not a transport —
it is two `SqliteConnection`s in one process, joined by the existing public
`GetChangesForPeerAsync → FromPeerChangeSet → ApplyAsync` chain. It stays inside M2.1 and needs no
G4 decision.

### 5.2 The five states, explicitly distinguished

| State | Representation | Where it lives |
|---|---|---|
| **Base snapshot** | `SyncBaseSnapshotRow` — per `(peerId, entityType, entityId)`, holds `Rev` + `CanonicalJson` of the last agreed state | `SyncBaseSnapshots` table, **one per device**, written by `SyncBaseSnapshotStore.UpsertAsync` |
| **Local / live state** | Ordinary domain rows (`HocKys`, `MonHocs`, `StudyTasks`, `StudyLogs`, `TaskNotes`, `TaskReferenceLinks`) with their `ISyncMetadata` block | each device's own `AppDbContext` |
| **Remote candidate / change set** | `PeerChangeSet` (producer side) → `IncomingChangeSet(PeerDeviceId, IReadOnlyList<IncomingChange>)` where each `IncomingChange` carries an inert `EntitySnapshot` | crosses between the two contexts; **`Rev` is deliberately dropped** at this boundary (D9 §21) |
| **Conflict record** | `SyncConflictRecordRow` — immutable Base/Local/Remote evidence, `BaseFingerprint`, status, `ConflictKey` | receiving device's `SyncConflictRecords` table |
| **Resolution** | `ResolutionRequest(Kind, ManualResult, ManualResultEntityId)` → `ResolutionOutcome(Kind, Reason, Error)`; persisted as `ResolutionKind`, `ResultEntityId`, `ResultFingerprint`, `ResultSnapshotJson`, `ResolvedAtUtc` | receiving device only — **no propagation exists** (OPEN-2) |

### 5.3 Proposed fixture shape (test-only; no production change)

```
SyncConvergenceFixture : IDisposable
  Device A : SqliteConnection connA  +  Func<AppDbContext> factoryA  (deviceId "DEV-A", clock A)
  Device B : SqliteConnection connB  +  Func<AppDbContext> factoryB  (deviceId "DEV-B", clock B)

  ExchangeAsync(from, to)            // T2.2 → bridge → T2.5-visible SyncApplyReport
      = IncomingChanges.FromPeerChangeSet(
            await SyncChangeEnumerator.GetChangesForPeerAsync(fromDb, to.DeviceId), from.DeviceId)
        |> to.Session().ApplyAsync

  CanonicalStateOf(device) → string  // whole-DB canonical reduction, DERIVED FIELDS EXCLUDED (P12)
  AdvanceClock(device, delta)        // per-device clock, so LWW legs are reachable
```

Three properties this shape must preserve, each with a stated reason:

1. **Distinct device ids and distinct clocks per side** — same trap the existing `SyncApplyFixture`
   header documents: identical identities make a broken implementation pass.
2. **`CanonicalStateOf` must exclude `FieldClass.Derived`** (`DiemUuTien`, `MucDoCanhBao`,
   `IsSeeded`) — required by D9-T3 as read through owner-triage §4. It should derive the exclusion
   from `MergeSurfaceRegistry`, never from a hand-written field list.
3. **Seeding must go through the ordinary local write path** (as `SyncApplyFixture.SeedTreeAsync`
   does) so rows carry real provenance and `Rev`, not hand-set values.

`SyncApplyFixture` is **not** replaced — it remains correct for single-device T2.4 tests (P1, P6,
P7, P11). The new fixture is additive, for the two-device rows (P3, P4, P5, P9).

## Decisions made (ADR-style, engineering only)

**1. Baseline taken from `origin/dev` (`fbc72ea`), not local `dev` (`96cf8ca`).**
*Why:* CLAUDE.md makes `origin/dev` canonical and local `dev` explicitly untrustworthy. *What for:*
the divergence was real — 5 commits, including the H-1 closure; reviewing against local `dev` would
have reported H-1 as an open blocker. *Experience:* the divergence check paid for itself
immediately; it should stay the first step of any agent session here.

**2. H-1 re-verified by mutation rather than accepted from its commit message.**
*Why:* project standard — a passing test is not evidence; the signal must be shown able to go red.
*What for:* M3 ⇒ RED confirmed the `ResultFingerprint` leg is genuinely pinned, which is what let
P8 be marked `Covered = Y` and dropped from T2.5's scope. *Experience:* cheap (one 7 s run) and it
removed an item from the blocker list on evidence instead of on trust.

**3. Generator strategy: hybrid deterministic-first; FsCheck deferred.**
*Why:* D9-E15 delegates this to engineering. The decision was argued from measured constraints —
7 s for 822 SQLite-backed tests, 22 merge fields, a 633-`[Fact]`/3-`[MemberData]` house style — not
from preference. *What for:* enumeration beats sampling at these cardinalities, and
`MergeTestData` already provides a registry-driven substrate. *Experience:* the registry-driven
builder is the reusable asset; whichever framework is chosen later, that code is written either way.

**4. Two databases in the fixture, from a code fact rather than a design preference.**
*Why:* `SyncChangeEnumerator.GetChangesForPeerAsync` takes an `AppDbContext` and reads raw `DbSet`s,
so a peer that *produces* a change set cannot be a snapshot. *What for:* exercising T2.2 as charter
requires is only possible with a second store; the apply side still crosses as inert snapshots.
*Experience:* checking the enumerator's signature before designing the fixture avoided proposing a
snapshot-only peer that could not have exercised T2.2 at all.

**5. Mutation-present verification made a mandatory step of the evidence loop.**
*Why:* M5's first attempt produced a green run from a `sed` that matched nothing — a false negative
that would have inverted the headline finding. *What for:* §7.1 and §9.5 both require a `grep` proof
that the mutant is in the file before any result is admitted. *Experience:* the one place this recon
nearly recorded a wrong conclusion was a broken instrument, not a wrong inference — consistent with
this project's prior lessons on manual-check setup.

**6. Orphaned authoritative documents reported, not committed.**
*Why:* the task requires a docs/recon-only PR; the owner-triage file is the owner's uncommitted
artifact and project memory records this exact file being clobbered before. *What for:* both are
recorded as N-1 / P-1 / P-2 with the exact commands that establish their state. *Experience:*
"authoritative source" and "present on the baseline" are independent properties and were worth
checking separately — two of seven named sources were not where the task said they were.
