## R1 — `MarkSyncApplied` requires an already-tracked entity

### Current behaviour (fact, read from the source)

- `MarkSyncApplied(object entity)` stores the intent in a
  `Dictionary<object, SyncApplyIntent>` built with `ReferenceEqualityComparer.Instance`, keyed by
  **reference identity** of the exact instance passed.
- `SyncStamper.Apply` consults that map only while walking `tracker.Entries()`. An instance that is
  not in the `ChangeTracker` is never visited, so marking an untracked instance is a **silent
  no-op**: no exception, no log, no write.
- The consequence is not "nothing happens" but something worse: the apply layer believes the winning
  provenance was preserved, while in fact **nothing was written at all** for that entity.

### Why PR-2 does not guard this

DoR §10.1's specified `MarkSyncApplied` body is a single dictionary assignment with no tracked-state
check, and PR-2 implemented it as specified. Independently of the spec, a tracked-state check at
mark time would be wrong: it would **spuriously reject a caller that marks before `Add()` /
`Attach()`**, which is a legitimate ordering. (The mark-after-`Add()` ordering is not the problem
case — by then the entity is already tracked and any guard would pass.) The check therefore cannot
live at mark time without constraining valid apply sequencing.

### Required PR-5 invariant

- The T2.4 apply session **MUST** call `MarkSyncApplied()` only on an entity instance that is
  actually tracked by the session's `AppDbContext` **and** will participate in the upcoming
  `SaveChanges` / `SaveChangesAsync`.
- **The apply session owns this sequencing guarantee.** The seam does not and cannot enforce it.
- PR-5 **MUST NOT** treat a successful `MarkSyncApplied()` call as proof that persistence intent was
  registered. It proves nothing on its own.
- Related trap, same root cause: DoR §11.3 has the merge load rows `AsNoTracking()`. A no-tracking
  instance and the tracked instance for the same row are **two different objects**, and reference
  equality does not bridge them. Marking the `AsNoTracking` instance is exactly the silent no-op
  above. PR-5 must mark the instance it will write, never the one it merged from.

### Required validation

An integration test through the **real** apply/session path (not a direct `SyncStamper` call):

```
create / load / attach a tracked entity
  -> set merged provenance
  -> MarkSyncApplied(entity)
  -> SaveChanges
  -> assert provenance preserved
  -> assert Rev incremented exactly once
```

A defensive helper (for example, a session-internal `MarkTracked(entity)` that asserts
`Entry(entity).State != Detached` at the point where the session knows the entity is attached) may
be added in PR-5 **if the implementation naturally provides one**. Do not retroactively alter PR-2
unless PR-5 demonstrates it is necessary.

## R2 — a failed `SyncStamper` validation leaves partially mutated in-memory state

### Current behaviour (fact, read from the source)

`SyncStamper.Apply` iterates entries sequentially and mutates as it goes. `ApplyPreservingProvenance`
performs `meta.Rev++` on each valid marked entry, and **throws** on an invalid one
(`EntityState.Deleted`, `ModifiedAtUtc == default`, empty `ModifiedByDeviceId`, or `IsDeleted` with a
null `DeletedAtUtc`). So a valid marked entry encountered **before** an invalid one has already
received `Rev++` in memory when the throw happens.

The throw occurs inside `Apply`, i.e. **before** `base.SaveChanges` is reached, so nothing is sent to
the database and DB state is unchanged. The `finally` in `AppDbContext` clears `_syncApplyIntents`.
What survives is a `ChangeTracker` holding **dirty, unmarked** instances whose `Rev` is ahead of the
persisted row.

### Escalation: this is not only a retry hazard — labelled INFERENCE, not reproduced

The owner's framing is that reusing the context *for a retry* is unsafe. Read against DoR §12.1, the
exposure is larger, because §12.1 specifies that the session owns **one** `AppDbContext` for the whole
run and that on any exception it does `ROLLBACK, record ApplyOutcome.Failed(op, reason), continue
with next op`. The dirty instance is therefore **not** waiting for a retry that may never be issued —
it is carried into the *next operation's* transaction as ordinary happy-path behaviour.

**Case A — throw inside `Apply` (before any save).** The entity remains `Modified` and, because the
intent map was cleared in the `finally`, it arrives at the next operation's `SaveChanges`
**unmarked**. The ordinary stamping path then applies a *second* `Rev++` **plus local
`ModifiedAtUtc` / `ModifiedByDeviceId`**, and commits it inside an unrelated operation's transaction.
A row the failed operation was supposed to leave untouched ships with local provenance — precisely
the failure mode PR-2 exists to prevent.

**Case B — throw between the two saves of one operation.** DoR §11.2 mandates two
`SaveChangesAsync` calls inside one transaction (apply, then baseline `Upsert`). If the **second**
throws and the transaction rolls back, the first save already completed with
`acceptAllChangesOnSuccess`, so EF has marked those entities `Unchanged` while the database was rolled
back. The context now holds a **clean-looking** instance whose `Rev` and provenance are ahead of the
database, with no dirty state to signal it, and EF identity resolution will hand that stale instance
back to any later read on the same context. This is harder to notice than Case A and it sits on the
DoR's own designed path.

**Evidence label:** both cases are **reasoning from the source and DoR §11.2/§12.1, not measured.**
They were not reproduced, because doing so requires new tests and this task's boundary forbids
touching code or tests. Per `docs/review/README.md` ("a claim that sets another package's severity
gets measured first"), PR-5 must **reproduce Case A and Case B before designing around them** — that
is item 1 of the checklist below. If reproduction shows either case does not occur, say so and
downgrade it here by dated amendment.

### Required PR-5 invariant

- A failed sync-apply operation **MUST NOT** reuse the mutated `DbContext` — neither for a retry nor
  for the next operation in the run.
- On failure: roll back the transaction if one exists, then **dispose and recreate** the
  `DbContext` before continuing or retrying.
- Retry **MUST** reload state from the database and rebuild the apply operation from authoritative
  persisted state. Never from surviving in-memory instances.

### Preferred implementation

> One logical sync operation owns its `DbContext`; failure ⇒ rollback + dispose; retry ⇒ fresh
> `DbContext`.

**Do NOT** add in-memory rollback machinery to `SyncStamper` unless PR-5 demonstrates a concrete need
that cannot be safely handled by context recreation. Snapshotting and restoring `Rev` inside the
stamper re-introduces exactly the batch-scoped statefulness PR-2 was built to avoid.

### OPEN — context lifetime deviates from DoR §12.1's written mechanism

DoR §12.1 states the session owns **one** `AppDbContext` created from the composition-root factory
**for the whole run**. The preferred implementation above is one context **per logical operation**.

- The `[FROZEN]` tag on §12.1 is on its *unit* claim — "one logical operation = one transaction" —
  and context lifetime appears in neither §2.1 (D1–D9) nor §2.2 (D9-T1..T6). Per-operation contexts
  therefore do **not** appear to violate the frozen contract.
- **This note does not rule on it.** Changing §12.1's mechanism is a DoR amendment and is outside
  this document's boundary. PR-5 must get the owner to ratify one of:
  1. **per-operation context** (recommended — makes R2 structurally impossible rather than
     disciplined-away, and keeps `DeviceIdProvider` identity by constructing from the same factory); or
  2. **one context per run, plus an explicit dirty-state reset between operations** — which then
     needs its own tested mechanism, because "detach everything touched by the failed op" is easy to
     get subtly wrong and Case B leaves nothing dirty to detach.

Whichever is ratified, the choice must be recorded before PR-5 implements against it.

### Required tests

1. Construct one operation with **one valid marked entry ordered before one invalid marked entry**.
2. Observe the failure.
3. Prove database state was not committed —
   **and note this assertion alone is degenerate.** With the seam as built, the throw happens inside
   `Apply` before anything is sent, so "nothing was committed" is trivially true and would pass
   against a completely broken implementation. The **discriminating** assertions are: after the
   failure the first entry's *in-memory* `Rev` is ahead of the persisted row, and a subsequent
   ordinary `SaveChanges` on the same context **commits that drift** (Case A) — plus the Case B
   variant, where the surviving instance is `Unchanged` and still ahead of the DB. This is the same
   degenerate-input class that let PR-2's batch-wide mutation stay green until the test was given a
   second local identity; write the version that can actually go red.
4. Do not reuse the failed context.
5. Retry with a fresh context.
6. Prove final `Rev` and provenance are correct.
7. Prove no duplicate revision and no stale in-memory state leaks into the retry.

Per the repo's standing convention, each of these must be accompanied by a named production mutation
observed RED; a green test is not by itself evidence.

## Strengths

- The per-entry marker (DoR §10.1) is genuinely per-entry: an unmarked `ISyncMetadata` entry in the
  same `SaveChanges` is stamped exactly as before, verified by a mixed-batch test that goes RED
  against a batch-wide gate.
- `ApplyPreservingProvenance` takes neither `utcNow` nor `deviceId`, so the marked path **cannot**
  consult local provenance sources. That is a compile-level guarantee, not merely a tested one.
- The seam fails closed on incomplete provenance rather than repairing it, which keeps a silently
  patched row from converging to different bytes on the two peers.

## Risks / watchouts

| # | Risk | Severity | Where |
|---|---|---|---|
| R2-A | Dirty `Rev` from a failed op is carried into the next op and committed **with local provenance** | **High** — defeats PR-2's purpose for that row | R2, Case A |
| R2-B | Post-first-save rollback leaves a clean-looking instance ahead of the DB, returned by identity resolution | **High** — silent, on the DoR's designed path | R2, Case B |
| R1 | Marking an untracked (or `AsNoTracking`) instance silently writes nothing | **Medium** — apply reports success having written nothing | R1 |
| §12.1 | Context lifetime unratified; PR-5 could implement either shape | **Medium** — blocks a clean R2 fix until decided | R2 OPEN |

## Final notes

PR-2 delivers exactly the seam DoR §10 specifies, and neither residual is a defect in it — both are
consequences of the seam being deliberately narrow, which is the right shape for it. The reason they
are worth a durable document is that both are **silent**: R1 writes nothing while reporting success,
and R2 writes the *wrong* provenance under a *different* operation's transaction. Neither would be
caught by the PR-2 test suite, because both live at the session boundary PR-2 was explicitly scoped
out of. The single most important line in this file is the R2 checklist item that says *reproduce
before designing* — the severity claims in the Risks table are reasoning, and PR-5 should measure
them before spending design budget on them.

## Decisions made

### Recording R2 as broader than the owner's framing

*Why it had to be made:* the owner framed R2 as a retry hazard. Read against DoR §12.1's
"continue with next op" on one run-scoped context, the dirty instance is carried forward on the
**normal** path, not only on a retry that may never be issued.
*What it's for:* so PR-5 does not scope its mitigation to a retry code path that would leave the
common case uncovered.
*Experience for future development:* a residual's blast radius depends on the surrounding design, not
only on the code that produces it. Re-read the integration spec before writing down a residual's
severity.

### Labelling both R2 cases as inference rather than measurement

*Why it had to be made:* this task forbids touching code or tests, so the cases could not be
reproduced, and `docs/review/README.md` requires a claim that sets another package's severity to be
measured first.
*What it's for:* PR-5 gets the hypothesis and the reproduction recipe, without a reasoned claim being
inherited as an established fact.
*Experience for future development:* when the boundary prevents measurement, ship the labelled
inference plus the recipe — not a confident claim, and not silence.

### Not ruling on the DoR §12.1 context-lifetime deviation

*Why it had to be made:* the owner's preferred R2 fix (one context per operation) contradicts
§12.1's written mechanism (one context per run). Choosing here would amend the DoR, which this
document's boundary forbids.
*What it's for:* PR-5 reads this file as authoritative; an unflagged silent amendment would
propagate as if ratified.
*Experience for future development:* a constraint note may record a tension and recommend a
resolution, but ratifying a change to a frozen-adjacent document stays with the owner.
