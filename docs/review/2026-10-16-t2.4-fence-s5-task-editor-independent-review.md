## 5. Risks / watchouts (findings by severity)

### F-1 — MEDIUM — REPRODUCED — X-19 misses DbSet-typed writes inside the ruled scope, and the blind-spot list does not name them

**Where:** `SmartStudyPlanner.Tests/Infrastructure/Persistence/SQLite/Mutations/SyncedEntityWritePathFenceTests.cs:33-37` (regex);
blind-spot list in the class comment at `:24-28`.

**What is wrong:**
- Rulings §4 [D] defines the scanner scope as "DbSet-typed writes on the six synced tables".
- The regex requires the method name to be followed directly by `(`, on one line, after a `.HocKys`…`.TaskReferenceLinks` member access.
- So it misses several DbSet-typed writes. None of them is in the documented blind spots (raw SQL, `Entry().State`, other receiver names, `ExecuteUpdate`, `.MaTask =`).
- The CHANGELOG row states the guarantee without qualification: "synced-table writes and FK reassignments only in allowlisted files".

**How shown:** each line below was planted alone in `QuanLyTaskViewModel.cs` as a dead method. Each built, then the X-19 class was run, then the line was reverted.

| Planted line | X-19 |
|---|---|
| `db.TaskNotes.Add(new TaskNote());` (the addendum's mutant) | **RED** |
| `await db.TaskNotes.AddAsync(new TaskNote());` | green — **missed** |
| `db.Set<TaskNote>().Add(new TaskNote());` | green — **missed** |
| `db.TaskReferenceLinks` ⏎ `.Remove(link);` (fluent chain split across lines) | green — **missed** |
| `await db.TaskNotes.ExecuteDeleteAsync();` | green — missed (only `ExecuteUpdate` is listed) |
| `dbc.Remove(link);` (receiver not named db/ctx/context/.Db) | green — listed blind spot, not a finding |

`AddAsync` matters most: the codebase is async throughout, so it is the form a future write is most likely to take.

A grep at head found no current production site in any of the missed shapes, so nothing is bypassing the fence today.

**Direction:**
- Extend the regex to `Async` variants and to `Set<T>()` for the six entity types.
- Scan a whitespace-normalised file instead of single lines, or at least join continuation lines that start with `.`.
- Add each shape to the non-vacuity self-check, and list `ExecuteDelete` beside `ExecuteUpdate`.

All of this is test-only.

### F-2 — MEDIUM — REPRODUCED — The OD-5 guard misses the codebase's own service-resolution idiom

**Where:** `SmartStudyPlanner.Tests/Infrastructure/Persistence/SQLite/Repositories/StudyTaskRepositoryMutationGuardTests.cs:28` (`DeclaredReceiver`).

**What is wrong:** the guard resolves a receiver in three ways:
- an identifier declared with the type name;
- `x = new SqliteStudyTaskRepository(..)`;
- `Get<IStudyTaskRepository>()` chained straight into the call.

It does not resolve a local assigned from the locator, `var repo = ServiceLocator.Get<IStudyTaskRepository>();`, which is how this codebase resolves services (`QuanLyTaskViewModel.cs:81`).

**How shown:** planted in `OutcomeMaturationService`, after its existing `GetAllAsync`:

| Planted | OD-5 guard |
|---|---|
| `if (allTasks == null) await _studyTaskRepo.DeleteAsync(Guid.Empty, ct);` (typed field) | **RED** |
| `var repo9 = ServiceLocator.Get<IStudyTaskRepository>();` ⏎ `await repo9.DeleteAsync(Guid.Empty, ct);` | green — **missed** |
| `var r2 = (IStudyTaskRepository)_studyTaskRepo; await r2.DeleteAsync(..)` (cast local) | green — missed (contrived; noted only) |

**Direction:**
- Add a `DeclaredReceiver` alternative for `<name> = <...>.Get|GetRequiredService|GetService<IStudyTaskRepository>()`.
- Add the shape to `TheGuard_ActuallyMatchesPlantedCalls`.

This is test-only.

### F-3 — MEDIUM — REPRODUCED — D-1 is reachable from the UI (edit → delete the same task → save); the report says it is not, and at head the VM is then stuck in edit mode

**Where:**
- Report §3e and §9 ("still unreachable from the UI (INFERENCE…)").
- `ViewModels/QuanLyTaskViewModel.cs:223-246`.
- Executor `LiveNoteAsync`, `LocalTaskEditorExecutor.cs:61-62`.

**What is wrong:** the report's reasoning is that the only local note tombstone is `TaskCascadeHelper`, which runs only when the owning task is tombstoned. That is true, but the user can tombstone the task while the form is still editing it:
1. `SuaTask(T)`, where T has a note.
2. Delete T from the grid (`XoaTask`). This does not touch `_taskDangSua` / `_editingTaskId`.
3. Click "Cập Nhật".

At step 3, `ThemTask` → `SaveEditorAsync(T, …)` finds no *live* note, plans a `Create`, and hits D-1's `UNIQUE constraint failed: TaskNotes.MaTask`.

**How shown (REPRODUCED, the same probe on base and head):** the probe runs `XoaTask`'s body directly (remove from `DanhSachTask`, then `LuuHocKyAsync`), because its `MessageBox` cannot run in a test.

| | `2ec5d31` (base) | `0f09d45` (head) |
|---|---|---|
| Exception at step 3 | `DbUpdateException` — `UNIQUE constraint failed: TaskNotes.MaTask` | same |
| Rows after | task dead; note 0 live / 1 dead; link 0 live / 1 dead | same (the whole request rolled back) |
| VM after | `Thêm Deadline` (edit mode already left before the editor call) | **`Cập Nhật`**: still editing the deleted task; every further click fails the same way until the user picks another task |

- **Data:** D-1 is pre-existing, and E2 makes this failure atomic, so head is no worse on data.
- **New at head:** the VM consequence is a direct, ruled effect of R-a + Q-1′. It is consistent with the ruling ("on any failure stay in edit mode"), but nobody ruled on it for this case.
- **Related, pre-existing (REPRODUCED, base and head):** the editor never checks that the task is live. `SaveEditorAsync` (head) and `UpsertNoteAsync` + `AddLinkAsync` (base) on a tombstoned task with no prior note both commit a **live** note and a **live** link under the dead task. The fence passes because no record exists.

**Direction:**
- Correct report §3e/§9 to "reachable via edit → delete → save (pre-existing)".
- The behaviour itself is an owner question (§9 Q-1). It needs either a VM change outside `ThemTask` (out of this slice's fence) or a parent-liveness check, which is a new rule.

### F-4 — LOW — REPRODUCED/OBSERVED — No structural guard that a production implementation overrides the non-atomic default `SaveEditorAsync`

**Where:** `Repositories/ITaskEditorRepository.cs:36-50`.

The addendum asks whether anything guards the override. The answer is split.

- **The current class is guarded behaviourally (REPRODUCED).**
  - Mutant: change the override's parameter to `IEnumerable<TaskReferenceLink>`. The class method then no longer implements the interface, so callers through the port silently get the default.
  - Result: **RED (6)**. That covers the E2 all-or-nothing test, the mid-save PK rollback, both Q2 rows and both VM failure retries.
  - The report's M7b (non-atomic body inside the override) is also RED (6) in my run.
  - Because a behavioural guard exists for the production class, this is not the addendum's MEDIUM.
- **A new implementation is not guarded (OBSERVED absence).** Nothing structural ties "production implementation" to "overrides `SaveEditorAsync`": no interface-map assertion, no check on the DI-registered type. Examples are a decorator such as a caching or logging wrapper, or a second store. A future implementation would silently be non-atomic.

**Direction:** a one-line test, e.g. `typeof(SqliteTaskEditorRepository).GetInterfaceMap(typeof(ITaskEditorRepository))` maps `SaveEditorAsync` to a method declared on the class; or assert the same on the type `ServiceLocator` registers.

### F-5 — LOW — REPRODUCED — `RollbackAsync(ct)` with a cancelled token replaces the original exception

**Where:** `Mutations/LocalTaskEditorExecutor.cs:80`.

**How shown:**
- An interceptor cancelled the caller's token and threw `InvalidOperationException("ORIGINAL")` on the 2nd write statement.
- The snapshot assertion **passed**: the data was byte-identical, because the `using` transaction's dispose rolls back.
- The message assertion **failed**: the caller saw `TaskCanceledException: A task was canceled.`, and the original exception was gone.

**Why only LOW:**
- It is unreachable in production. `ThemTask`'s only call passes no token (grep: `QuanLyTaskViewModel.cs:241`).
- `LocalSemesterSaveExecutor.cs:83` has the identical line, so this is a copied, pre-existing pattern (INFERRED for the semester side; not probed).

**Direction:** roll back with `CancellationToken.None` in both executors, or wrap the rollback so the original exception is preserved.

### F-6 — LOW — OBSERVED — `App.xaml.cs:30` says "the executor already restored the in-memory graph before throwing"

That is false for editor rejections. Under R-a, nothing is restored; the form keeps the input. The implementer disclosed it (report §11) and correctly left it alone, because `App.xaml.cs` is outside the scope fence. The next agent will read it as fact.

**Direction:** a one-line comment fix in the next PR that may touch `App.xaml.cs`.

### F-7 — LOW — OBSERVED — Report build figures: "96 warnings, same as the baseline" — head has 97

### F-8 — LOW — REPRODUCED — `PlanSave` trusts the incoming link's `Id` and `MaTask`

**Where:** `Mutations/TaskEditorPlanner.cs:85-96` and `:155-160`.

- **Incoming `Id` is live under another task:** the planner emits `Create` for an existing row. The fence judges a create that is not one. SaveChanges then fails `UNIQUE constraint failed: TaskReferenceLinks.Id`, and the request rolls back (tables identical).
- **Incoming `MaTask` is a different, existing task:** the link is written under that other task. The intent's relation names it too, so the fence and the write agree. This contradicts the port doc's "the complete live set the task should end up with".
- **Neither is reachable from the UI (INFERRED from code):**
  - `ThemTask` overwrites every `vm.MaTask` with `taskId`.
  - `SuaTask` clears and reloads `StudyLinks` per task.
  - A dead id under this task is already pinned by `PersistenceFailureMidSave_LinkPkCollision…`.

**Direction:** when a defensive check is wanted, have `PlanSave` reject an incoming link whose `MaTask != taskId`, as a business validation after the fence.

## 10. Final notes

PR #113 delivers what the rulings asked for:
- The task editor's whole change is one fenced transaction.
- The planner and the writer cannot disagree about what is written.
- The VM keeps the form and the task identity on any failure, in both modes, without a catch.

I tried to break atomicity at every write position inside SaveChanges, and the intents ⇔ writes link across every diff shape. Neither broke. Every critical mutant went RED.
