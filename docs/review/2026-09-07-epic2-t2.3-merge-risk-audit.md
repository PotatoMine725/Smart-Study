# Epic 2 / T2.3 — Merge-Risk Audit (3-way field-level merge; LWW `ModifiedAtUtc`→`DeviceId`, no HLC)

> Independent adversarial audit, read-only, performed **before** any T2.3 code exists. Goal: find
> failure modes in the frozen merge mechanics (D-I) that a plausible-looking implementation could
> hit without anyone noticing until data is silently lost or two peers diverge.

## Scope reviewed

  `docs/architecture/lessons-learned.md` L6 (`Rev` is a local clock), L7 (merge granularity bounded
  by tracking granularity), L9 (delete/edit trilemma); `docs/architecture/data-model.md` §8;
  `docs/knowledge/sync-data-model.md`; Epic 2 task breakdown in

- **Code at `origin/dev`** (T1.4+T2.2 confirmed merged via PR #66, commits `6056438`/`053b258`/`15f3a1c`):
  `SmartStudyPlanner/Data/SyncStamper.cs`, `Data/AppDbContext.cs`, `Models/ISyncMetadata.cs`, all six
  synced entity models (`HocKy`, `MonHoc`, `StudyTask`, `StudyLog`, `TaskNote`, `TaskReferenceLink`),

- Confirmed via `git log --all` and a repo-wide grep: **no T2.3/T2.4/T2.5 code exists anywhere** —
  this is a pre-implementation audit, not a review of a finished change.

## Verdict

**`block`** — equivalently, **NOT SAFE TO START T2.3** against the current write paths as-is.

No new architecture decision is required to unblock. The frozen D-I text is sufficient. What's
missing is that three of the lowest-friction implementation shortcuts available in this codebase
today each independently violate D-I in a way that would compile, pass a shallow test, and look
correct. Once the implementing agent is briefed on the risks below (and two small open questions —
full-tie tie-break behavior, parent-tombstone-vs-child-create — are given an explicit, documented
default), **T2.3 is safe to start.**

## Strengths

- T1.4 (`SyncBaseSnapshotStore`) and T2.2 (`SyncChangeEnumerator`) are both narrowly scoped, match
  their task-card description exactly, and carry mutation-tested evidence for their two
  regression-critical properties (watermark check present; tombstoned rows not hidden by a query
  filter). No defect found in either.
- The team already recognizes this general class of bug elsewhere: `SyncBaseSnapshotRow`
  deliberately does **not** implement `ISyncMetadata`, with a doc comment explaining exactly why
  (so `SyncStamper` can't stamp/tombstone sync bookkeeping as if it were user data). The same
  discipline needs to extend to T2.3's own field-diff logic (Risk 5) and to sync-apply writes
  generally (Risk 1) — the precedent for getting this right already exists in the codebase.
- `T2.2`'s commit message already states the raw-`DbSet`-not-repository rule that Risk 7 below
  depends on — the constraint is documented, just not yet propagated to where T2.3 will need it.

## Risks / watchouts (ranked)

### 1. The single stamping seam will silently overwrite relayed LWW provenance — **blocks T2.3**
**Evidence.** `SyncStamper.Apply` (`Data/SyncStamper.cs:27-32`) runs unconditionally inside both
`AppDbContext.SaveChanges`/`SaveChangesAsync` overloads, with no bypass. For any tracked entity in
`Added`/`Modified` state: `meta.Rev++; meta.ModifiedAtUtc = utcNow(); meta.ModifiedByDeviceId = deviceId;`
— always the *local* clock and *local* device.

**Why it matters.** When T2.3 persists a merged row — even one where a field's true winner is
"remote, unchanged, remote wins LWW" — saving it through the normal path re-stamps
`ModifiedAtUtc`/`ModifiedByDeviceId` to "now, by me." The row's LWW tie-break inputs, which are
supposed to answer "who last touched this field and when," now say "the relaying device, just now,"
destroying true provenance. A later sync against a third peer (or a stale copy of the same peer)
uses the fabricated timestamp instead of the real origin time, letting an already-superseded value
win a future LWW race it should have lost.

**Minimal test.** Peer B edits field F at `T_B`. Peer A (untouched on F) applies the merge. Assert
the resulting row's `ModifiedAtUtc`/`ModifiedByDeviceId` equal `T_B`/`B` — not `now`/`A`. Any
implementation that calls `SaveChanges*` on the merged entity without special-casing this fails.

### 2. `LuuHocKyAsync`'s reconcile is remove-by-absence — reusing it mass-deletes — **blocks T2.3**
**Evidence.** `SqliteHocKyRepository.LuuHocKyAsync` diffs the *incoming* graph against the DB and
treats "row present in old graph, absent from new one" as a genuine delete, tombstoning it.

**Why it matters.** T2.2's `PeerChangeSet` deliberately contains only *changed* rows. If T2.3's
apply logic builds a partial `HocKy` graph from just the changed entities and calls
`LuuHocKyAsync` (the only existing "save a HocKy graph" entry point), every local subject/task the
remote peer didn't touch is absent from that partial graph and gets tombstoned — total, silent
data loss on the very first sync-apply.

**Minimal test.** Seed a `HocKy` with 2 `MonHoc`, 3 `StudyTask`. Build a `PeerChangeSet` touching
only 1 task. Apply via whatever path T2.3 chooses; assert every untouched row still has
`IsDeleted == false`.

### 3. `CopySyncSafeValues` is whole-row LWW, not field-level merge — **blocks T2.3**
**Evidence.** `CopySyncSafeValues` does `entry.CurrentValues.SetValues(source)` — copies *every*
scalar property from the incoming object onto the tracked entity (restoring only the five
`ISyncMetadata` fields afterward).

**Why it matters.** This is exactly the anti-pattern lesson **L7** warns against: row-level
metadata is "a materially different (and lossier) policy than what D-F promises." Reusing this
helper (or an equivalent "overwrite from the winning side" shortcut) instead of computing per-field
winners silently degrades field-level merge to entity-level LWW — two devices editing *different*
fields of the same task clobber each other, and it would still compile and look correct.

**Minimal test.** Base: `TenTask="X"`, `DoKho=2`. Local changes `DoKho=3` only. Remote changes
`TenTask="Y"` only. After merge, assert **both** survive. Whole-row overwrite fails immediately.

### 4. `DeviceId` is not guaranteed unique — the LWW tie-break's second key can be a real tie — **blocks T2.3**
**Evidence.** `DeviceIdentity.cs`'s own doc comment: `DeviceHelper.GetId()` derives from
`Environment.MachineName` and "collides between 2 machines with the same hostname... for LAN sync,
neither is acceptable." The class then seeds its persisted `device-id.txt` from that same
non-unique value ("not random," by design, for backward compat), so a genuine hostname collision
becomes **permanent**, not transient.

**Why it matters.** Two devices sharing a hostname (cloned VM images, shared corporate naming —
not hypothetical) produce identical `ModifiedByDeviceId` forever. If their edit timestamps also
collide (see Risk 10), the tie-break has no third key and no documented behavior for a genuine
full tie — whichever code path processes first wins, which can differ by peer, breaking
convergence.

**Minimal test.** Two fixture peers with equal `ModifiedByDeviceId` and equal `ModifiedAtUtc`
(post-DB-round-trip) editing the same field differently from base. Run "peer A applies" and "peer B
applies" and assert both converge to the same winner.

### 5. Generic field-diffing must not treat sync-metadata as mergeable business fields — **blocks T2.3**
**Evidence.** `ISyncMetadata` (`Rev`, `ModifiedAtUtc`, `ModifiedByDeviceId`, `IsDeleted`,
`DeletedAtUtc`) is implemented as plain public properties, indistinguishable by reflection from
`TenTask`/`DoKho`/etc. `SyncBaseSnapshotRow` deliberately does *not* implement `ISyncMetadata`,
showing the team already knows this bug class exists elsewhere.

**Why it matters.** A naive "diff every public property, LWW whatever differs" implementation
would (a) compare `Rev` across devices — exactly what L6 forbids; (b) LWW-merge `ModifiedAtUtc`/
`ModifiedByDeviceId` as if they were data, which is incoherent (they *are* the tie-break); (c)
apply generic LWW to `IsDeleted`/`DeletedAtUtc` instead of the mandated tombstone-wins rule.
`StudyLog.DeviceId` (a genuine *business* field, semantically distinct from `ModifiedByDeviceId`)
is a concrete naming trap for any name-based special-casing.

**Minimal test.** Base/local/remote where only `Rev` differs — assert the row is treated as
*unchanged*. Separately: local edits a field, remote deletes — assert delete wins even though the
edit's `ModifiedAtUtc` is later (tombstone-wins must not go through generic LWW).

### 6. No FK-referential-integrity guard exists outside `LuuHocKyAsync`
**Evidence.** The only check that `StudyTask.MaMonHoc` references an existing `MonHoc` is the
fail-loud `InvalidOperationException` inside `LuuHocKyAsync`'s reconcile. If T2.3 avoids that
reconcile (correctly, per Risk 2) and writes merged entities directly via `AppDbContext`, no such
check exists anywhere else.

**Why it matters.** A remote `StudyTask` create/update referencing a `MaMonHoc` not present locally
(parent not synced yet, or independently deleted) silently persists a dangling FK — nothing in
SQLite or EF enforces it once `LuuHocKyAsync` is bypassed.

**Minimal test.** Apply a `ChangedEntity<StudyTask>` whose `MaMonHoc` doesn't exist locally. Assert
the apply fails loud or defers — not that it silently persists.

### 7. Repository tombstone-filtering must not leak into merge-apply's "does this exist locally" check
**Evidence.** T2.2's commit message states the rule explicitly: callers "MUST pass the raw
DbSet... never a Sqlite*Repository, since repositories filter out tombstoned rows" — pinned by a
mutation test. `data-model.md` §8 confirms every repository read excludes `IsDeleted` rows.

**Why it matters.** If T2.3's "look up local row" step goes through a repository instead of the
raw `DbSet` — an easy mistake, since repositories are the idiomatic access point everywhere else —
a locally-tombstoned row becomes invisible, and an incoming remote edit for it looks like "no local
row exists" → gets added as new, silently resurrecting a delete that should have won per D-I.

**Minimal test.** Locally tombstone a task. Remote sends an edit to it. Apply the merge; assert the
task stays tombstoned and is not re-inserted as a live row.

### 8. Parent-tombstone vs. child-create is a race the frozen decision doesn't name
**Evidence.** D-I's text resolves only *same-row* delete-vs-edit. Cascade rules only cascade a
delete to loaded/tracked children on the *deleting* device — nothing addresses a child created
independently, concurrently, on the other device.

**Why it matters.** Peer A deletes `MonHoc` M (cascade-tombstones its currently-known tasks on A).
Peer B, unaware, creates a new `StudyTask` under M. T2.2 enumerates it as genuinely new on B's
side. If applied without checking M's tombstone state, A ends up with a live task under a dead
subject — invisible to every read path, unreachable via the UI, occupying a live row forever.

**Minimal test.** Base: `MonHoc` M live, no tasks. Peer A tombstones M. Peer B adds a new task with
`MaMonHoc = M`. Apply B's change to A's DB; assert the outcome is decided (tombstoned too, or
rejected/conflict-recorded) — not a silent live orphan.

### 9. Base-snapshot shape (`SnapshotJson`) is explicitly undecided and must exclude navigation collections
**Evidence.** `SyncBaseSnapshotRow.SnapshotJson`'s doc comment: "Opaque, caller-supplied... T2.3
(not built yet) decides that shape." `HocKy.DanhSachMonHoc` and `MonHoc.DanhSachTask` are
`ObservableCollection<T>` navigation properties on the very entities needing per-field diffing.

**Why it matters.** A naive "serialize the whole entity" snapshot pulls in child collections.
Diffing a `HocKy` row would then treat its entire subject list as one field, and any subject
add/remove (which should be tracked as a separate, independently-merged `MonHoc` row) would look
like a same-field conflict on the parent, or duplicate/drop children depending on serializer
defaults.

**Minimal test.** Snapshot a `HocKy` with 2 subjects. Concurrently: local adds a 3rd subject
(unrelated `MonHoc` row), remote renames `HocKy.Ten`. Assert both survive independently and the
diff never treats `DanhSachMonHoc` as a merge-relevant field of `HocKy`.

### 10. Nullable/default-value and DateTime round-trip traps in the diff
**Evidence.** `StudyTask.MucDoCanhBao` defaults to `"An toàn"` specifically so non-UI write paths
(explicitly including sync-apply, per the comment at `StudyTask.cs:27-29`) don't crash;
`ThoiGianDaHoc` defaults to `0`. No doc or test characterizes `ModifiedAtUtc`/`DeletedAtUtc`
round-trip precision/`Kind` through this project's SQLite/EF Core datetime handling.

**Why it matters.** A 3-way diff can't distinguish "peer genuinely reset this to the default" from
"never touched" using value equality alone on fields whose default coincides with a legitimate
value. Separately, if `ModifiedAtUtc` loses sub-tick precision on round-trip, genuinely-ordered
in-memory edits can become falsely equal on reload, pushing more conflicts onto the already-fragile
`DeviceId` key (Risk 4) than a correct implementation would.

**Minimal test.** Round-trip a freshly-stamped entity through a real save+reload; assert
`ModifiedAtUtc` compares equal in both `Kind` and value. Separately: `ThoiGianDaHoc` base=5, local
sets back to 0, remote unchanged — assert the diff detects "local changed," not "no value."

## Suggested follow-ups

### "Must not happen" — constraints for the T2.3 implementation agent

1. Must not call `SaveChanges`/`SaveChangesAsync` on a merged entity without first deciding, per
   row, what `ModifiedAtUtc`/`ModifiedByDeviceId` the result should carry (Risk 1).
2. Must not route merge-apply through `LuuHocKyAsync` with anything less than the complete current
   local graph (Risk 2).
3. Must not reuse `CopySyncSafeValues` or any "overwrite all scalars from one side" helper as the
   merge-apply mechanism (Risk 3).
4. Must not assume `ModifiedByDeviceId` is globally unique; must define explicit, deterministic
   behavior for a genuine full tie (`ModifiedAtUtc` *and* `ModifiedByDeviceId` both equal) (Risk 4).
5. Must not diff via untyped reflection over "every public property" without excluding `Rev`,
   `ModifiedAtUtc`, `ModifiedByDeviceId`, `IsDeleted`, `DeletedAtUtc`; must not confuse
   `StudyLog.DeviceId` (business field) with `ModifiedByDeviceId` (sync metadata) via name-matching
   (Risk 5).
6. Must not persist a merged row referencing a local-missing parent FK without an explicit, tested
   decision (fail loud / defer / reorder) (Risk 6).
7. Must not read "current local state" for the diff or the add/update decision through any
   `Sqlite*Repository` — must read the raw `DbSet` (Risk 7).
8. Must not apply a newly-created child row without checking whether its declared parent is
   tombstoned (Risk 8).
9. Must not serialize whole entity graphs (including navigation collections) into
   `SyncBaseSnapshotRow.SnapshotJson` — scalars only, one entity at a time (Risk 9).
10. Must not treat "differs from base by `==`" as sufficient without accounting for
    constructor-default collisions on value-typed fields; must verify `ModifiedAtUtc` round-trip
    fidelity through the real SQLite path before trusting it as a tie-break input (Risk 10).
11. Must not build conflict-record persistence, tombstone retention/purge, or transport/networking
    as part of this task — those are T2.4, T2.6, and M2.2/G4 respectively. T2.3 *should* surface
    which fields conflicted and the losing value in its output, even though persisting that is
    T2.4's job, so T2.4 doesn't need to re-thread conflict detection through T2.3's internals later.
12. Must not claim convergence or no-data-loss as verified by this task alone — that's T2.5's
    property suite; T2.3's own tests should stay scoped to per-row/per-field merge correctness.

### Open decisions to make explicit (not new architecture, just need a documented default)

- Full-tie tie-break behavior when both `ModifiedAtUtc` and `ModifiedByDeviceId` compare equal
  (Risk 4).
- Parent-tombstone-vs-child-create outcome (Risk 8).

## Final notes

T1.4 and T2.2 are sound and need no changes. T2.3 itself requires no new architecture decision —
D-I is sufficient as written. The risk is entirely in *implementation shortcuts the existing
codebase makes tempting*: three separate reuse-the-existing-write-path shortcuts (Risks 1–3) each
independently collapse "field-level merge with provenance-preserving LWW" into something that
compiles, passes a shallow test, and quietly isn't that. None of the ten risks above require
scope creep into T2.4/T2.5/T2.6 to fix — they require the implementer to write the small amount of
genuinely new code (a real field-by-field diff, a metadata-excluding property walk, a
provenance-preserving save path) that the task card actually calls for, instead of assembling it
from parts built for a different write pattern (single-device UI edits).
