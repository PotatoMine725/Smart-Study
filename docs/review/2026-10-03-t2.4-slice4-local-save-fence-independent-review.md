## 3. Verdict

### `ship-with-followups`

The fence is wired where the ruling and plan put it. It runs on the executor's own context, inside
the transaction that holds SQLite's write lock from BEGIN, before the writer. Non-passed decisions
never reach the writer. OD-7 R2 restores the caller's graph in place before the throw, and the
rejection reaches the dispatcher handler with its rule ids. I reproduced all four mutants the card
requires (M1 fence ignored, M2 writer before gate, M3 restore dropped, M4 swallow), and each goes
RED as the report says. I also reproduced M5 (fence decided outside the transaction), which makes
X-12 fail on its TOCTOU invariant.

I found no BLOCKER or HIGH. The one MEDIUM (M-1) concerns VM form state that the restore cannot
reach. It changes no persisted data incorrectly by itself. It is unreachable in production today,
because no `SyncConflictRecord` can exist while sync is unwired. It should be decided before Slice 6
or sync wiring makes rejections real.

## 4. Strengths

- **The TOCTOU close is real, and X-12 tests it the hard way.**
  - The test uses `FileBackedSqliteFixture` (WAL asserted), a separate saver context with a
    `DbCommandInterceptor`, and a second real connection with a 1 s busy timeout that inserts the
    record right after the selector's read (OBSERVED, `LocalSemesterSaveConcurrencyTests.cs:107-170`).
  - The invariant assertion (`!(recordCommitted && taskTombstoned)`) is separate from the
    observed-shape assertions. That is the right split.
- **No restore-source pollution.** Every query under `Sync/Fence/` is `AsNoTracking`
  (`ConflictDependencySelector.cs:86`; `ImpactResolver.cs:335-390`, OBSERVED by grep). The fence's
  reads on the shared context therefore cannot fix up dead or foreign rows into `hocKyCu`. This was
  the first thing I checked, because a tracked read there would silently bring back the D-2 re-stamp
  class.
- **Restoration runs on the Dispatcher thread, as the code comment assumes (REPRODUCED).** I drove
  `QuanLyTaskViewModel.HoanThanhTaskCommand` through `ICommand.Execute` on an STA thread with a
  `DispatcherSynchronizationContext`. The restore's `CollectionChanged` fired on the dispatcher
  thread (id 15 = 15), and the rejection arrived at `Dispatcher.UnhandledException`, which
  `App.DispatcherUnhandledException` is raised from. That closes the report's "NOT RUN: any VM save
  command end to end" for two sites (§6, attack 6).
- **N-6 holds where the caller can see it (REPRODUCED).** A rejected save leaves an unstamped new
  task's `MaMonHoc` at `Guid.Empty`, so the writer's FK heal never ran. The probe is GREEN at head
  and RED under M1 and M2.
- **Re-added instances do not poison the next save (REPRODUCED, attack 14).**
  - Setup: a rejected MonHoc delete; the restorer re-adds a detached copy (`NotSame`, as documented).
  - Then: editing a task inside that copy and saving succeeds and changes **exactly one row**, that
    task. The MonHoc is not re-stamped, T stays live, and the record stays Unresolved.
- **Intent completeness has a structural guard.** Every EF-mapped scalar is classified in
  `MergeSurfaceRegistry`, and `MergeSurfaceRegistryGuardTests` G-1a fails on any unclassified
  column. Every writable class has a route: Merge → `UpdateFields`, Structural → `Reparent`. A newly
  mapped column cannot be written onto a held row without either being classified (and routed) or
  failing G-1a. Derived-class columns are the deliberate exception, and that is E-2.
- **N-10 has an empty allowlist.** No production `catch (MutationRejectedException`, and the scan
  goes RED under M4. Grep found no `catch` around `LuuHocKyAsync` in Setup, QuanLyMonHoc, Dashboard
  or QuanLyTask either. The one `try/catch` in `DashboardViewModel` (`:98-129`) wraps the load, not

## 5. Risks / watchouts

### [MEDIUM] M-1 After a rejected edit of a held task, the next click on the same button creates a duplicate task and sends the note to the held task

- **Evidence:** REPRODUCED (`Probe_Site2_EditHeldTask_Rejected_ThenSecondClick`, GREEN at head).
- **Location:** `SmartStudyPlanner/ViewModels/QuanLyTaskViewModel.cs:207-208` (pre-await state
  change), `:215` (save), `:222-226` (post-await note save) at `2842b98`. The file is unchanged by the
  PR, but its interaction with the new rejection path is new.

**What is wrong.** In edit mode, `ThemTask` clears `_taskDangSua` and resets the button text to
"Thêm Deadline" **before** `await LuuHocKyAsync`. It clears `_editingTaskId` and the form only
**after** the await. The R2 restore reaches the model graph, but not VM fields. The report's
§2.3 and Phase 0 §3a list the code skipped after the await. They do not list the VM state mutated
before it.

**How I showed it.**
1. Stage S1-CR on T and construct the VM on the loaded graph.
2. Run `SuaTaskCommand(T)`, set `TenTask = "edited while held"` and a note, then call
   `ThemTaskCommand` through `ICommand.Execute` on a Dispatcher.
3. Result: `MutationRejectedException` (`S1CR.NonStructuralFields`, Blocked) reaches
   `Dispatcher.UnhandledException`. The graph matches persisted state, and no note was saved. Both
   are correct.
4. VM state afterwards: `TextNutThem = 'Thêm Deadline'`, `TenTask = 'edited while held'`,
   `_taskDangSua = null`, `_editingTaskId = <T's id>`.
5. Second click (`ThemTaskCommand.ExecuteAsync`), which saves:
   - task count goes 1 → 2;
   - a **new** task row `634d9333…` is persisted, carrying the rejected edit's content (a `Create`,
     which the fence correctly passes);
   - T is unchanged;
   - `UpsertNoteAsync` is called with **T's id**.

**Why it matters.**
- The user's single intended edit of T gets split. The fields land on a duplicate row, and the note
  lands on the held T through the task-editor repository, which Slice 5 has not fenced yet.
- The handler's message has already told the user that the app's data was restored to saved state.
- This is not an automatic retry (N-10/X-13 hold, because the user clicked), and no ruled invariant
  is violated. That is why the severity is MEDIUM, not HIGH.
- It is unreachable in production today, because no record can exist.

**Suggested direction (not a patch).** Choose one:
- Make the pre-await VM mutations in the save commands survive a failed save. Either move them after
  the await, or restore them in a `finally`/failure branch.
- Accept the behaviour and name it in the OD-7 limits, and in the report's §2.3 list of
  caller-visible effects.

## 10. Final notes

This slice moves the fence from a library onto the live save path. The hard parts are correct and
proven by tests that can fail:
- the decision is atomic with the write;
- the writer is gated;
- the restore runs on the UI thread from an untainted old graph and preserves identity where it
  matters;
- the rejection cannot be swallowed.

What remains is at the edge between the persistence layer and the VMs. R2 deliberately restores
only what the executor can see, so VM-local state mutated before the save is outside its reach (M-1).
That is acceptable to ship while no record can exist in production, but it should be decided before
sync makes rejections real.

## Decisions made

### Reviewing the PR head found by `gh`, not an addendum value
- **Why:** the addendum left PR and SHA as `<fill>`.
- **What for:** an unambiguous subject. I re-checked the head at the end (`2842b98`, unchanged), so
  every claim here is about one revision.
- **Experience:** a template with unfilled slots is still usable if the reviewer resolves the slots
  from primary state and says so in the header.

### Driving real `ICommand.Execute` on a Dispatcher instead of accepting "VM path NOT RUN"
- **Why:** attack 6 asked for the command → dispatcher path at two sites. Both the report and the
  PR mark it NOT RUN because the commands show MessageBoxes.
- **What for:** two of the eight sites (`HoanThanhTask`, `ThemTask` in edit mode) show no MessageBox
  on the save path. With a `DispatcherSynchronizationContext` on an STA thread, the toolkit's rethrow
  lands in `Dispatcher.UnhandledException`, which the app handler is raised from. That also measured
  the restore's thread, which the code comment only asserted.
- **Experience:** "it shows a MessageBox" ruled out only some sites. Checking each site's code for a
  MessageBox on the failure path found two testable ones. The same probe exposed M-1, which no
  executor-level test could show.

### Capping M-1 at MEDIUM although it is REPRODUCED
- **Why:** the template's HIGH requires wrong behaviour reachable through a production path. The VM
  path is production code, but the precondition, an Unresolved record, cannot arise until sync is
  wired.
- **What for:** severity that matches reachability today, with the reachability condition stated so
  the owner can re-grade when Slice 6 / OD-1 opens.

### Running M5 myself, after first misattributing X-12's discrimination to M1
- **Why:** the first draft of this review (commit `3ada9b5`) said X-12 goes RED under
  M1. My own M1 run contradicts that: X-12 was not among its 27 failures. That is correct behaviour,
  because M1 ignores the decision but keeps the read inside the locked transaction. The draft also
  overstated M5's cost.
- **What for:** attack 1 (TOCTOU) is the slice's central invariant, so it deserved a reproduced
  discriminator, not "construction verified". M5 moves the decision onto a separate context before
  BEGIN, about six lines. X-12 then fails on the invariant assertion itself, with the interceptor
  confirmed fired.
- **Experience:** check each mutant row against the actual failure list before writing it into a
  summary. The "same class of mutant" intuition put X-12 under M1 where it does not belong.
  Separately, a mutant that removes the instrumented call can turn a test RED through its
  precondition assertion (here, `hook.Fired`) rather than through its invariant.

### Fixing my own vacuous probe before relying on it
