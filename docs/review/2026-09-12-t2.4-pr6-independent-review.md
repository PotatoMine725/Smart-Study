## 5. Dedicated E-12 finding

### Classification: **engineering recommendation falsified by implementation evidence — NOT an owner semantic change**

**This is the correct classification, and the rulings file itself authorises it.**
`T2.4-PR6-ConflictResolver-Rulings-2026-09-11.md` §"What these rulings do not decide" states the
write-plan keying is engineering, not ruling:

> **B-2's "would actually write" clause (engineering).** The review keys the exemption on "the
> resolution's write plan is empty", not on `Kind == KeepBase`. […] The clause is therefore a
> structural guard, and **no test can observe it**.

That paragraph makes two claims. The implementation contradicts **both**, and I verified the
contradiction independently rather than accepting the implementation's account.

### The counter-example is real and reachable — MUTATED, not argued

In the test-M shape, the local side never edited the task, so **Local, Base and the live row are all
byte-identical**, and the shared parent is tombstoned. Therefore `writesNothing` (`:159-160`) is
**`true` for KeepLocal as well as for KeepBase**. `Kind` is the *only* discriminator between them.

Three prerequisites for the counter-example all hold (this matters — if any failed, an earlier gate
would fire and the counter-example would be moot):

1. **`LocalEntityId` is non-null** — the live task exists, so step 5 (`KindNotApplicable`) does *not*
   pre-empt the check. (INFERRED from the shape builder; corroborated because `ZN4`, the AL-PT test,
   *does* hit `KindNotApplicable` while test-M reaches `ResultParentTombstoned`.)
2. **The drift gate passes** — Base == live, so `Matches` is true. Corroborated: the same test gets
   `Applied` for KeepBase, which is only reachable past drift.
3. **`writesNothing` is true for KeepLocal** — proven by the mutation below.

I replaced line 170 with the *exact* E-12 predicate:

```csharp
// PR-6 as written:      if (!(request.Kind == ResolutionKind.KeepBase && writesNothing))
// E-12 as recommended:  if (!(writesNothing))
```

Result (OBSERVED):

```
ZPT1_TestMShape_BothSidesRejected_KeepBaseAccepted_ManualMergeToLiveParentAccepted
  Assert.Equal() Failure: Values differ
  Expected: ResultParentTombstoned
  Actual:   None
```

`Actual: None` means KeepLocal was **not rejected at all** — it took the exemption and was applied.
This proves, in order:

1. `writesNothing == true` for KeepLocal here (otherwise the mutation would change nothing);
2. E-12's predicate **would materialise a StudyTask under a tombstoned MonHoc**, which owner ruling
   B-2 forbids;
3. the `Kind == KeepBase &&` clause is **load-bearing**, not decorative;
4. therefore the claim "no test can observe it" is false — a test observes it, and turns RED without it.

## 8. Issues

### H-1 — MEDIUM — E-1 replay fingerprint leg is correct but **untested**

Dropping `&& StringComparer.Ordinal.Equals(Norm(rec.ResultFingerprint), Norm(replay.Fingerprint))`
from the replay identity (`:127`) leaves **all 38 tests green** (OBSERVED, mutant M6).

*The production code is correct — this is a coverage gap, not a defect.* Why the gap exists: for
KeepLocal / KeepRemote / KeepBase the result content is fully determined by `Kind` + `EntityId`
(it is read from immutable evidence columns), so the first two legs already imply the third. The
fingerprint leg only does independent work for **ManualMerge**, where the same `Kind` and the same
`ManualResultEntityId` can carry *different content* — and there is no ManualMerge replay test.
(The scenario is INFERRED from the code; the coverage gap itself is OBSERVED.)

Consequence if it ever regressed: replaying a ManualMerge with edited content would return
`NoOpReplay` and silently discard a different human decision, instead of `MismatchedReplay`.

Suggested (not required for correctness): one test that resolves `ManualMerge(A, id)` then replays
`ManualMerge(B, id)` with `B` differing only in content, expecting `MismatchedReplay`.

### L-1 — LOW — `TaskReferenceLink` absent from the resolver's parent map (latent only)

`CheckResultParentAsync` (`:295-301`) maps MonHoc→HocKy, StudyTask→MonHoc, TaskNote→StudyTask and
returns "no parent check" for everything else. `SyncApplySession` classifies `TaskReferenceLink` as
**`ParentRule.FkOnlyChild` — the same rule as TaskNote** (`SyncApplySession.cs:684-685`).

**Not reachable today, therefore not a defect.** I verified the reachable conflict surface:

- Structural records: staging cascade-tombstones `FkOnlyChild` instead of staging a conflict
  (`SyncApplySession.cs:230-244`), so Structural `EntityType` ∈ {MonHoc, StudyTask} only.
- Constraint records: the sole production `ConstraintScope` is `TaskNote/MaTask`
  (`SyncApplySession.cs:294`), and the sole domain unique index is `TaskNotes.MaTask`
  (`AppDbContext.cs:122`).

So the reachable set is exactly {MonHoc, StudyTask, TaskNote} — precisely what the map covers.
`StudyLog` (`NoFkChild`) is correctly excluded by frozen rule; `HocKy` has no parent. The risk is
purely forward-looking: adding a constraint scope or structural rule for `TaskReferenceLink` later
would silently skip its parent check. Worth a comment naming the reachable set, at most.

### N-1 — NON-BLOCKING — rollback on non-Applied is unobservable (by design)

Changing `tx.RollbackAsync` to `tx.CommitAsync` for non-Applied outcomes leaves all 38 tests green
(mutant M13). This is **expected and self-documented** at `:59-60`: the rollback is defence-in-depth,
converting "no early-return path writes anything" from a claim into a guarantee.

Worth noting the inversion: M13's survival is *positive* evidence. Had any reject or replay path
performed a write, committing it would have surfaced in at least one of the 38 assertions. It did not.

## Decisions made

**Treated E-12 as engineering, not owner semantics — and verified it by mutation rather than argument.**

*Why:* The review brief flagged a risk that an implementation agent might quietly upgrade its own
engineering correction into a semantic change. The rulings file settles the category question from
primary source: it lists the write-plan keying under "What these rulings do not decide" and calls it
an engineering choice the owner may override. So the only open question was empirical — is the
counter-example real, or is the implementation's justification post-hoc?

*What for:* To avoid both failure modes. Accepting the implementation's account would have meant
trusting the party under review; rejecting it as an unauthorised semantic change would have blocked a
correct fix. Neither is decidable by reading. Running the E-12 predicate as an actual mutation made it
decidable: the suite goes RED with a specific, legible failure (`Expected: ResultParentTombstoned /
Actual: None`) that could not be produced by a post-hoc rationalisation.

*Experience:* The rulings document's own claim that "no test can observe it" turned out to be the
falsified part — and it was falsified by a test that already existed. The lesson generalises: a
predicate justified as "unobservable, therefore equivalent" deserves a mutation before the
equivalence is believed. Two predicates that agree on every case anyone thought to enumerate can
still diverge on a shape the frozen docs already describe.

**Ran 14 mutants instead of auditing the implementation's claim of 7.**

*Why:* The claim "7 mutation tests all RED" is unfalsifiable from the outside — it says the seven they
chose were killed, not that the suite discriminates the requirements the owner cares about. The
brief's requirement list is the right basis for the mutant set, not the implementation's.

*What for:* To produce per-requirement evidence rather than an aggregate pass. The payoff was the two
survivors, which no amount of reading the green suite would have surfaced: one a genuine coverage gap
(H-1), one a by-design structural guard (N-1) whose survival is itself positive evidence that no
reject path writes.

*Experience:* Deriving mutants from the requirement list rather than from the code found the gap the
code-derived set missed. It also made "819 green" mean something specific per requirement instead of
conveying only that nothing is obviously broken.

**Scoped the `TaskReferenceLink` gap down to LOW by proving unreachability instead of reporting it as a B-2 hole.**

*Why:* `TaskReferenceLink` carries the same `ParentRule.FkOnlyChild` as `TaskNote` yet is absent from
the resolver's parent map, which reads like a live B-2 violation. Reporting it that way without
checking reachability would have been an escalation by inference — the exact pattern
`feedback_reproduce_before_escalating` warns against.

*What for:* Severity had to follow evidence. Tracing the two staging paths showed `FkOnlyChild` is
cascade-tombstoned rather than staged, and that the only constraint scope and the only domain unique
index are both `TaskNote/MaTask` — so the reachable set is exactly the three types mapped.

*Experience:* The difference between a HIGH and a LOW here was two greps. An asymmetry in a lookup
table is a prompt to check reachability, not evidence of a defect on its own.
