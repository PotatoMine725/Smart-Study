## 4. Merge-surface registry (frozen; encode verbatim)

### 4.1 Pure DTO / value-object model [ENG, D1-compliant]

All types are immutable records in a new namespace `SmartStudyPlanner.Sync.Merge` with **no reference to EF, `AppDbContext`, or `Models.*` entities**. Entities are converted to `EntitySnapshot` at the apply-layer boundary (§11.3); the pure core never sees a tracked object (F-b is the reason).

```csharp
// Identity of what is being merged. EntityType is a SyncEntityTypes string; EntityId is the PK.
public sealed record EntityRef(string EntityType, Guid EntityId);

// Row-level provenance as stored on the row. Rev is deliberately ABSENT (D9 §21).
public sealed record Provenance(
    DateTime ModifiedAtUtc,          // Kind == Utc, tick precision (§5.4)
    string   ModifiedByDeviceId,     // compared with StringComparer.Ordinal
    bool     IsDeleted,
    DateTime? DeletedAtUtc);         // Kind == Utc or null

// One field value on the merge surface, already normalised (§5.3). Only these CLR shapes exist.
public abstract record FieldValue;              // closed hierarchy:
public sealed record StringValue(string? Value)      : FieldValue;
public sealed record Int32Value(int Value)           : FieldValue;   // also enums (underlying int)
public sealed record BoolValue(bool Value)           : FieldValue;
public sealed record GuidValue(Guid Value)           : FieldValue;   // structural + copy-on-create refs
public sealed record WallClockValue(DateTime? Value) : FieldValue;   // Kind Unspecified, no offset
public sealed record UtcValue(DateTime? Value)       : FieldValue;   // Kind Utc

// The unit the pure core reasons about. Fields are keyed by registry field name, ordered by registry.
public sealed record EntitySnapshot(
    string EntityType,
    Provenance Provenance,
    IReadOnlyDictionary<string, FieldValue> Fields);   // exactly the registry's field set

public enum FieldClass { Identity, Structural, ConstraintScope, Merge, CopyOnCreate, Derived, NotMapped, SyncMetadata, Tombstone }

public sealed record FieldSpec(string Name, FieldClass Class, Type ValueType, bool IsUtc);
public sealed record EntitySpec(string EntityType, IReadOnlyList<FieldSpec> Fields);  // order = canonical order

// Per-field merge outcome (D9 §12.1 five cases + structural).
public enum FieldDecision { Base, Local, Remote, Common, LwwLocal, LwwRemote, StructuralConflict }
public sealed record FieldOutcome(string Field, FieldDecision Decision, FieldValue? Result);

// Result of merging ONE entity (same EntityId on both sides).
public sealed record MergedEntity(
    EntityRef Ref,
    EntitySnapshot? Result,                   // null only when the scope must have no live row (D9-T1 with null Base) — never for entity merge
    Provenance ResultProvenance,              // §6.5
    IReadOnlyList<FieldOutcome> Outcomes,
    IReadOnlyList<ConflictCandidate> Candidates,
    bool IsNoOp);                             // Result equals Local on every field + provenance → apply must not write

public enum ConflictKind { FieldConflict, StructuralConflict, ConstraintConflict, TombstoneConflict }
public enum StructuralReason { ConcurrentReparent, ParentTombstoned }   // ParentTombstoned is produced by the APPLY layer, not the pure core (D4/D9-T4)
public enum ResolutionKind { KeepLocal, KeepRemote, KeepBase, ManualMerge, AutoLww, AutoTombstone }

public sealed record ConstraintScope(string EntityType, string Key, string Value);   // e.g. ("TaskNote","MaTask","<guid D-format>")

public sealed record ConflictCandidate(
    ConflictKind Kind,
    string EntityType,
    Guid? EntityId,                    // Field/Structural/Tombstone
    string? FieldName,                 // Field/Structural
    ConstraintScope? Scope,            // Constraint
    StructuralReason? Reason,
    EntitySnapshot? Base,              // may be null (D6-B)
    Guid? BaseEntityId,
    EntitySnapshot Local,  Guid LocalEntityId,
    EntitySnapshot Remote, Guid RemoteEntityId,
    ResolutionKind? AutoResolution,    // AutoLww / AutoTombstone ⇒ persisted directly as Resolved (D9-T5); null ⇒ Unresolved
    EntitySnapshot? AutoResult);       // the deterministic outcome for auto kinds

// Input for a constraint scope (D5): built by the apply-layer loader, consumed by the pure core.
public sealed record ConstraintScopeInput(
    ConstraintScope Scope,
    (Guid Id, EntitySnapshot Snap)? Base,     // baseline row in scope for this peer, if any
    (Guid Id, EntitySnapshot Snap)? Local,    // LIVE (IsDeleted == false) local row in scope, if any
    (Guid Id, EntitySnapshot Snap)? Remote);  // live remote row in scope from the change set, if any
```

Purity guarantee (test E-1/E-4 in §17): `ThreeWayMerge.Merge(EntityRef, base?, local, remote)` and `ConstraintMerge.Detect(ConstraintScopeInput)` are `static`, allocate only their return value, take no clock, no device id, no comparer beyond `StringComparer.Ordinal`, and are referentially transparent. Contract violations (e.g. field set mismatch, non-UTC provenance) throw `MergeContractViolationException`; they are never turned into conflicts.

### 5.1 Envelope (exact)

```json
{"v":1,"entityType":"StudyTask","provenance":{"modifiedAtUtc":"2026-09-08T01:02:03.1234567Z","modifiedByDeviceId":"desktop-1a2b3c4d","isDeleted":false,"deletedAtUtc":null},"fields":{"MaMonHoc":"0f3a…-…","TenTask":"Ôn chương 3","HanChot":"2026-09-10T00:00:00.0000000","TrangThai":"Chưa làm","LoaiTask":0,"DoKho":2,"ThoiGianDaHoc":0,"NgayHoanThanh":null}}
```

Rules:

1. Exactly four top-level members in this order: `v`, `entityType`, `provenance`, `fields`. No PK, no `Rev`, no navigation, no derived, no `[NotMapped]` (D2).
2. `provenance` has exactly four members in this order: `modifiedAtUtc`, `modifiedByDeviceId`, `isDeleted`, `deletedAtUtc`.
3. `fields` has exactly the registry's field set for that `entityType`, in registry declaration order (§4.2 table order, top to bottom, excluding Identity/Derived/NotMapped/SyncMetadata/Tombstone classes).
4. No whitespace anywhere. UTF-8, no BOM.

### 5.2 Canonical scalar encoding

| Canonical type | JSON | Rule |
|---|---|---|
| string | JSON string | escape **only** `"` → `\"`, `\` → `\\`, U+0008/0009/000A/000C/000D → `\b \t \n \f \r`, other U+0000–U+001F → `\u00xx` (lowercase hex). Everything else, including all non-ASCII, raw UTF-8. (RFC 8785 §3.2.2.2 set.) `null` → `null`; `""` → `""` (distinct). |
| int (incl. enum) | JSON number | invariant decimal, no sign for zero, no leading zeros. |
| bool | `true`/`false` | |
| Guid | JSON string | `Guid.ToString("D")` (lowercase, hyphenated). |
| WallClock (`NgayBatDau`, `HanChot`, `NgayHoanThanh`, `NgayHoc`) | JSON string | `yyyy-MM-ddTHH:mm:ss.fffffff` — **no zone suffix, no offset, ever**. |
| Utc (`modifiedAtUtc`, `deletedAtUtc`, `CreatedAtUtc`) | JSON string | `yyyy-MM-ddTHH:mm:ss.fffffffZ`. |
| null (any nullable) | `null` | |

Writer [ENG]: a hand-written `CanonicalJsonWriter` (~40 lines; `StringBuilder`, the escape table above). Not `JsonSerializer` and not `Utf8JsonWriter` with a stock encoder: the probe (F-m) shows STJ's default encoder escapes Vietnamese as `ế` and the relaxed encoder emits uppercase hex for controls; either is deterministic *today*, but neither is contractually stable across runtime versions, and a stored fingerprint must recompute identically after an app update. Reader: `System.Text.Json.JsonDocument` with `AllowTrailingCommas=false`, `CommentHandling=Disallow`, `MaxDepth=4`, plus the strict checks below.

**Canonical-only input rule:** after parsing, the reader re-serializes and requires byte equality with the input (`canonical(parse(s)) == s`). This single check enforces field order, no whitespace, lowercase GUIDs, exact DateTime shapes and escape form — anything non-canonical fails closed without per-rule code.

### 5.3 Fingerprint and ConflictKey (OPEN-1 closed here)

```text
fp(snapshot)  = lowercase hex SHA-256 of the canonical UTF-8 bytes        (64 chars)
fp(null)      = "null"                                                    (cannot collide with hex)

ScopeKey (FieldConflict / TombstoneConflict) = EntityType + "|" + EntityId(D) + "|" + FieldName   (TombstoneConflict: FieldName = "*")
ScopeKey (StructuralConflict)                = EntityType + "|" + EntityId(D) + "|" + FieldName   (the FK field)
ScopeKey (ConstraintConflict)                = EntityType + "|" + ConstraintKey + "=" + ConstraintValue

CandidateFp(side) = fp(side.Snapshot) + "@" + side.EntityId(D)            (constraint candidates differ by Id)

ConflictKey = lowercase hex SHA-256 of UTF-8( "ck1|" + Kind + "|" + ScopeKey + "|" + fp(Base) + "|"
                                              + min(CandidateFp(L), CandidateFp(R)) + "|" + max(CandidateFp(L), CandidateFp(R)) )
```

`min`/`max` by ordinal string order make the key symmetric: both peers compute the same key from mirrored Local/Remote (D7-B, D5-G). No GUID randomness, no `Rev`, no clock.

### 5.4 DateTime semantics at the boundary (OPEN-5 frozen here) [ENG]

| Situation [FACT] | Rule |
|---|---|
| EF/SQLite stores `DateTime` as `yyyy-MM-dd HH:mm:ss.fffffff` text, tick-exact, and reads it back with `Kind = Unspecified` (prior probe A.1). | At the entity→snapshot boundary, **re-kind, never convert**: `DateTime.SpecifyKind(v, Utc)` for Utc-class fields, `SpecifyKind(v, Unspecified)` for WallClock. `ToUniversalTime()`/`ToLocalTime()` are forbidden in `Sync/` (guard test greps for them). |
| `DateTime.ToString("O")` on a `Local` value emits the machine offset (`+07:00`, probe F-m). | Never use `"O"`/`"o"` or STJ default DateTime handling for sync data. Only the two formats in §5.2. |
| `ParseExact` with the Utc format rejects an offset form (probe F-m). | Reader uses `ParseExact(s, fmt, Invariant, AssumeUniversal \| AdjustToUniversal)` for Utc, `ParseExact(s, fmt, Invariant, None)` for WallClock. Any other shape ⇒ fail closed. |
| Equality/ordering of `ModifiedAtUtc` | **tick equality** on the re-kinded UTC value. Kind never participates. |
| The apply layer writes a merged snapshot back | snapshot→entity uses the same re-kind rule; EF drops Kind on write anyway, so the DB column is unaffected. |

Both peers store wall-clock user dates without a zone; treating them as opaque ticks preserves exactly what each user typed (the app is single-timezone by design; cross-zone reinterpretation is not a v1 concern and is not decided here).

|---|---|

## 6. LWW algorithm

### 6.1 Definition [FROZEN semantics, ENG formalisation]

For a field `f` where `L[f] ≠ B[f]`, `R[f] ≠ B[f]`, `L[f] ≠ R[f]` (D9 §12.1 case 5), with row-level provenance `PL`, `PR` (there are no per-field timestamps in the schema — [FACT]):

```text
Key(side) = ( side.Provenance.ModifiedAtUtc.Ticks            // Int64, after §5.4 re-kind
            , side.Provenance.ModifiedByDeviceId             // compared by StringComparer.Ordinal
            , UTF8(canonical(side[f])) )                     // compared as unsigned byte sequences

winner = the side whose Key is lexicographically greater.
```

Equality of value literals is byte equality of the canonical encoding; `null` is the four bytes `null` and needs no special case (byte order puts it after any string literal since `"` = 0x22 < `n` = 0x6E — a consequence, not a rule).

### 6.2 Argument-order independence (B-6) — proof

Let `K_L`, `K_R` be the keys. The comparison is a lexicographic order on a product of three total orders (Int64 order, ordinal string order, unsigned byte-sequence order), hence a total order `≤`. `winner(L, R)` returns the argument with the maximum key; `max` over a total order is commutative, so `winner(L, R)` and `winner(R, L)` select the same key. When `K_L = K_R` the third component forces `canonical(L[f]) = canonical(R[f])`; canonical encoding is injective on each canonical type (§5.2 — every scalar has exactly one encoding and distinct scalars have distinct encodings), so `L[f] = R[f]`, contradicting case 5. Therefore a full tie **cannot reach** the LWW branch; it is case 4 (common value). The returned value and the returned provenance are identical in both call orders. ∎

### 6.3 Determinism for full provenance ties (D9-T2)

If `Ticks` and `DeviceId` are equal and values differ, component 3 decides. Component 3 is a pure function of the value under §5.2 and byte order is runtime-independent (unlike UTF-16 `string.CompareOrdinal`, which orders supplementary characters differently from code-point order — hence bytes, not strings). Both peers therefore compute the same winner without consulting `Rev`, clocks, or argument position. ∎

### 6.4 Where LWW is *not* applied

Structural fields (§7.1), copy-on-create fields (contract violation if they differ), tombstoned rows (§7.3, tombstone-wins pre-empts field merge), constraint scopes (§7.2).

### 6.5 Provenance of the merged row [ENG]

| Case | `ResultProvenance` |
|---|---|
| no field changed on either side | Base's (row untouched; `IsNoOp = true`) |
| only Local changed (any field) | Local's |
| only Remote changed | Remote's |
| both changed (any mix of cases 4/5 across fields) | the side with the greater `(Ticks, DeviceId)` — i.e. the same side that wins every case-5 field in this row (row-level provenance means every LWW field in one row has the same winner unless it is a component-3 tie, in which case both provenances are already identical). |

This is the natural extension of C-1/C-2 ("winning timestamp/DeviceId preserved") to mixed rows and is symmetric, so both peers write the same provenance and converge. `Rev` is not part of it (§11).

## 7. Structural / constraint apply model

### 7.1 Structural fields in the pure core (D4) [FROZEN]

For `f ∈ {MonHoc.MaHocKy, StudyTask.MaMonHoc}` with values `B, L, R`:

| Condition | Outcome |
|---|---|
| `L = B ∧ R = B` | `Base` |
| `L ≠ B ∧ R = B` | `Local` |
| `L = B ∧ R ≠ B` | `Remote` |
| `L ≠ B ∧ R ≠ B ∧ L = R` | `Common` |
| `L ≠ B ∧ R ≠ B ∧ L ≠ R` | `StructuralConflict(ConcurrentReparent)` — candidate with Base/Local/Remote **full row** snapshots; `MergedEntity.Result = Base row`, `IsNoOp` per Base vs Local. |

Scope of the structural conflict = the entity row (`EntityType|EntityId|FieldName`). While Unresolved, D9-T1 says the *live state* equals Base — read literally as the **whole row** (other fields are not partially applied; applying them would make live ≠ Base). The full-row evidence in the record is what allows KeepLocal/KeepRemote to restore either side's other fields later. Parent existence is not examined here (D4).

### 7.2 Constraint scope detection (D5) without UNIQUE exceptions (D9 §19)

Input `ConstraintScopeInput` for scope `("TaskNote","MaTask",T)` is built by the apply loader (§11.3) from: the peer baseline row(s) whose `MaTask = T` (Base), the **live** local `TaskNotes` row with `MaTask = T` (raw DbSet, `IsDeleted = 0`), and the live remote row with `MaTask = T` from the change set.

| Local | Remote | Outcome |
|---|---|---|
| none | none | nothing to do |
| none | R | ordinary create of R (subject to §12.2 parent check and §12.4 scope-lock) |
| L | none | nothing (remote has no candidate; local remains) |
| L, R with `L.Id = R.Id` | same entity ⇒ ordinary 3-way merge (§6/§7.3) |
| L, R with `L.Id ≠ R.Id` | **`ConstraintConflict`** — candidate: `Scope`, `Base` (baseline row in scope or null, with its Id), `Local = L`, `Remote = R`, both Ids. Live outcome per D9-T1: Base row (if any) stays; **neither** candidate is live (§9). |
| any live row in scope already covered by an Unresolved record | operation **rejected** (§12.4) |
| scope occupied only by a **tombstoned** note and R is a live note with a different Id | `ScopeOccupiedByTombstone` rejection (fail closed, no UNIQUE exception). Unreachable in v1 by construction: the only path that tombstones a note is the task cascade (`TaskCascadeHelper.cs:19-20`; `UpsertNoteAsync` never removes), and a tombstoned task cannot receive a new note. Documented, guarded, not "handled". |

### 7.3 Tombstone-wins in the pure core (T2.4 policy, D9-T5 evidence) [FROZEN]

Evaluated before any field merge, on `Provenance.IsDeleted`:

| B | L | R | Outcome |
|---|---|---|---|
| live | live | live | field merge (§6) |
| live | dead | dead | tombstone; provenance = greater `(Ticks, DeviceId)` side (both agree; deterministic pick); no evidence (D-1) |
| live | dead | live | tombstone wins; **`TombstoneConflict` evidence, `AutoResolution = AutoTombstone`, `AutoResult = Local` tombstone** (D-2/D-4), emitted only if `R ≠ B` on any field (otherwise remote made no competing claim) |
| live | live | dead | mirror of the above with Remote's tombstone |
| dead | dead | dead | no-op |
| dead | live | * or * | live | `MergeContractViolationException` — resurrection does not exist in the model (no code path un-tombstones; [FACT]) — fail closed, not a conflict |

`AutoLww` evidence (D9-T5): one `FieldConflict` candidate per case-5 field with `AutoResolution = AutoLww`, `AutoResult = winning value`. Emitting evidence never changes `MergedEntity.Result`.

### 8.4 Idempotency contract

| Situation | Behaviour |
|---|---|
| Staging: record with same `ConflictKey` exists (any status) | no-op (evidence already stored) — retry-safe (D5-G, D7-C). |
| Staging: no same-key record, but an `Unresolved` record with the same `ScopeKey` exists | **operation rejected** `ScopeHasUnresolvedConflict` (D9-T6). The partial unique index is the last line of defence; the code checks first so rejection is a typed outcome, not an exception. |
| Staging: no same-key record, a `Resolved` record with the same `ScopeKey` exists | new record allowed (a later, different conflict in a scope whose earlier conflict was resolved). |
| Resolution replay: record `Resolved`, request `(Kind, ResultFingerprint, ResultEntityId)` equal | no-op success (D7-C). |
| Resolution replay: record `Resolved`, request differs | rejected `MismatchedReplay` (never re-resolved; D7-D, D9-T5). |
| Resolution of an `AutoLww`/`AutoTombstone` record | rejected `NotResolvable` (D9-T5). |

`ConflictId` is minted **once** per new `ConflictKey` (`Guid.NewGuid()` at first insert) and is what a UI/resolution API addresses; `ConflictKey` is what retries collapse on. They are never interchanged (D7-A).

## 9. D9-T1 implementation recommendation

**Requirement [FROZEN]:** while a Structural/Constraint conflict is Unresolved, live = Base; with null Base the scope has no live row. Candidates are preserved in the record. `UNIQUE(TaskNotes.MaTask)` stays (D5-C). Epic-1: no hard DELETE on synced entities (enforced today only by `SyncStamper` converting `Deleted` → tombstone, `SyncStamper.cs:33-41`; [FACT] there is no raw DELETE anywhere, F-n).

**Who must withdraw what.** The remote candidate is never materialised (D9 §19) — nothing to withdraw. The local candidate is already live (it was created/edited locally before sync). Two shapes:

| Shape | Local candidate | Withdrawal needed |
|---|---|---|
| S1 Structural (`Base = A`, `Local = B`, `Remote = C`) | the existing row with `MaMonHoc = B` | rewrite the row to the **Base row** (ordinary update through the apply seam, provenance = Base's, `Rev++`). No delete of any kind. |
| S2 Constraint with `Base ≠ null` (`Base = N0`, `Local = N0'` same Id, `Remote = N2`) | `N0'` | rewrite `N0'` to `N0` (as S1). Only reachable through the tombstone-occupied path of §7.2, i.e. not in v1. |
| **S3 Constraint with `Base = null`** (`Local = N1`, `Remote = N2`, concurrent creates) | `N1`, a live row | the scope must end with **no live row**. This is the only shape that needs a mechanism. |

### 9.1 Mechanisms compared for S3

| Mechanism | Schema change | New state | Audited exception | Resurrection semantics | Extra invariant | Fatal problem |
|---|---|---|---|---|---|---|
| **M1 Tombstone N1** (ordinary `IsDeleted = 1`) | no | no | no | **yes** (KeepLocal must un-tombstone) | — | (a) `KeepRemote`/`ManualMerge(new Id)` insert into a scope still occupied by N1's tombstone ⇒ UNIQUE failure (F-d). (b) The tombstone is a **real change** in the ordinary stream (`Rev++`, `IsDeleted`): every peer receives "N1 deleted" and tombstone-wins makes that permanent even after KeepLocal resurrects it. Uses domain tombstones as staging state — contradicts D8-D and pre-empts OPEN-2. |
| **M2 Tombstone N1 + partial unique index** (`WHERE IsDeleted = 0`, F-m (c)) | **yes** (drop/recreate index on upgraded DBs) | no | no | **yes** | one live note per task (the partial index) | Fixes M1(a), not M1(b). Also changes the physical meaning of D5-C ("keep UNIQUE(MaTask)") for tombstones — arguably fine, but it is a DB-contract change on user tables (DbBackup gate) taken *only* to serve a staging trick. |
| **M3 Flag column on TaskNotes** (`StagedConflictId`) with every read path and the enumerator filtering it | **yes** (column on a user table) | **yes** (third row state) | no | no | "staged rows are invisible everywhere" | Touches every read path (`!IsDeleted` filters in 9 repositories), the enumerator, and still leaves N1 physically in the UNIQUE scope ⇒ same UNIQUE problem as M1(a) at resolution unless combined with M2. |
| **M4 Change N1.MaTask to a parking value** | no | yes | no | no | — | FK to `StudyTasks` (F-i) rejects it; also invents data. Not viable. |
| **M5 Audited hard delete of N1 inside the staging transaction, evidence-first** | no | no | **yes** (one method, one row class) | no (re-materialisation is an ordinary `Add` through the apply seam) | "a synced row may be hard-deleted only if its full snapshot + Rev were written to an Unresolved ConflictRecord in the same transaction" | Loses `Rev` continuity for N1 — mitigated by storing `LocalRowRev` and restoring it (`Rev` is local-only, so this is legitimate); `SyncBaseSnapshots` rows for N1 held for *other* peers become dangling (harmless: the enumerator iterates live rows, and a re-inserted N1 with `Rev = LocalRowRev + 1` is emitted again). |

### 9.2 Recommendation: **M5** [ENG, requires ACK A1]

Only M5 satisfies all of: live = Base literally (no row), all four resolutions materialise without touching the index (F-d), no fake delete enters the ordinary change stream, no new row state, no schema change, no resurrection path added to a model that has none. The exception is "absolutely required" in the owner's sense because every no-hard-delete alternative either leaks a domain tombstone as staging state (M1/M2 — a semantic contamination, not an engineering nuisance) or adds a third row state plus a schema change on user tables (M3).

Exact shape:

```csharp
// Sync/Apply/ConflictStaging.cs — the ONLY production site allowed to issue a physical DELETE.
// Epic-1 exception, audited: docs/review/2026-09-08-t2.3-t2.4-engineering-dor.md §9.
internal static Task HardDeleteWithdrawnCandidateAsync(AppDbContext db, Guid taskNoteId, CancellationToken ct)
    => db.Database.ExecuteSqlInterpolatedAsync($"DELETE FROM TaskNotes WHERE Id = {taskNoteId}", ct);
```

Preconditions enforced in `ConflictStaging` (fail closed if any is false): the caller is inside the staging transaction; the ConflictRecord row for this scope with `LocalWithdrawal = 2`, `LocalSnapshotJson`, `LocalRowRev` has already been added to the tracker *and* will be saved in the same `SaveChanges`; the target row is a `TaskNote`; its `Id == record.LocalEntityId`; it is not tracked (loader used `AsNoTracking`, §11.3). Raw SQL is used deliberately so `SyncStamper` is not taught a "real delete" mode — the HIGH seam stays smaller (D9 §20 "audited exception", not a silent shortcut).

**Audit fence test** (§17): a test scans `SmartStudyPlanner/**/*.cs` for `DELETE FROM` / `ExecuteDelete` and asserts the only hit is that method; F-n proves it is red-capable today by construction (add a second `DELETE FROM` anywhere ⇒ red).

What M5 requires, stated explicitly per the brief: schema change **no**; new state **no** (`LocalWithdrawal` is a column on the *conflict* table, not domain state); audited exception **yes** (A1); resurrection semantics **no**; additional invariant **yes** (evidence-before-delete, same transaction).

## 10. Apply seam design (OPEN-3)

### 10.1 Mechanism [ENG]: per-entry intent marker, not a batch flag

```csharp
// Data/AppDbContext.cs (additions)
public enum SyncApplyIntent { PreserveProvenance = 1 }
private readonly Dictionary<object, SyncApplyIntent> _syncApplyIntents = new(ReferenceEqualityComparer.Instance);
public void MarkSyncApplied(object entity) => _syncApplyIntents[entity] = SyncApplyIntent.PreserveProvenance;

public override int SaveChanges(bool acceptAllChangesOnSuccess)
{
    try { SyncStamper.Apply(ChangeTracker, Clock, DeviceIdProvider(), _syncApplyIntents); return base.SaveChanges(acceptAllChangesOnSuccess); }
    finally { _syncApplyIntents.Clear(); }
}
// SaveChangesAsync identical.

// Data/SyncStamper.cs (new overload; existing 3-arg overload delegates with intents = null → byte-identical behaviour)
public static void Apply(ChangeTracker tracker, Func<DateTime> utcNow, string deviceId,
                         IReadOnlyDictionary<object, SyncApplyIntent>? intents)
{
    foreach (var entry in tracker.Entries().ToList())
    {
        if (entry.Entity is not ISyncMetadata meta) continue;
        if (intents is not null && intents.TryGetValue(entry.Entity, out _))
        {
            if (entry.State == EntityState.Deleted)
                throw new InvalidOperationException("sync-apply must set IsDeleted explicitly; Remove() is not allowed on a marked entry");
            if (entry.State is not (EntityState.Added or EntityState.Modified)) continue;
            if (meta.ModifiedAtUtc == default || string.IsNullOrEmpty(meta.ModifiedByDeviceId) || (meta.IsDeleted && meta.DeletedAtUtc is null))
                throw new InvalidOperationException("sync-apply entry carries incomplete provenance");
            meta.Rev++;                                   // local counter only (§11)
            continue;                                      // ModifiedAtUtc / ModifiedByDeviceId / IsDeleted / DeletedAtUtc untouched
        }
        /* existing Added/Modified/Deleted branches, unchanged */
    }
```

## 11. Rev and baseline design (OPEN-4)

### 11.1 Rules [FROZEN where marked, ENG otherwise]

1. `Rev` is local-only; never serialized (§5.1), never compared across devices, never a tie-break (**FROZEN**, D9 §21).
2. The pure core neither reads nor produces `Rev` (`Provenance` has no Rev field — enforced by the type, §4.1) (**FROZEN**, C-3).
3. A successful apply write increments local `Rev` exactly once via the marked seam path (§10.1) [ENG].
4. A no-op merge (`IsNoOp`) writes nothing; the entity is left `Unchanged`, so `Rev` is untouched. The session must not force `Modified` [ENG; needed for E-3 idempotent replay].
5. `KeepRemote` never copies the remote `Rev` (there is none in the snapshot to copy) (**FROZEN**, D9 §21).

### 11.2 Baseline must record the POST-apply local Rev

Within the same transaction, after `SaveChangesAsync` (which performed `Rev++`), the session reads `entity.Rev` from the tracked instance and upserts `SyncBaseSnapshots(peer, type, id) = (Rev = entity.Rev, SnapshotJson = canonical(post-apply live row), SyncedAtUtc)`. A second `SaveChangesAsync` in the same transaction commits the baseline rows; the domain entities are `Unchanged` by then, so nothing is re-stamped (this is why two saves are acceptable; the alternative — predicting `Rev+1` before the first save — couples the session to stamper internals).

**No re-emission proof:** after commit, `row.Rev == baseline.Rev` for that peer; `SyncChangeEnumerator`'s predicate is `row.Rev > snapshot.Rev` (`SyncChangeEnumerator.cs:30`), so the row is not enumerated for that peer until a genuine local edit bumps `Rev` through the ordinary path. Test: apply → enumerate for same peer → empty.

Per outcome:

| Outcome | Live row after tx | Baseline row for this peer |
|---|---|---|
| merge applied (create/update/tombstone) | merged state, `Rev = old + 1` (or 1 on create) | `(Rev_post, canonical(merged))` |
| no-op | untouched | `(Rev_current, canonical(current))` if the baseline was missing/older; otherwise untouched |
| Structural conflict staged (S1) | Base row, `Rev = old + 1` | `(Rev_post, canonical(Base))` |
| Constraint conflict, S3 (hard delete) | no row | no baseline row for N1 (Base was null ⇒ none existed for this peer); nothing written |
| operation rejected (scope-lock, missing parent, baseline unreadable) | untouched | untouched (rolled back) |

### 11.3 Entity ⇄ snapshot boundary [ENG]

`Sync/Apply/EntitySnapshotMapper`: per entity, a hand-written `ToSnapshot(entity)` and `ApplyTo(entity, snapshot)` pair over the registry (no reflection at runtime; the registry guard test is the reflection). Loading for the merge uses the raw DbSets **`AsNoTracking()`** (F-b is the hazard; two `AsNoTracking` usages already exist in production, so the pattern is native). Writing attaches or loads a tracked instance only for rows the session will write.

### 11.4 `SyncBaseSnapshotStore` change (PR-3) [ENG]

Add `Upsert(AppDbContext db, …)` (synchronous tracker mutation, **no** `SaveChanges`) and re-implement `SetAsync` as `Upsert` + `SaveChangesAsync` so the existing T1.4 tests stay green. The session calls `Upsert` only. This removes the self-save hazard (F-g) without changing the T1.4 contract.

## 12. Transaction design (D8-G, D9 §18)

### 12.1 Unit: one logical operation = one transaction [FROZEN]

`Sync/Apply/SyncApplySession` owns **one** `AppDbContext` created from the composition root's factory (`ServiceLocator.cs:54`, so `DeviceIdProvider` is the persisted identity) for the whole run, and opens one `BeginTransactionAsync` per logical operation:

```text
for each logical operation (ordered §12.5):
    BEGIN
      load Base (baseline row) / Local (live raw DbSet, AsNoTracking) / Remote (change set)   → EntitySnapshots
      pure merge  (§6/§7)                                                                     → MergedEntity / candidates
      parent check (§12.2), scope-lock check (§12.4)
      apply result to tracked instance(s) via MarkSyncApplied  OR  stage conflict (§8, §9) OR reject
      SaveChangesAsync                                                                         (Rev++ on marked)
      baseline Upsert (§11.2) ; SaveChangesAsync
    COMMIT
    on any exception: ROLLBACK, record ApplyOutcome.Failed(op, reason), continue with next op
```

A logical operation is: one entity (create/update/tombstone) **plus** its mandatory cascade tombstones (§12.3) **plus** its evidence rows **plus** its baseline rows; for a constraint scope, the whole scope (both candidates) is one operation. Independent operations never share a transaction (a TaskNote conflict never rolls back a StudyLog apply).

Repositories are not used anywhere in the session (F-h: they create their own contexts and cannot join the transaction). The session reads and writes raw DbSets only, so tombstones are visible (as `SyncChangeEnumerator` already requires).

### 12.2 Parent handling at apply [D9-T4 FROZEN for D4 targets; ENG extension for FK-only children]

For every live row the session is about to write (create **or** update), check each parent reference:

| Reference | Parent live | Parent tombstoned | Parent missing |
|---|---|---|---|
| `MonHoc.MaHocKy`, `StudyTask.MaMonHoc` (D4) | apply | **`StructuralConflict(ParentTombstoned)`** staged (§8): Base/Local/Remote = the child's rows; live = Base row if Base exists, else no live row (Base = null ⇒ the incoming child is simply not materialised). Never a live orphan. [FROZEN] | **deferred** to the end of the run (ordering §12.5); if still missing ⇒ `Rejected(MissingParent)`, no record (nothing to resolve; the parent may arrive next run). [FROZEN: fail-closed/deferred] |
| `TaskNote.MaTask`, `TaskReferenceLink.MaTask` (FK-enforced, no reparent semantics — copy-on-create) | apply | **cascade tombstone**: the incoming row is materialised *as a tombstone* with the parent's tombstone provenance, with `TombstoneConflict/AutoTombstone` evidence if the incoming row was live. [ENG derivation: the Epic-1 cascade rule "deleting a task tombstones its notes + links" (`data-model.md:87`, `TaskCascadeHelper`) is the only outcome under which every resolution kind stays valid — a StructuralConflict here would offer KeepLocal/KeepRemote that both re-create a live child under a dead parent, which is invalid, leaving KeepBase(null) as the only legal choice.] **ACK A2-a.** | deferred, then `Rejected(MissingParent)` [ENG: same rule as D4 targets; FK would reject the insert anyway (F-i), and a typed rejection beats a `SqliteException`]. |
| `StudyLog.MaTask` (no FK, F-i; logs survive task deletion today — `TaskCascadeHelper` does not touch logs) | apply | **apply as-is** (a live log under a tombstoned task is the *current* local model; analytics/ML read them). No evidence. [FACT-based] | deferred, then `Rejected(MissingParent)` [ENG]. |

Both peers evaluate parent liveness on their own live state; with tombstone-wins already applied to parents in the same run (§12.5 order) the two evaluations agree.

### 12.3 Cascade tombstones generated locally [ENG; ACK A2-b]

When a remote parent tombstone is applied, the session loads the parent's **live local children** through raw DbSet queries by FK (not navigation `Include`, which only reaches loaded children — the documented Epic-1 gap) and tombstones them in the same transaction via the marked path. Provenance written on those children: **the parent's tombstone provenance** (`DeletedAtUtc`, `ModifiedAtUtc`, `ModifiedByDeviceId` copied from the parent). Rationale: the causal event is the parent's deletion; copying its provenance makes both peers write identical bytes (convergence), whereas local-now stamping would differ per device. Alternative (local clock/device) is deterministic per device but not across devices; not recommended. Children that had local changes vs baseline get `TombstoneConflict/AutoTombstone` evidence (D9-T5 "delete-vs-edit evidence"). Grandchildren (task → note/link) cascade the same way.

### 12.4 Scope-lock [ENG, derived from D9-T1 + D9-T6]

Before applying anything into a logical scope (`ScopeKey`, §5.3 — for entities the entity itself, for TaskNotes also the `MaTask` scope), the session checks for an `Unresolved` record on that scope. If one exists and the incoming operation is not the identical `ConflictKey` (no-op), the operation is **rejected** (`ScopeHasUnresolvedConflict`). Reason: any other write would make live ≠ Base while Unresolved, violating D9-T1; rebase is explicitly not v1 (D8-H). This is a consequence, not new policy.

### 12.5 Ordering within a run [ENG]

1. Parent tombstones first, top-down: HocKy → MonHoc → StudyTask (so §12.2 evaluates against already-applied tombstones).
2. Creates/updates top-down: HocKy → MonHoc → StudyTask → {StudyLog, TaskNote scopes, TaskReferenceLink}.
3. Deferred-parent retry pass (one pass; anything still missing is rejected).

### 12.6 Isolation

SQLite is single-writer; `BeginTransactionAsync()` (Serializable default) is sufficient. A concurrent `LuuHocKyAsync` from the UI waits on the busy timeout — see §15 for why this must not happen in v1.

## 13. Resolution / drift design (D6-H, D8-E, D8-H)

### 13.1 API [ENG]

`Sync/Apply/ConflictResolver.ResolveAsync(Guid conflictId, ResolutionRequest req, CancellationToken)` with `ResolutionRequest(ResolutionKind Kind, EntitySnapshot? ManualResult, Guid? ManualResultEntityId)`; returns `ResolutionOutcome ∈ { Applied, NoOpReplay, Rejected(reason) }`. One transaction per call.

### 13.2 Sequence

```text
BEGIN
  rec := load SyncConflictRecords by ConflictId (not found ⇒ Rejected(UnknownConflict))
  if rec.Kind is auto (AutoLww/AutoTombstone) ⇒ Rejected(NotResolvable)                        (D9-T5)
  if rec.Status == Resolved:
        request fingerprint == (rec.ResolutionKind, rec.ResultFingerprint, rec.ResultEntityId) ⇒ NoOpReplay   (D7-C)
        else ⇒ Rejected(MismatchedReplay)                                                     (D7-D)
  -- drift check (D8-H): re-read CURRENT live state of the scope from raw DbSets, AsNoTracking
  liveFp := fp(current live row(s) in scope)   // no live row ⇒ "null"
  if liveFp != (rec.BaseFingerprint ?? "null") ⇒ Rejected(LiveStateDrift)                     (no force, no rebase)
  -- materialise
  KeepLocal  : result = rec.Local  , id = rec.LocalEntityId
  KeepRemote : result = rec.Remote , id = rec.RemoteEntityId
  KeepBase   : result = rec.Base   , id = rec.BaseEntityId        (null ⇒ nothing to write; D7-G)
  ManualMerge: result = req.ManualResult (validated §5.5), id = req.ManualResultEntityId (required; must be Local/Remote/Base id or a fresh Guid)
  parent check (§12.2) and scope-lock (§12.4, this record excluded) on the result
  write result: existing row ⇒ update fields+tombstone block; absent row ⇒ Add (for S3 KeepLocal: Rev seeded from rec.LocalRowRev before the seam's ++)
  update rec: Status=Resolved, ResolutionKind, ResultEntityId, ResultSnapshotJson, ResultFingerprint, ResolvedAtUtc=Clock(), ResolvedByDeviceId=DeviceIdProvider()
  SaveChangesAsync
COMMIT   (evidence columns untouched — trigger §8.3 would abort otherwise)
```

### 13.3 ManualMerge identity [FROZEN result, ENG rule]

`ManualResultEntityId` is mandatory. Allowed values: `LocalEntityId`, `RemoteEntityId`, `BaseEntityId`, or a Guid that does not exist in the target table (checked; collision ⇒ `Rejected(ResultIdInUse)`). For constraint scopes the result row's `MaTask` must equal `ConstraintValue` (checked; §5.5 contract).

### 13.4 Provenance of the resolution result [ENG; ACK A2-c]

The result is written as an **ordinary local write** (no `MarkSyncApplied`): `SyncStamper` stamps `ModifiedAtUtc = now`, `ModifiedByDeviceId = this device`, `Rev++`. Rationale: a resolution is a decision made *here, now*; D8-F says the result becomes ordinary synced state, and stamping it locally lets it win LWW against any stale concurrent edit elsewhere. The candidate's original authorship stays in the immutable evidence. Alternative (preserve the chosen candidate's provenance for KeepLocal/KeepRemote) is deterministic too but makes a human decision lose LWW to an older automatic edit; not recommended.

### 13.5 Baseline after resolution

Not advanced for the peer (left at Base). The resolved row then enumerates to the peer as an ordinary change (`Rev` above baseline), which is exactly what should carry the decision across — subject to §13.6.

### 13.6 v1 limitation stated plainly (OPEN-2 / D7-H)

The peer holds its own `Unresolved` record for the same scope (both sides stage symmetrically, §5.3). Its scope-lock (§12.4) will **reject** the incoming resolved row until that record is resolved on the peer. Without a propagation protocol, two-device convergence *after* a human resolution is therefore not guaranteed in v1 and must not be claimed by T2.5. M2.1 is "merge engine, no network"; T2.5 property tests should model resolution on one device and assert single-device invariants (live = Base while unresolved; result valid after resolution; replay no-op; drift rejected). This is stated, not solved, here.

## 15. Runtime sequencing constraint (F-j; not redesigned here)

**What breaks [FACT-based reasoning]:** the running app holds the whole `HocKy` graph in view-models for the session (`MainWindow.xaml.cs:139`, `SetupViewModel.cs:48`) and every add/edit/complete/delete re-saves it through `LuuHocKyAsync`, which (a) copies **all scalar values** from the in-memory objects onto tracked rows (`CopySyncSafeValues`, `SqliteHocKyRepository.cs:224-241`) and (b) **tombstones rows absent from the in-memory graph** (lines 153-164, 183-189). If a sync apply commits while the graph is held, the next UI save silently (a) reverts merged field values to the stale in-memory ones and (b) tombstones every remotely-created `MonHoc`/`StudyTask` under that semester — i.e. undoes the apply and emits fake deletes. Additionally the read-side dedup (`LayDanhSachHocKyAsync:42-76`) rewrites `task.MaMonHoc` on load and the next save persists it, which can rewrite a merged structural field.

**v1 entry constraint for T2.4 (M2.1):** the apply session runs only from a test harness or a headless entry point while **no** `AppDbContext`-backed UI graph is loaded — M2.1 is "merge engine, no network", so this is satisfied trivially and **M2.1 is not blocked**.

**M2.2 (transport / live app) — blocked until both exist:** (1) a gate that refuses to start an apply run while the app holds a semester graph with unsaved edits, and (2) a forced graph reload (`LayDanhSachHocKyAsync` → VM refresh) after every apply run before any `LuuHocKyAsync` may execute. Both are UI/lifecycle changes outside T2.3/T2.4 and are M2.2 entry criteria, not v1 work. The dedup-on-read mutation is a third M2.2 item (make the representative deterministic or stop mutating on read).
