## 3. Verdict

### `block`

Not because the slice is unsafe — **there are no BLOCKER findings**. Nothing here permits an invalid
mutation, corrupts the fence contract, or crosses a mandatory safety boundary. The failure modes are
**over-blocking** (H-1, H-3), **lost `Passed` evidence** (H-2), and **misreported stage/effect** (M-1).

It is `block` rather than `ship-with-followups` because H-2 is a ~1-line fix that makes two
owner-ratified test rows (P-CR-5, P-PT-5) passable, and H-1 and H-3 would each ship a known
false-rejection path into the Slice-4/5 baseline. Fixing them now is cheaper than fixing them under a
wired executor.

## 4. Strengths

These are real and should survive the fixes.

- **`StructuralDependencyRegistry` is the strongest component in the slice.** Explicit edges, no
  structure derived from naming conventions, a static constructor that fails closed on an incomplete
  configuration, and a guard test reconciling three independent sources: EF's `OnDelete(Cascade)` in
  *both* directions (no missing edge, no phantom edge), `MergeSurfaceRegistry` field classes, and
  behavioural agreement with `SyncApplySession`'s own staged ScopeKeys. `StudyLog` is registered
  non-cascading with an explicit "has no FK at all" assertion. **No finding.** (OBSERVED)
- **The router's core contract is met.** `RouteKnown` gates before any DB read as a precondition, not
  an early exit. Every selected record is evaluated — no `break`, no `return` inside the loop, no
  `Blocked` short-circuit. `Aggregate` sorts **after** all results are collected, on all three keys
  `(Stage, ScopeKey ordinal, ConflictId)` with `StringComparer.Ordinal`. `FencePassed` requires
  `RouteKnown` and treats `Unsupported` as non-passing; an empty request passes vacuously (N-9).
  (OBSERVED)
- **N-3 is handled precisely, which is the hard part.** The catch is
  `when (ex is SnapshotContractException or JsonException)` — narrow enough not to convert
  infrastructure failures — and it is placed around `Derive` only, with **both DB awaits outside it**,
  so a database failure cannot become `Unsupported`. `policy.Evaluate` is deliberately outside. Two
  further throw sites are verified unreachable rather than left latent:
  `ConstraintOccupancyFencePolicy.Derive`'s `Guid.ParseExact` is gated by the classifier's
  `TryParseExact`, and `AbsentLocalParentTombstonePolicy.ExpectedParentType`'s throw by
  `IsKnownStructuralField`. (INFERRED from code read at final state)
- **The read-only proof is properly discriminating.** Zero saves *and* empty `ChangeTracker.Entries()`
  *and* byte-identical table snapshots, over both a `Blocked` and a `FencePassed` scenario, plus
  per-component isolation tests, plus a source scan whose every regex carries a non-vacuity
  self-check. The `ChangeTracker` assertion beside `SaveCount` is exactly the right second axis: a
  save of zero pending changes would otherwise look identical to no save. (OBSERVED)
- **Two tests are explicitly built against the trap of a weaker assertion passing.**
  `X1_ConstraintResult_IsBlockedScopeReleased_NotThePassedEmptyScopeBranch` pins the exact rule id so
  the OD-4 empty-scope branch cannot silently absorb an occupied scope while the aggregate still reads
  "not FencePassed". And the X-3 redesign described in the PR body is a genuine improvement whose
  reasoning checks out: the selector's own `OrderBy(ConflictId)` would otherwise give the "sort
  omitted" mutant a coin-flip, and the adversarial-`ConflictId` test removes the luck. (INFERRED)
- **Owner rulings are honoured and correctly *scoped*.** SB-3/OD-3 blocks the held row only — verified
  not expanded into an entity, parent, ancestor, descendant or subtree lock, and no PR-6 fingerprint
  touched. OD-4 returns `Passed` as this policy's contribution only. No `FencePendingDecisions` type
  exists. No diff to `ConflictResolver`, `ConflictStaging`, or the D8-H fingerprint code. (OBSERVED)
- **Slice-1 is consumed without semantic drift.** Dispatch by classified shape through
  `FencePolicyRegistry`; contract, evidence and identity inputs passed unmodified; no reinterpretation
  of `NotApplicable`/`Passed`; no `Unsupported`↔`Blocked` conversion. The router adds no semantics of
  its own. (INFERRED)

### [HIGH] H-2 A conflict reachable only as an edge *parent* endpoint escapes selection

**Location** `SmartStudyPlanner/Sync/Fence/ConflictDependencySelector.cs:56`.

**Evidence (REPRODUCED)** — S1-PT staged on StudyTask `T`; an `ImpactSet` containing one
`ImpactEdge(TaskReferenceLink, link, "MaTask", ParentId: T, Added)` → `SelectAsync` returns
**0 records**. Line 56 feeds only `edge.ChildType` / `edge.ChildId` into the predicates;
`edge.ParentId` never reaches `entityIds` or `scopeKeys`.

**Expected** — plan §11.2 note: "T's policy is invoked because T is *named by an edge*, not because of
ancestry, and it passes"; §16.1 P-CR-5 / P-PT-5 key assertion "Passed entry present in result list";
§11.2 rows "delete N", "reparent N", "delete sibling N2".

**Why it matters** — both S1 policies carry a
`foreach (edge) if (edge.ParentId == e.EntityId) ⇒ Passed *.ChildEdgeOnly` branch. It is
**unreachable from the router**: a tested Slice-1 code path is dead in integration, and the fence
drops exactly the evidence that spec §3.3's "relevant ≠ violates" distinction is built on.

**Blast radius is bounded — enumerated, not assumed (INFERRED):** S1-CR/S1-PT run the row loop first
and reach the edge loop only for a parent-endpoint-only impact (⇒ `Passed`); AL-PT's `HeldParentId`
leg scans `Rows`, not `Edges`; Constraint consults `Scopes` and `Rows` only. **No `Blocked` outcome
today is reachable only through an edge parent.** The cost is lost `Passed` evidence, two dead
branches, and P-CR-5/P-PT-5 unpassable — not a present fail-open.

**Reachability** — proven (selection gap); latent (fail-open, if any future policy blocks on a parent
endpoint).

**Minimal correction** — `entityIds.Add(edge.ParentId)` in the `:56` loop. The identity predicate
suffices: S1 records always populate `EntityId`. A ScopeKey leg (parent type via
`All.FirstOrDefault(e => e.ChildType == edge.ChildType)?.ParentType`) is an index optimisation, not a
correctness requirement. Add a test asserting the record is selected **and** returns
`*.ChildEdgeOnly`.

### [HIGH] H-3 Intents are resolved against live DB state in isolation, inventing cascade over rows a sibling intent removes from the envelope

**Location** `SmartStudyPlanner/Sync/Fence/ImpactResolver.cs:101`, `:144-148`.

**Evidence (REPRODUCED)** — request `[Reparent(StudyTask T, MaMonHoc M1→M2), Tombstone(MonHoc M1)]`,
with T live under M1 and one TaskNote N under T:

```
row       MonHoc    M1   Tombstoned
row       StudyTask T    Reparented
row       TaskNote  N    CascadeTombstoned      <-- false
scope     TaskNote|MaTask=T  Released           <-- false
lifecycle MonHoc    M1   Tombstone
lifecycle StudyTask T    Tombstone              <-- false; contradicts T's own Reparented row
lifecycle TaskNote  N    Tombstone              <-- false
```

The executing path does the opposite (OBSERVED in
`SqliteHocKyRepository.LuuHocKyAsync`): it reparents surviving tasks off the doomed FK **and runs
`DetectChanges()` before** `db.MonHocs.Remove(oldMon)`, precisely so T is not swept; and
`TaskCascadeHelper.RemoveChildrenAsync` is called only for tasks absent from the new graph, so N is
untouched. **T and N are not in the real write set.**

**Expected** — spec §3.1 "[D] Actual cascade, not invented closure"; plan INV-2; spec §13.5 and
acceptance criterion 5.

**Why it matters** — a Constraint record on `K(T)` returns `Blocked CONS.ScopeReleased` for a save
that never touches the note: a **false Blocked**. Under OD-2/L1 a local save is a whole-semester
compound save, so one false block rejects the entire save. T's `Reparented` row surviving at all is
luck, not design — it depends on the `Rank` tie-break in M-1.

**Reachability** — proven at resolver level; production-shaped once Slice 4 wires local save. This is
exactly the documented load-time-dedup shape: plan §4.1 row 2 records that dedup "persists that as an
implicit **reparent** plus a clone **delete**" (R-6 / OD-8). OD-8 prices the *reparent* blocking — a
true positive. It does **not** price this descendant over-reach.

**Minimal correction** — resolve the request as a unit: exclude rows a `Reparent` intent moves *out
of* a tombstoned parent's subtree (and their descendants) from the cascade walk, or walk the cascade
over the intent-adjusted graph rather than raw DB state. Add the `[Reparent, Tombstone(old parent)]`
envelope test, and an `ImpactSet` self-consistency assertion (no id may be `Reparented`/`Created` in
`Rows` while `Lifecycle` says `Tombstone`).

### [MEDIUM] M-1 Row-effect precedence is inverted and intent-order dependent; the direct/cascade distinction is lost

**Location** `ImpactResolver.cs:46` (`Rank`), `:122` (`visited.Add` early return).

**Evidence (REPRODUCED)** — same logical request, two intent orders:
`[Tombstone(M), Tombstone(T)]` ⇒ T = `CascadeTombstoned`;
`[Tombstone(T), Tombstone(M)]` ⇒ T = `Tombstoned`.

Two mechanisms, one defect: (a) `:122` returns early for a row already visited as a cascade child,
discarding the *direct* intent entirely; (b) `:46` ranks `CascadeTombstoned` as **weakest** (0) with
everything else 1 and first-wins among equals, so a tombstone loses to a `FieldsChanged`/`Reparented`
written earlier.

**Expected** — plan §7.3: "Deduplicate rows by `(EntityType, EntityId)`, **keeping the strongest
effect**". Plan §16.1 distinguishes `@DirectSubject` (P-PT-2) from `@CascadeReached` (P-PT-3). No
canonical source defines the implemented 2-level rank — it is invented.

**Why it matters** — `RoutingStage` is the **primary sort key** of `FenceRouter.Aggregate`, so intent
order changes the reported stage, rule id and result ordering for a logically identical request. X-3
varies record *insertion* order only and cannot see this.

**Reachability** — proven; and the combination is production-reachable: the local reconcile diffs
tasks **flat across the whole HocKy** (`oldTasksByMaTask` / `newTasksByMaTask`,
`SqliteHocKyRepository`), so deleting a MonHoc makes its tasks absent too and the planner emits
`Tombstone(MonHoc)` **and** `Tombstone(StudyTask)` in one request — MonHoc loop first, which is the
order that swallows the direct intent.

**Minimal correction** — define an explicit total order over `RowEffect` (tombstone strongest, direct
above cascade) and apply it in `AddRow`; make `ExpandTombstoneAsync` upgrade an existing
`CascadeTombstoned` row to `Tombstoned` when re-entered as `isDirect: true` instead of returning
early. Add an order-permutation test.

### [MEDIUM] M-3 The live-only cascade predicate is undecided, and the PR's stated justification is falsified by the tree

**Location** `ImpactResolver.cs:206-224` (`LiveChildIdsAsync`, `!IsDeleted`).

**Evidence** — the PR body justifies live-only with "a row protected by an unresolved conflict is live
by construction (D9-T1)". The tree contradicts this: plan §16.3 **P0-c** states the present-day W-2
crossing outcome as "T tombstoned, record Unresolved, `Matches == false`", and W-2/F-2 is **MEASURED**.
A held-at-Base row *can* be dead while its record is Unresolved. (INFERRED from primary source.)

**Second leg, outcome-changing (INFERRED)** — an S2 record on `K(t)` (`BaseEntityId` set ⇒
`Form = BasePresent`) whose occupant note `N0` is present but `IsDeleted = true` — a state the plan
acknowledges (R-9 / D-1: a tombstoned note occupies the unfiltered `UNIQUE(MaTask)`). On
`Tombstone(StudyTask t)`: `LiveChildIdsAsync` skips N0 ⇒ **no `Released(K)` emitted** ⇒ the record is
still selected (rows contain `t` ⇒ `constraintValues.Add(t)`) ⇒ `ConstraintOccupancyFencePolicy` finds
no matching scope, sees `t` tombstoned, and returns **`Passed CONS.EmptyScopeParentTombstoned`** — a
branch that never checks `Form == BaseNull`, on a mutation OD-4 governs only for *empty S3* scopes.
The policy branch is **pre-existing Slice 1** and is not to be changed here; the *mechanism* is Slice
2's predicate.

**Expected** — plan §7.3: query children "with **the same predicate the executing path uses**". Two
executing paths disagree: the sync cascade is live-only
(`SyncApplySession.cs:595, 603, 611, 614`); the local path loads the old graph **unfiltered** and
`TaskCascadeHelper` has no filter (plan §4.2). Plan §7.4 explicitly defers the resolution to **Slice-0
measurement P0-a, which has not been run.**

**Why it matters** — under the local path the resolver *under*-models rows the executing path really
writes; a re-stamp of a held-at-Base row drifts the D8-H fingerprint (owner rulings §7, E-2) ⇒ W-1 —
the exact harm SB-3 was ruled to prevent, arriving through a different door.

**Cost of the obvious alternative, so whoever rules can price it** — an unfiltered cascade emits
`Released(K)` for already-dead notes, flipping OD-4-adjacent cases to `Blocked CONS.ScopeReleased`.
"Just unfilter it" is not free. An origin-conditional predicate is also out: it would break X-5 origin
equivalence.

**Reachability** — latent. PR-6 DoR §2.1 records S2 as unreachable in v1; sync is unwired, so no
ConflictRecord can exist in production today (plan §18).

**Classification** — **specification ambiguity** for the predicate itself, plus a defect in the PR's
recorded rationale. See §9 Q-1.

## 10. Final notes

PR #93 is a careful, well-tested slice that gets the hard parts right — no early exit, no semantic
priority, a genuinely read-only orchestration layer, a correctly narrow N-3 boundary, and a
registry-plus-guard-test pattern that is the best structural work in the fence so far. Its defects are
not in the parts the mission warned would be hardest; they are in the seams **between** layers, where
each component is individually defensible and the composition loses information: the selector never
sees an edge's parent, the resolver never sees that one intent changes another's envelope, and the
effect merge never decides what "strongest" means. That is why 942 green is compatible with three
HIGH findings, and why the probes that found them all went RED on the first run.

None of it is unsafe — the fence over-blocks and under-reports rather than letting anything through —
so this is `block` on economics, not on risk: four bounded fixes now, against a Slice-4/5 baseline
that would otherwise inherit two known false-rejection paths and a dead Slice-1 branch. The two owner
questions are genuine source conflicts, and Q-2 in particular gates Slice 5 regardless of what this PR
does next.

## Decisions made

### Reviewing at the PR head rather than the PR description

*Why it had to be made* — the PR body is unusually thorough and self-critical, which makes it tempting
to review the narrative instead of the code. Three of the six findings that carry this verdict (H-1,
H-3, M-1) are invisible from the description; one (M-3) exists only because the description's stated
justification could be checked against the tree and turned out to be falsified.

*What it's for* — keeping "the implementer documented it" from functioning as "the implementer
resolved it". A documented engineering decision is a disclosure, not an authorisation.

*Experience for future development* — when a PR body volunteers a judgement call, check the premise it
rests on before accepting the call. Here the premise ("a protected row is live by construction") was
contradicted by a MEASURED result already in the repo.

### Reproducing four findings in a throwaway worktree instead of reporting them by inspection

*Why it had to be made* — `docs/review/README.md` requires that a claim setting another package's
severity be measured first, and all three HIGH findings set severity. Inspection alone would have
left them arguable, and one (H-1) was found only because a probe was written for something else.

*What it's for* — the distinction between "I read the code and believe X" and "I ran it and X
happened". The probe outputs are quoted verbatim above so a later reader can re-derive them.

*Experience for future development* — the probes cost about fifteen minutes and changed the verdict.
Writing the smallest possible failing test is cheaper than arguing about whether a gap is reachable,
and it produces the fix's first test for free. A probe that goes RED on first run is also, by
construction, proof that the existing suite did not cover it.

### Skipping one reproduction deliberately and saying so

*Why it had to be made* — the `AsNoTracking()` claim (L-4) could have been reproduced by mutating
`ImpactResolver`, but inspection gives a *stronger* result: every query there projects to an anonymous
type or scalar, so EF tracks nothing either way, which means no RED/GREEN outcome exists to observe.

*What it's for* — not padding the "independently reproduced" list with a check that cannot fail.

*Experience for future development* — "I did not reproduce this, and here is why reproduction would
prove less than the reading" is a legitimate and more informative result than a green run. The
substantive finding was not the wrong comment but what the comment concealed: the read-only property
rests on projection shape, which nothing guards.

### Reporting the two source conflicts instead of resolving them

*Why it had to be made* — Q-1 and Q-2 are contradictions between authoritative sources (plan §7.3 vs
two executing paths; plan §6's RouteKnown definition vs plan §6's own intent table). The project's
precedence rule makes resolving those an owner act, not an implementer's or a reviewer's.

*What it's for* — preventing a review from silently becoming a ruling, which is how the SB-3 tension
would have been "solved in code" had it not been escalated.

*Experience for future development* — an implementation defect and a specification gap look identical
from inside the code. The tell is whether a correct answer can be derived from the sources: H-2 and
H-3 have one and are defects; H-1 and M-3 do not and are escalations. Separating them stopped H-1
from being filed as an implementer error when the implementer followed the plan's literal text.

### Filing under `docs/review/` with this folder's verdict vocabulary

*Why it had to be made* — the commissioning brief specified its own verdict words ("CHANGES
REQUIRED"), which are not the ones this repo greps for.

*What it's for* — `docs/review/README.md` requires the per-artifact vocabulary verbatim so a later
reader can find it. The mapping is stated in §0 so neither reader is misled.

*Experience for future development* — when an external brief and a repo convention disagree on
formatting, satisfy the repo and record the mapping. The brief's structure survives underneath; only
the grep-able token has to match the house rule.
