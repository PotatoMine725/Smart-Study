## What's correct (confirmed)

- **`MonHocIdentity.Normalize`** — `NFC → Trim → collapse internal whitespace → ToLowerInvariant`,
  **diacritics preserved** (`"Toán" == "toán "` but `"Toán" != "Toan"`), `null`/whitespace-only →
  `string.Empty`. Exactly the owner-locked decision. `NameComparer` uses `Normalize` on both sides of
  `Equals` and for `GetHashCode` (never NRE — `Normalize` never returns null). 15 unit cases cover
  the NFC precomposed-vs-decomposed pair, case, leading/trailing/internal/tab whitespace,
  diacritic-distinct, and null/empty.
- **The 4 read-side dedups are centralized** on the shared key, and each keeps the **representative's
  raw name for display** (`g.First().TenMonHoc`), not the lowercase key — so the UI still shows
  "Toán", not "toán". `StudyAnalyticsService.ComputeSubjectInsights`, `AdaptStage.Execute`,
  `AnalyticsViewModel.SubjectOptions`, and `SqliteHocKyRepository.LayDanhSachHocKyAsync` all route
  through `Normalize`.
- **D4 — the downstream filter was fixed too, not just the dropdown.** `AnalyticsViewModel.ApplyFilters`
  compares each log's subject against `SelectedSubject` — this now uses `NameComparer.Equals`, so
  selecting a deduped option matches logs from *all* merged clones, not just the display
  representative. This was beyond the brief's literal line-4 target but is the same feature; fixing
  only the dropdown would have been a "dedup that half-works." Correct call.
- **Prevent-at-source** (`QuanLyMonHocViewModel.ThemMon`) — on **add only** (not edit), rejects a new
  name that `Normalize`-equals a **live** (`!IsDeleted`) `MonHoc` already in the semester, via
  `MessageBox` consistent with the VM's existing convention. The test-facing constructor overload
  (`(HocKy, IHocKyRepository)`) mirrors the M1.1 `FocusViewModel` dual-constructor pattern and is the
  minimal seam needed to test a VM that otherwise hard-resolves the repo via `ServiceLocator`.
- **The reconcile rewrite is right.** `LuuHocKyAsync`'s task diff is now flat across the whole `HocKy`
  (`oldTasksByMaTask`/`newTasksByMaTask` keyed by `MaTask`), and survivors are reparented (FK
  reassigned) **with `ChangeTracker.DetectChanges()` forced before any `MonHoc.Remove()`** — the D3
  ordering is the crux. EF's cascade-on-remove fixup reads the *tracked relationship snapshot* at the
  moment `Remove()` executes (these are plain POCOs on snapshot-based tracking), not the live
  `ObservableCollection`, so the FK must have moved *and* `DetectChanges` must have run first, or the
  survivor is swept into the cascade and wrongly tombstoned. This matches the known EF cascade-fixup
  timing behavior; the fix is placed correctly.

### The pre-existing-gap claim — substantiated, not trusted

The report says the reconcile collision was reachable on **unmodified M1.2** code (M1.3 only widens
the trigger). I confirmed the mechanism from the `e2f8268` source directly:

- At the M1.2 tip, `LayDanhSachHocKyAsync` **already** deduped clones with
  `GroupBy(mon => mon.TenMonHoc)` (raw name) — so two same-name `MonHoc` rows each owning a distinct
  task were already being merged into one representative.
- The M1.2 merge moved the losing clone's task into the representative's `DanhSachTask` **but never
  reassigned the task's `MaMonHoc` FK scalar** (the `task.MaMonHoc = daiDien.MaMonHoc` line is *new*
  in M1.3). That is the internally-inconsistent detached graph (nav says survivor, FK says loser)
  that makes the per-`MonHoc`-parent reconcile double-operate the same `StudyTask` row on resave.

So the collision was genuinely M1.2-era, latent because byte-identical seed clones rarely carried
*distinct* tasks; M1.3's case/whitespace key merges variants that plausibly do — widening the
trigger, not introducing the bug. The framing holds.

## Non-blocking observations (noted, not findings — none require action)

1. **Dead-clone `Rev` churn.** `LuuHocKyAsync` loads `hocKyCu` **without** the `!IsDeleted` filter,
   so a clone that was merged-away and tombstoned in a prior save is present in the old graph but
   absent from the new one, and gets re-`Remove()`d (→ `Rev++`, `IsDeleted` re-stamped `true`) on
   every subsequent resave. Harmless under LWW — `IsDeleted` stays `true`, the live/tombstoned counts
   stay 1/1, and a higher-`Rev` tombstone still merges as "deleted" in Epic 2. **The no-filter is
   deliberate and should stay:** filtering `hocKyCu` on `!IsDeleted` would make a DB-tombstoned but
   now-live row read as "new" → `Add()` → PK collision, breaking resurrection. Same class as the
   `DeleteAsync` re-tombstone idempotency noted in the M1.2-R1 review.
2. **Throw-on-abnormal-input, unreachable via the real flow.** `ToDictionary(t => t.MaTask)` throws on
   a duplicate `MaTask`, and the `.First(...)` owner lookups (lines 138, 184) throw on an incoming
   graph that wasn't deduped by `LayDanhSachHocKyAsync`. Both are impossible through the app's
   load→save path and **fail loud rather than corrupt data**. Not worth guarding.
3. **Blast radius is CRITICAL — but it's fan-out breadth from a hub write path, not a surprise.**
   `LuuHocKyAsync` backs 5 UI save flows; the discriminating + regression integration tests and the
   isolation runs are the correct mitigation, and they're present and green.
